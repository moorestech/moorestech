# 列車の開閉失敗理由は汎用モデルでなく source 側が持つ

- **日付**: 2026-09-06
- **文脈**: PR #1325 で新設した汎用モデル `SubInventoryModel` が `TrainInventoryMessageType? TrainMessage`（列車専用の開閉失敗理由）を抱え、`SetTrainMessage` は「列車ソースのみが呼ぶ」という暗黙の運用規律に依存していた。レビュー7系統が一致して指摘。AGENTS.md「汎用基盤にドメイン語彙を持ち込まない」に抵触する。

## 決定

固有状態は source 側（`TrainSubInventorySource.LastOpenMessage`）が持つ。`TrainInventoryDtoFactory.Create` は既に `TrainSubInventorySource source` を受け取っているため、消費側は `ResolveError(source.LastOpenMessage)` の1行修正で閉じる。`TrainInventoryMessageType.cs` は `Inventory/Train/` へ `git mv` する。あわせて `SetItems` 冒頭で状態をクリアし「エラー種別が入ったままアイテムが並ぶ」矛盾状態（W01）を塞ぐ。

## 棄却した案

- **派生モデル `TrainSubInventoryModel : SubInventoryModel`**: 消費側に `is TrainSubInventoryModel` の型分岐が復活し、本 PR が `ITrainInventoryView` キャスト除去で得た改善を後退させる。
- **`SubInventoryOpenFailure?` へ一般化**: ブロック取得失敗の握りつぶし（W02）も同時に閉じられるが、`block_inventory` の `Error` に新しい値が乗るため R5（Web 側 topic/action 契約は不変）に触れる。
- **現状維持**: 暗黙の運用規律への依存を残す。

## 理由

判断は具体側で行い、基盤には値をプッシュする。source は既に消費側へ渡っているので、汎用モデルを経由させる必要がそもそも無い。
