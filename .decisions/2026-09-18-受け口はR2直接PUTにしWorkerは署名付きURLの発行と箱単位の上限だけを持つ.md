# 受け口は R2 直接 PUT にし、Worker は署名付き URL の発行と箱単位の上限だけを持つ

2026-09-18 ユーザー裁定（原文「単に時間がかかるからってほぼ使われないサービスに安易に課金するその判断ってどうなの」「R2直接アップロードで変なことされたりはしない？」→ 設計対話「はい」→ 質問「R2 への直接 PUT にすると Worker はバイト列を見なくなります。サイズの縛りはどこまでやりますか？」→ 選択「ファイル単位に加えて箱単位も縛る」）。

決定: Cloudflare Workers は無料プランのまま運用する。受け口 Worker はアップロードのバイト列を中継せず、認証・許可リスト照合のあとにファイルごとの署名付き R2 PUT URL を発行し、クライアントは R2 へ直接 PUT する。署名にはファイルごとの Content-Length を含め（R2 が長さ不一致を拒否）、1ファイル 100MB の上限は維持する。加えて URL 発行時に箱全体のファイル数と合計バイト数の上限を検査し、超過は 413 で拒否して理由をログへ出す。`complete` では R2 の実オブジェクトを列挙して発行した一覧と照合する。

理由: 無料プランの CPU 上限（10ms/リクエスト）に対し、8MB 級ファイルのストリーミング中継は 120〜230ms を要して exceededCpu（503/1102）になる（2026-09-18 wrangler tail 実測）。使用頻度の低いサービスに固定費（Workers Paid）を付けない。バイト列を Worker から外せば CPU はほぼゼロになり、経過時間の上限は元々無いので低速回線にも影響しない。Worker が PUT 時にやっていた長さ検査は署名で、数と総量の検査は発行時と complete 時で置き換える。

棄却案:
- Workers Paid（月額 $5、CPU 30秒）にしてコードを変えない — 使用頻度の低いサービスへの固定費。
- ファイル単位の上限だけ（今の Worker と同じ防御範囲）— 許可リストのテスターが箱1つで無制限に送れる。
- テスターごとの累計上限も足す — 累計の集計を R2 に持つ必要があり Worker の処理が増える。
