# 旧セーブは V1→V2 ステップで救い python 手変換の案内を撤去する

2026-09-14 ユーザー裁定（plan F 実装セッションの事前計画レビューで発覚）。

## 決定

`WorldSaveAllInfoV1.CurrentVersion` を **2** とし、`SaveMigrationStepV1ToV2` を本番コードとして実装する。
ステップは旧セーブ（版1）へ `currentTick`・`randomState`・`miningCooldowns` を補い、`world[].state` の
JSON文字列値をオブジェクトへ展開する。あわせて `WorldLoaderFromJson.Load` の
「`scripts/save_migration/migrate_block_state_objects.py` で移行してください」という欠損ガードを撤去する。

## 棄却した案

- **CurrentVersion=1 のまま文書だけ直す（最小案）**: 連鎖の器だけが入り、実在する旧セーブ破損は
  python 手変換のまま残る。AGENTS.md へ「形式変更はステップを同梱せよ」と書きながら、
  プロダクションコードがテスターに python を案内し続けるという規約と製品挙動の乖離が残る。
- **版を上げつつガードは二重の安全網として残す**: ステップ適用後は必ず満たされる条件を
  ロード時に再検査することになり、ガードの文面（python 案内）を直す義務だけが残る。
  欠損3項目のうち `currentTick`（`Nullable.Value`）と `randomState`（`RestoreState` の長さ検査）は
  使用時点で例外になるため、無音の縮退にはならない。

## 理由

plan F は「plan A（`currentTick`/`randomState` 追加）は未実装」を前提に書かれていたが、実際には
コミット `0aa028699` で **既に master へマージ済み**であり、しかも `worldVersion` は 1 に据え置かれていた。
つまり「形式は変わったのに版が上がっていない」状態が実在し、旧セーブは python スクリプトでしか救えない。
plan F の目的（テスターのワールドをセーブ形式変更をまたいでロードできるようにする）を満たすには、
この既存の断絶こそが最初のマイグレーションステップの題材になる。

## 残論点（実装セッションの判断）

- 旧セーブに復元すべき正しい乱数状態は存在しない（保存されていなかった）。種0由来の固定状態へ落とす。
  python 版は world.json の seed を使っていたが、ステップは save.json しか見えないため種を持てない。
  既にプレイ済みのワールドでは乱数列の位置はいずれにせよ復元不能で、決定性さえあれば足りる。
  重複実装を避けるため `GameRandom.StateFromSeed(ulong)` を公開し `Reseed` と共有する。
- `scripts/save_migration/migrate_block_state_objects.py` は削除しない（worldVersion 導入前の
  開発者手元セーブ用の補助手順として moorestech-save-migration スキルに残る）。
