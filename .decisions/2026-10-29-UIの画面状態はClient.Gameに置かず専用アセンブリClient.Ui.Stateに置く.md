# UI の画面状態は Client.Game に置かず専用アセンブリ Client.Ui.State に置く

決定: 段階 0 で WebUiHost から `Client.Game` へ移した画面状態 13 ファイル（研究・チャレンジ・ブロック詳細・時刻表・モーダル・通知・BP 名入力の橋渡し・言語ゲート）を、中間層として新設するアセンブリ `Client.Ui.State` へ移す。参照の向きは `Client.Game` ← `Client.Ui.State` ← {`Client.Ui`（UITK）・`Client.WebUiHost`・`Client.Starter`}。段階 1 以降の新しい画面状態も `Client.Ui.State` に置く。移行計画 §3.1・§3.2 の「ViewModel は `Client.Game` に置く」はこれで置き換える。段階 0 の統合 PR（#1559）のマージ前に移す。同じ PR が既存の `Client.Game` に入れた残りの差分（`UIStateControl` の UniRx 化・言語選択待ちの NRE 修正・名前付き差し込み・旧 SkitUI の削除）は中身が正しいので残す。段階 0 より前から `Client.Game` にある画面寄りのクラスは動かさない（bd `moorestech-albof.14`）。
棄却案: (1) 計画 §3.2 のまま `Client.Game` に置く（段階 1〜5 で全画面の状態が `Client.Game` に積もる）。(2) 中間層を WebUiHost に残し UITK から読む（UITK が CEF のアセンブリに依存し、CEF なし起動ができず、段階 5 で同じ切り出しが要る）。(3) UITK の `Client.Ui` の中に置く（共存規則 R1 で `Client.Ui` が WebUiHost を触るため循環する）。(4) 差分を 0 にするため `UIStateControl` の UniRx 化を戻し新アセンブリで包む（規約違反を残す非本質的な迂回）。
理由: ユーザーの方針「既存コードへの差分は極力減らし、新規コードのアセンブリだけで対応する」。中間層は master では WebUiHost の中にあったもので、ゲームの正本ではない。移した 13 ファイルは `Client.Game` の残りから参照されず、依存の反転なしで出せる。差分を減らすための非本質的な変更はしない。
出所: ユーザー 2026-10-29「そういうのって全部UITKアセンブリに隠蔽して、UI自体はUIの制御だけに集中できないの？今後もどんどんUIが肥大化するってことにならない？」「既存コードへの差分は極力減らし、新規コードのアセンブリだけで対応する感じ」「そもそものレイヤーが Client.Game ← 中間層 → Web UIだったと思うんだけど、これをただUITKに買えるだけじゃダメなの？」「差分を0にするために変なことや非本質的なことはしていない？」→ agent が範囲を①の 13 ファイルの移動だけに絞り、②〜⑤は残すと回答 → ユーザー「いまぱっとできる？」
