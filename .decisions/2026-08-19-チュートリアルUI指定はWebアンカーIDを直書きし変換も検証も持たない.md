# チュートリアルUI指定はWebアンカーIDを直書きし変換も検証も持たない

決定: チュートリアルがUI要素を指す値は、Web側の実anchorId（`recipe.craft-button` / `hotbar.hud` / `build-menu.entry-block-<guid>` / `research.node-<guid>` 等）をマスタデータに直書きする。中間語彙 uiObjectId・変換辞書（TutorialAnchorIdMapper の対訳表）・サーバー側の値検証（ChallengeMasterUtil の ValidateUiObjectId）・Core.Master.TutorialUiObjectId は全廃。UnityはanchorIdを無変換でWebへ送り、DOMとの紐づけはWeb側の `data-tutorial-anchor` 文字列一致のみで行う。スキーマのフィールド名も実態に合わせ `highLightAnchorId` / `fromAnchorId` / `toAnchorId` へ改名。例外は実行時のitemIdからしか導出できない `recipe.item-<itemId>`（FromItemId）のみ残す。

誤設定の扱い: anchorIdの誤記は検証で弾かず素通りさせる。DOMが見つからず表示されないだけで、それは設定者の責任とする。エラー化・ログ化は行わない。mod走査の突合テスト（TutorialAnchorContractTest）は設定者向けの任意ツールとして残すが、ゲートではない。

棄却案:
- 案A: Core.Master.TutorialUiObjectId に anchorId対応表とTryParseを集約（独立レビューPR1175の推奨。二重手書きは消えるがMaster層がWebのanchorId対応表を抱え、語彙が2つのままになる）
- 案B: キーのみCore.Masterに残しパースだけ集約（二重手書きと無言ドリフトの故障シナリオが残る）
- 未知IDのthrow復帰/LogError化（レビューC2。素通り方針と正反対のため棄却）

理由: ユーザー裁定 2026-08-19。「uiObjectIdは導出規則で一意に決まり、設定者がそれを認識して書く。どのDOMがどのIDかの定義が存在すること自体は問題なく、誤設定の素通りは設定者の責任」という設計思想に対し、案A/Bはいずれも中間語彙と門番を温存しており思想から外れる。語彙を1つにすれば変換・検証・parityテスト群が丸ごと不要になる。代償（Web側アンカー改名がmodを黙って壊す）は承知の上で受け入れる。本裁定は同日の「uiObjectIdの正本はCore.Masterに置く」を上書きする。
