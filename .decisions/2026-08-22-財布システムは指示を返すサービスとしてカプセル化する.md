# 財布システムは「指示を返すサービス」としてカプセル化する

日付: 2026-08-22
出所: ユーザー裁定 2026-08-22（moores-code-review run 2026-08-22-0254 の Critical C5 / 設計判断 D3 の議論から確定）

決定: 財布（残り設置数）システムは、呼び出し側が「指示に従うだけ」で済むサービスとしてカプセル化する。設置は「これを消費せよ（空なら消費なし）」、撤去は「これを返却せよ（空なら返却なし）」という同じ形の指示を返し、判断は財布側に閉じる。ブロックが財布を持つか（`placementsPerCost > 1` か）で呼び出し側は分岐しない。

線引き: 呼び出し側が知ってよいのは「財布管理システムが存在すること／問い合わせること／指示に従うこと」まで。知ってはいけないのは財布の中身と判断ロジック — `placementsPerCost` の値・残り設置数・財布キーの正規化・「Nに達したか」の判定・`remaining + sets×N` の算術・`RequiredItems` が空かどうか。存在を知るのは可だが、段取り（Lookup を引いてから Mutation を呼ぶ順序）を呼び出し側が決めるのは不可。

理由: 財布キー正規化がプロダクション6か所の呼び出し側の責務のままで、忘れても型エラーにも実行時例外にもならず（辞書引き失敗は 0 を返す設計）「上り/下りベルトでだけ残数が常に 0」という無言の壊れ方をする。加えて撤去側が `WouldCondenseOnReturn` の bool を受けて返却アイテムを自前で組み立てており、アイテム列を受け取る設置側と非対称。財布は今まさに導入している新機構であり、漏れたままマージすると後から呼び出し側を追いかけ直すことになる。ユーザー原文「ウォレット管理システムが『素材を消費せよ』といったら素材を消費するし、『素材を返却せよ』と言ったら返却する」「財布の存在は知るが、裏で何をしているかは知らない。呼び出し側は財布管理側の指示したとおりに動くだけ」。

棄却案:
- D3案A（`GetRemainingCount` の入口で正規化するだけ）: 正規化の漏れ6か所は塞がるが、撤去側の自前計算・クライアントの `remaining + sets×N` 算術・`ResolveCostToConsume` の空配列の二義性が残る部分対処。本決定に吸収される
- D3案B（サーバー側の重複4件だけ private ヘルパへ畳む）: 同上に加えクライアント2か所の2段書きが残る
- D3案C（触らない・bd へ積む）: 新機構の漏れを温存し、将来の追加呼び出し側で無言のバグを再生産する
