# クライアントの財布窓口は問い合わせ専用の共有クラスへ集約する

日付: 2026-08-23
出所: ユーザー裁定 2026-08-23（PR #1223 のコメント https://github.com/moorestech/moorestech/pull/1223#issuecomment-5380369554 を起点とした実装確認と、それに続く grill）

背景: サーバー側は `ConstructionWalletService` が「消費せよ／返却せよ」の指示を返す形になり、設置・撤去の全プロトコルが同じ2メソッドを通るようになった（[[2026-08-22-財布システムは指示を返すサービスとしてカプセル化する]]）。一方クライアントには財布を素通りする経路と、財布の有無で分岐する箇所が3つ残っていた — `BuildMenuDetailSidebar.tsx:15` の `placementsPerCost > 1`、`ElectricWirePoleGhostPart.cs:59` の `ConstructionMaterialAffordability` 直呼び、`GearChainPoleFrameInputCollector.cs:50` の `ConstructionCostService.ToItemCounts` 直呼び。現時点で `placementsPerCost > 1` はベルトだけなので実害は出ないが、他ブロックに `>1` を書いた瞬間に型エラーも例外も出さずクライアントのプレビューだけが食い違う。

## 決定

- 財布の判断ロジックはサーバーとクライアントで**同一クラスを共有する**。共有の深さは「共有は `ConstructionWalletUtil` 止まりでクライアント窓口だけ集約する」でも「判断をサーバー独占にして置ける数を配信する」でもなく、判断クラスそのものの共有とする。
  出所: ユーザー裁定 2026-08-23 原文「そこってサーバーのロジックを使いつつ、クライアントの窓口も集約できるようにしたい」→ 選択「B: `ConstructionWalletService` を残数 lookup 注入型にして `Game.Construction` へ移設し、サーバーとクライアントが同じクラスの同じメソッドを呼ぶ」
- 共有するのは**問い合わせ専用クラス**（`IRemainingPlacementCountLookup` だけを受け取る）に切り出す。サーバーの `ConstructionWalletService` はそれを内部で使い、クライアントはそれだけを窓口として持つ。クライアントに `Commit`・mutation・payers は露出させない。`ClientRemainingPlacementCountDatastore` は `IRemainingPlacementCountLookup` の実装（ミラー）へ役割を移し、窓口の座を共有クラスへ譲る。
  出所: ユーザー裁定 2026-08-23「案2」選択
- クライアント窓口が返すのは**「何セル置けるか」の数1本**。ドラッグは返り値までを置け、電柱・ポールの単発経路は `1 <=` で判定する。3か所すべてこの1本に寄り、呼び出し側は財布の有無を意識しない。
  出所: ユーザー裁定 2026-08-23「「何セル置けるか」の数1本」選択
- webui へは生値ではなく**財布判定済みの nullable オブジェクト**（`setPlacement: {perCost, remaining} | null`）を配信する。tsx は null 判定だけで分岐し、`> 1` という述語は webui から消える。
  出所: ユーザー裁定 2026-08-23「nullable オブジェクトに畳む」選択
- `placementsPerCost > 1` をベルトファミリー限定に縛るマスタ検証は**追加しない**。クライアントの全経路が財布経由になれば逸脱しても静かに壊れないため、汎用のマスタ検証にベルトという業務語彙を持ち込まない。
  出所: ユーザー裁定 2026-08-23「縛らない・汎用のまま」選択
- 適用範囲は **PR #1223 に載せてやりきる**。[[2026-08-22-財布システムは指示を返すサービスとしてカプセル化する]] が未確定として残していた「本ブランチでやりきるか次ブランチか」を、やりきる側で確定する。
  出所: ユーザー裁定 2026-08-23「PR #1223 に載せてやりきる」選択

## 棄却案

- 共有は `ConstructionWalletUtil` 止まりにし、クライアント側だけ窓口を1つに集約する（案A）— 却下: 判断の正本が2箇所に残り続け、今回問題になっている状態を温存する。出所: ユーザー裁定 2026-08-23
- 財布の判断をサーバー独占にし「あと何セル置けるか」を配信、クライアントは表示するだけ（案C）— 却下: 所持素材が変わるたびに再計算・再配信が要り、クライアントが手元に持っている在庫をサーバーへ往復させる。出所: ユーザー裁定 2026-08-23
- `ConstructionWalletService` ごと `Game.Construction` へ移設してクライアントも同じクラスを生成する（案1）— 却下: クライアントが `CommitPlacement`・`FlushRemainingCountChanges` を呼べる窓口を持ってしまう。出所: ユーザー裁定 2026-08-23
- クライアント窓口もサーバーと同型の「消費素材列を返す指示」にする — 却下: ドラッグの N セル見積りが別メソッドで要るため、クライアント窓口が結局2本立てになる。出所: ユーザー裁定 2026-08-23
- webui へ生値のまま配信し tsx の `> 1` 分岐を表示専用として残す／表示文字列までホストが決めて配信する — 却下: 前者は判定条件の重複が残り、後者は i18n がホスト側へ移って webui の翻訳資産と二重管理になる。出所: ユーザー裁定 2026-08-23
- `BlockMasterUtil` に「`>1` はベルトファミリー所属ブロックのみ」の検証を足す — 却下: 将来ベルト以外へ財布を広げるとき検証を外す作業が要る。出所: ユーザー裁定 2026-08-23
- PR #1223 は現状でマージし、窓口集約は後続ブランチで別PR — 却下: 漏れたままマージされる期間ができる。出所: ユーザー裁定 2026-08-23
