# ベルト財布ブランチの最終レビュー裁定3件（D2 / D4 / D5）

日付: 2026-08-22
出所: ユーザー裁定 2026-08-22（AskUserQuestion。moores-code-review 全ブランチレビュー run 2026-08-22-0254 の `design.md` に対する裁定）
対象: `feature/belt-remaining-placement-count`（ADR 0026）

決定:
- **D2（凝縮判定の集約）**: 「残り設置数が N に達したか（素材1セットを返すか）」の判定式を1本に集約する。`ConstructionWalletUtil.WouldCondense(remaining, placementsPerCost) => placementsPerCost <= remaining + 1` を置き、`RemainingPlacementChargeService.WouldCondenseOnReturn` と `RemainingPlacementCountDataStore.ReturnOne` の双方がこれを呼ぶ。あわせて `ReturnOne` の未使用 `bool` 戻り値を `void` へ落とす。
- **D4（webui DTO）**: `placementsPerCost` / `remainingPlacementCount` を全kind共通の必須フィールドから **block variant へ移す**。C# 側は `int?`（`NullValueHandling.Ignore` でキー省略）、利用側は `entry.kind === "block" && entry.placementsPerCost > 1`。
- **D5（無料設置デバッグの非対称）**: **現状維持**。`FreeBlockPlacement` ON でベルトを置き OFF で撤去すると未払いの素材1セットが生まれるが、デバッグ専用トグル限定の挙動であり、旧実装（撤去毎に全額返却）より増殖量はむしろ 1/N に縮小している。

理由:
- D2: 同じ意味論の式が2実装に分裂しており、将来どちらか片方だけ直すと「財布が0に戻らない／素材が消滅する」不整合が無言で発生する。案A（式のSSOTを1本立てる）は最小変更で、撤去確定前に事前判定が必要という構造制約とも両立する。
- D4: 計画時の免責根拠は「zod の `.strict()` と C# 単一DTOの整合のため」だったが、レビューで同一DTOの `Label`/`IconUrl` が既に「非該当 kind は null → キー省略」で `.strict()` と両立していると判明し、構造的制約ではないことが確定した。現状では `{ kind:"trainCar", placementsPerCost:3 }` のような取り違えペイロードがスキーマを通過してしまう。
- D5: プロダクションのプレイヤーには影響せず、デバッグ機能の対称化には「free設置ブロックへの永続パラメータ追加」が要り、ADR 0026 の「永続台帳」裁定の枠外になる可能性がある。

棄却案:
- D2案B（`PlanReturn` → `CommitReturn` の2段階で判定を撤去前に凍結）: 判定が1度だけなのが型で見えるが `RemoveBlockProtocol` の書き換えが要る。D2案C（`ReturnOne` を `void` にし `WouldCondenseOnReturn` を唯一の判定点にする）: 最小変更だが DataStore の実測値を捨てる形が残る。D2現状維持: 片方修正の事故リスクが残る
- D4現状維持（全kind共通の必須）: 取り違えペイロードがスキーマを通る risk が残る
- D5案A（free設置ブロックに印を付け撤去側も素通り）: ブロックへの永続パラメータ追加が ADR の枠外になりうる。D5案B（ベルトファミリーで無料設置を禁止）: デバッグ機能の使い勝手が落ちる
