# ビルドメニューの財布問い合わせと素材合算は呼び出し元へ集約する

日付: 2026-08-29 / 出所: ユーザー裁定（moores-code-review 統合結果への AskUserQuestion 回答）
関連: PR #1290 / [[2026-08-28-ビルドメニューの素材不足判定はホストで行い財布残りは不足としない]] / docs/adr/0041-build-menu-material-shortage-tooltip.md

## 決定1: 「ブロックか」の判定と財布問い合わせは `BuildMenuEntryDtoFactory` へ集約する

`BuildMenuMaterialAvailability` から `ConstructionWalletQuery` 依存を外し、`paymentSkipped: bool` を受け取る形にした。
`ResolveBlockTarget` はクラス直下の `private static` へ上げ、`CreateDtos` のループ先頭で `GetWalletStatus` を1エントリ1回だけ叩き、
設置数表示（`SetPlacement`）と支払い免除（`paymentSkipped`）の両方をその1回の結果から導く。

理由: 判定が2箇所に分かれていると、財布対象の種別が増えたとき片方だけ直し漏れて
「残り2セット設置可能」と「素材が足りません」が同一スロットに同時に出る自己矛盾表示になる（両方のテストは緑のまま）。

棄却案:
- `BuildMenuMaterialAvailability` を削除し中身を `CreateDtos` のローカル関数へ戻す — ブロック解決の二重化は解けるが財布への二重問い合わせが残り、factory が約190行まで膨らむ
- 現状維持 — 現行データでは表示が矛盾しないが、財布対象種別の追加で顕在化する

## 決定2: 必要素材の同一アイテムはビルドメニュー側で合算してから比較する

`BuildMenuMaterialAvailability.CreateRequiredItemDtos` が itemId 別に初出順で合算し、`held < 合算required` を見る。
既存の設置時判定 `ConstructionCostShortageCalculator` と同じ数え方になる。

理由: 行ごとに比較すると、必要素材が同一アイテムを複数行持つブロック（木材3＋木材3・所持4）で
ビルドメニューは各行4/3で「足りている」と出すのに、実際の設置は合算6に対して不足でブロックされる。
現行マスタに重複は0件だが、重複を禁じる検証も存在しない。

棄却案:
- 合算処理を `ConstructionCostShortageCalculator` へ切り出して設置時判定と共有する — 式は一本になるが既存シグネチャ変更でゴースト段の呼び出し側まで波及する
- 現状維持＋マスタ側で itemId 一意性を検証する — コード変更は不要だが、表示と実挙動の食い違いを構造的には防げない

## 決定3: 不足素材の絞り込みは呼び出し元へインライン化する

`logic/buildMenuShortage.ts`（1行 filter）と専用テストを削除し、`BuildMenuSlot` 内で
`entry.requiredItems.filter((item) => item.lacking)` を直接書く。

理由: 直系前例（`ResearchDetailPane` の `isConsumeItemLacking` を map 内で直接呼ぶ形・`CraftRecipeEntry` の JSX 内インライン）は
コンポーネント側に直書きしている。挙動は `BuildMenuSlot.test.ts` の3ケースが保証し続ける。

棄却案:
- 現状維持（`features/recipe/logic/` の8ファイル規約に合わせる）— 規約自体は実在するが、素通しラッパー1行に専用ファイルと専用テストを起こす形は前例が支えていない
- 既存の `logic/buildMenuGrouping.ts` へ関数を足す — ファイルは増えないが grouping と shortage が同居する
