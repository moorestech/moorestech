# 裁定の忠実性 — 較正実例と特化ガイド

SKILL.md「§1.5 裁定の質問設計と記録の忠実性」の較正実例集。一般規則は本文が正で、ここは実例とドメイン特化の具体化のみを置く。

## 実例: PR1176 研究UIレイアウトの意図取り違え（2026-08-18発生・08-19検出）

ユーザー原文「研究UIの上側のちょっとしたスペースを埋めて、ほぼ全面表示にしたい」が、最終的に「研究パネルがステージ全域を占有し、持ち物パネルを上層に重畳（ノードが持ち物の裏に隠れる）」として実装・マージ直前まで到達した。取り違えは3点の複合で、いずれも§1.5の規則の違反にあたる:

1. **プレビューが帰結を隠した。** 占有範囲の裁定質問は3案とも「上端をどこまで詰めるか」の差だけで構成され、ASCIIプレビューは空パネル＋HUDのみ。重畳相手になる持ち物パネルが描かれておらず、「ノードが持ち物の裏に隠れる」帰結は一度も裁定卓に載らないまま「上端も埋めてほぼ全面」が採択された。
2. **Other自由記述の枠内圧縮。** 「持ち物パネルをどうしますか？（外す/重畳の2択）」へのOther回答「持ち物は今まで通り表示する。それ以外で全面表示する」を、既決の全域占有前提の枠内で「重畳」に写像した。自然な読みは「持ち物**以外の領域**を全面に使う」（=全域前提を覆す読み）であり、復唱確認していれば1問で止まった。
3. **架空棄却案の台帳化。** `.decisions/` に棄却案②「研究パネルが持ち物列を避けて縮む案」（=ほぼ正解の案）を記録したが、この案は会話で一度も提示されていない。「ユーザーは避ける案を検討のうえ退けた」という誤った既成事実が台帳に固定化され、以後の全レビューゲート（台帳SSOT）を素通りする根拠になった。

台帳は下流の全レビュー系統が疑わないSSOTなので、転記の歪みはレビューでは原理的に捕まらない。忠実性はここ（grill工程）でしか担保できない。

## 実例: PR1157 クラフトUIのボタン配置の取り違え（2026-08-17発生・08-20検出）

ユーザー原文「クラフトレシピには、ボタンのすぐしたにクラフトボタンを置く（そのため、クラフトレシピのエントリは少し大きくなる」（先頭の「ボタン」は誤記で、旧UIの矢印下の配置を指していた）が、「レシピ行の直下にエントリ幅のクラフト実行ボタン（秒数込み）」として台帳化・実装・マージされた。ユーザーの意図は「矢印のすぐ下に旧サイズの小ボタン」。取り違えは3点の複合:

1. **拒否後の同一選択肢の再提示。** 「"ボタンのすぐ下"の意図を確認」の二択（全幅 / 結果アイテム真下の小ボタン）をユーザーが拒否し「クラフト実行ボタン」とだけ返したのに、次の一手で**同じ二択**を再提示し、Recommended の全幅が選ばれた。ユーザーが欲しかった「矢印の下に小ボタン」はどちらの選択肢にも無かった。拒否は「選択肢が合わない」のシグナルであり、自由記述で形を取るべき場面だった。
2. **プレビュー副次情報の昇格。** プレビュー図の「クラフト (2秒)」から「秒数込み」が決定文に入り、旧UIで矢印下にあった秒数表示が消えた。秒数の置き場は一度も質問されていない。
3. **原文引用の欠落。** `.decisions/` の出所は「プレビュー付き質問で全幅ボタン案を採択」のみで原文の句が無く、下流の含意チェック（reviewer §5）は検査対象を持たなかった。独立レビューは `.craftButton 107.6px→全幅` と `.craftTime削除` の diff を正確に見ていたが、`suppressed-by: ユーザー裁定（決定3）` で折り畳んだ。

## ドメイン特化: UIレイアウト裁定のプレビュー規則

- 画面の占有・配置・重なりに関する裁定では、プレビュー（ASCII図・モック）に**その画面へ同時に表示される既存要素**（持ち物パネル・チャレンジHUD・ホットバー・キーヒント等）を必ず描く。新パネル単体の空箱モックは重なりのトレードオフを隠す。
- 既存要素と重なる案を提示するときは、選択肢の説明文に「何が何の裏に隠れるか」を明記し、回避手段（パン等）を根拠にする場合はその根拠自体を裁定対象として書く。
- 「ほぼ全面」「全画面」等の語はユーザーの発話では余白の解消を指していることがある。端まで・背後まで・重畳許容のどれを意味するかを図で確定してから採択する。
