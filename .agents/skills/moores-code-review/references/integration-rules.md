# 統合ルール（回収・照合・適用・報告の規約）

決定論スクリプト・moores設計レンズ群・汎用reviewer群・Codex外部監査・Fable全般レビューの生結果を、そのままユーザーへ転送しない。以下で1つの統合結果にマージする。

**実行者の分担**: §0〜§2.7（回収・照合・重複排除・掃引）は統合integrator（`integrators/finding-integrator.md`）が実行し、結果を `integrated.md` に書く。§3〜§5（適用・保留・安全規則）はオーケストレータが `integrated.md` を入力として実行する。各Criticalの§3/§3.5/§4への区分判定はintegratorが行い、オーケストレータは疑義がある件だけ判定し直す。

## 0. 5系統の性質の違い

- **決定論チェック（`deterministic_checks.py`）** — AGENTS.md・moorestech規約の機械判定可能分（partial・try-catch・200行・10ファイル・デフォルト引数・SerializeField命名・master_default_fallback・packet_response_root）の `confirmed`。**検出は正確で裏取り不要**（誤検出はスクリプトのバグ扱い）。ただし修正が設計作業になるものは §3/§4 の判断フローに乗せる。**例外: 200行超過（file-too-long）は努力目標** — Criticalに数えず報告のWarning備考のみ、質問・強制修正なし。
- **moores設計レンズ（`lenses/`）** — moorestech固有の設計規約（ドメイン境界・サーバー状態同期3点セット・DataStore分離・マスタデータ防御・型構造・前例一致）。実PRレビュー指摘由来。実コード（patch+cwd）を読んで `Critical` のみ返す。
- **汎用reviewer（`reviewers/`）** — 言語横断のコード品質（命名・重複・デッドコード・一方向フロー・Unity規約・React作法等）。全数調査で採用実績のある観点＋設計レンズ5本のts/tsx翻案版を採録。
- **Codex外部監査（3起動）** — 別モデルの独立第三者視点。俯瞰（3観点同梱）＋バグ狩り専任＋設計整合専任の3本を並列起動する。**コードを実行しないため行番号・事実主張を誤ることがある**。重大度(Critical/High/Medium/Low)付き。3本は同一モデルなので相互には独立系統でない（§2）。
- **Fable全般レビュー（`generalists/`）** — チェックリスト非依存の俯瞰監査。報告前にRead/Grepで**自己裏取り済み**の契約なので、Codexより軽い照合で採用できる（`[検証済み]` の事実だけspot-check）。

独立した複数機構が同じ問題を指摘したら、それは確度の高いsignal。

## 1. 実コード検証（最初に必ず行う）

- **Codexの各指摘** — 該当ファイルを実際にReadし、主張（行番号・「XがYを参照」等）が正しいか確認。**誤りは破棄、正しいものだけ採用**。
- **レンズ/reviewerのCritical** — サブエージェントが実コードを読んで出しているが、適用前に該当箇所をReadして裏取りする。precedent-alignmentの `[検証済み]` 注記はspot-checkで足りる。
- **FableのCritical** — `[検証済み]` 注記の事実をspot-check（全件再検証は不要）。`未検証` の懸念はCodexと同じ扱いで裏取り。
- **決定論チェックのconfirmed** — 裏取り不要。そのまま統合結果に載せる。
- 検証で否定された指摘は統合結果から落とす（落とした件数だけ最終報告に残す）。

### 1.5. 棄却の挙証責任（組み込み /code-review verify 層由来・2026-08-14）

指摘を「誤り」として落とせるのは、**コードから構成的に示せる場合のみ**:

1. **事実誤り** — 主張と食い違う実際の行を引用できる
2. **不可能の証明** — 型・定数・不変条件で到達不能と示せる（それを明示する）
3. **処置済み** — この diff 内のガード・修正を引用できる
4. **純スタイル** — 観測可能な挙動差が無い

「投機的だから」「実行時状態次第だから」は棄却理由に**ならない** — 競合・稀だが到達可能な null 経路（エラーハンドラ・コールドキャッシュ・欠落 optional）・falsy な 0 の欠落扱い・境界の off-by-one・リトライ嵐/部分失敗は現実的な状態であり、確定できなければ Warning として残す。上の 4 条件を引用せずに指摘を落とすのは禁止。

## 2. 重複排除

- 複数系統（決定論・レンズ・reviewer・Codex・Fable）が同一問題を指摘したら **1件に統合**し「N系統一致（高確度）」と明記する。
- 複数系統のCriticalが同じsurfaceを指す場合、両方の修正方針を満たす **1つの編集** にまとめる。片方を無視・優先しない。両立不能な場合のみ、より具体的・詳細な方を採用し、その旨を最終報告に1行記す。
- **同一モデルの複数起動は独立系統に数えない（Codex 3本）** — 俯瞰/バグ狩り/設計整合のcodex間で同一問題が重複したら1件に畳み、出所は「Codex」1系統として扱う。「N系統一致」の確度ブーストはClaude系統・決定論との一致にのみ適用する。

## 2.5. Warning/Infoの統合（3段階セベリティ・ユーザー裁定 2026-07-23）

サブエージェントの共通出力契約はCritical/Warning/Infoの3段階。二値に潰さない。

- **Warning** — 破棄禁止。統合報告に1件1行で必ず載せる（目的は「とりあえずコンテキストに乗せる」保険。確信の一段弱い実指摘が `なし` に丸められて消えるのを防ぐ）。照合は軽く（明白な事実誤認のみ落とし、落とした場合も件数を報告）。**昇格規則**: 複数系統が同一surfaceをWarning以上で指摘した場合、または照合Readで事実が確定した場合はCriticalとして扱い §3/§4 のフローに乗せる。
- **Info** — 照合不要・対応不要。報告末尾に圧縮列挙する（過検知ガードで落とした事実の記録はレンズ改善の材料になる）。
- Warning/InfoはAskUserQuestionに載せない（§4の対象は設計判断のみ）。

## 2.6. suppressed指摘の統合（免責は消音でなく降格）

- 観点ファイルが `suppressed:` 節で返した指摘は、統合結果から**削除しない**。最終報告の「免責で消された指摘」専用セクションに固定形式 `- [Critical|Warning] <指摘要約> — suppressed-by: <トレードオフ1行, 出所ラベル>` で必ず列挙する（元の重大度を行頭に保持。0件なら「suppressed: 0件」）。
- 列挙対象はCritical/Warning級のみ。Info級は列挙しない（ノイズ化防止）。
- **suppressed指摘は §3/§3.5 の自動適用対象外・§2.5 の昇格規則も適用しない**（ユーザー裁定で合意したトレードオフを黙って自動修正で覆さない）。ユーザーが報告を見て否認したら、初めて通常のCritical/Warningとして再統合し通常フローに乗せる。
- suppressed指摘はAskUserQuestionに載せない（拒否権は報告セクションの1行で行使できる）。
- `suppressed-by` の出所が `[agent前提]` の指摘が返ってきたら、それは観点ファイルの契約違反 — suppressed扱いにせず通常のCritical/Warningとして統合する。

## 2.7. 同型インスタンスの全数掃引義務（PR1095見逃し由来）

観点が「Xという形の欠陥」を1件挙げたら、**統合側はそれを1箇所の問題として受け取ってはならない**。同じ形が同じpatch内に何個あるかを必ず数え直す。

- 手順: 採用したCritical/Warningごとに、その**形を1行で言語化**し（例「到達不能な失敗経路を呼び出し側がsilent skipしている」「同じ値を作る処理が中継段で書き写されている」「新設publicメンバーの参照元が自ファイルだけ」）、patchの変更ファイル全体を `rg` で当たって同型の残りを列挙する。
- **同型は字面でなく「口」で数える**: 欠陥の形が「ある種の書き込み・副作用の口に保護機構（記録・ガード・検査）が無い」であるときは、パターン文字列の `rg` では同型が出ない。保護されるべき**口の側**を列挙する（同じ外部リソースへの書き込み経路すべて・同じside channelの呼び出し箇所すべて）→ 各口に保護があるかを1つずつ照合する（実例2026-08-18 cmux-connector: 「自書き込みを相手発と誤読しないためのresidue記録」の欠落を配置passの1箇所で採用しながら、同じpatch内の別passにある同一リソースへの書き込み口を掃引せず、本番で配置巻き戻しが再発した）。
- 見つかった同型は**元の指摘に併合する**（別件として新規に数え直さない）。修正方針は全インスタンスを1行ずつ持つ形に書き換える。
- 掃引で0件（本当にその1箇所だけ）だったときも、報告に「同型掃引: 0件」と書く。掃引したことが記録に残らないと、次回また1件だけ挙げて終わる。
- **根拠**: PR1095では「到達不能フォールバック」「カスケード重複」「不要抽象」がいずれも1件は検出できていたのに、同型の別インスタンス（計7件超）を掃引しなかったため人間レビューで見逃しとして返ってきた。検出できなかったのではなく、**検出できたものを数え上げなかった**のが失敗の形である。

## 3. 確定修正の自動適用

検証を通過した指摘のうち、次を**すべて**満たすものは確認を挟まず自動でインライン適用する（デフォルト動作）:
- 具体名（ファイル/クラス/メソッド/引数名/フィールド名）と修正方針が挙がっている
- 修正の仕方に選択の余地が無い（妥当な実装が事実上1つ）
- 波及判断が不要、または波及先が修正方針に列挙されている

適用時の規則:
- レンズ/reviewerが具体名を挙げたら**その具体名どおりに編集**する。同等処理を別構造で実装し直さない。
- 修正方針が波及（「全呼び出し元に配線」「型変更に追従」「全JSONに追加」）を含むなら、列挙対象を**すべてReadしてすべてに適用**する。一部だけ適用して「スコープ外」と切らない。
- 「集約/一本化/共有/再設計/判別共用体化/新クラス新設/レイヤ抽出」を指示されたら、指示どおり実行する。自分の判断で「最小侵襲」に読み替えて縮小しない。
- 行数・配置系指摘の修正方針が「コードの移動」を含む場合、移動が**呼び出し元の依存方向を変えるか**を適用前に確認する。依存方向が汎用層→ドメイン層のまま不変なら、行数が減っても問題は解消していない — 修正を適用せず§4の設計判断として保留する（行数圧縮で汚染を隠す抜け道の封鎖）。

## 3.5. 単独系統のcosmetic-only修正の扱い（照合して自動適用）

cosmetic/規約整形クラス（未使用引数・未使用フィールドの除去/配線、rename、`#region`再編・メンバー並べ替え、staticアクセス→DI取得、後方互換コード削除、その他**挙動を変えない**整形）は、具体的な修正内容（ファイル/対象/直し方）が示されている限り、単独系統であっても §3 どおり質問せず自動適用する。規約整形をAskUserQuestionへ回してはならない。

誤検知への防御は「質問」ではなく「実コード照合」で行う:
- 修正方針を実コードと照合し、事実誤認（対象が存在しない・既に規約準拠・実際は挙動が変わる）なら**破棄**し、報告に破棄理由を書く。
- 照合を通過したら適用する。単独系統のcosmetic適用は報告に「単独系統cosmetic」と明記する。

**構造変更**（ファイル切り出し・判別共用体化・型分割・レイヤ抽出・ロジック修正）は §3 の波及ルールに従い全件適用対象。

## 4. 設計判断の保留（末尾でAskUserQuestion）

次に該当する指摘は適用せず保留し、報告のあとに **AskUserQuestionでまとめて**方針を仰ぐ:
- 複数の妥当な選択肢がある（型分割の粒度、イベント新設の要否の裁定等）
- スコープに影響する（全JSON更新・アーキテクチャ変更・別PR切り出し）
- レンズ/reviewer/Codexの指摘同士が両立せず設計判断が要る
- CodexのHigh/Mediumで対応方針が一意に定まらないもの
- 決定論confirmedのうち修正が設計作業になるもの（partial解消・try-catch再設計等）
- レンズ/reviewerが `設計判断: あり` で返した比較付き項目（type-driven-structure・caller-orchestration等の第3出口）。備考落ちさせず必ず載せる

**本体は統合に無い選択肢を足さない（2026-08-23 C8 教訓）**: design.md が A/B を出したら、本体が「現状維持」「本PRでは触らず別issueへ」を第3選択肢として追加するのは禁止。推奨はレンズの修正方針（正解形）と一致させ、最小差分だからという理由で弱い案を推奨にしない。Critical が出口で薄まるのは体制の成果を本体が潰す行為である。

**系統間で判定が矛盾した指摘の推奨（PR1045教訓）**: 2系統が正反対の判定を返した場合、そのままAskUserQuestionへ丸投げして「現状維持(推奨)」に倒すのは禁止。先に**どちらのレンズの適用条件が本件に合っているか**を実コードで検証し（例: 「正解形前例はDTO文脈か、本件は振る舞いを持つ型か」）、検証結果に基づいて推奨を決めるか、検証で決着しない場合のみ推奨なしで両論併記する。ユーザーは推奨に強くアンカーされる — 誤った推奨は質問の意味を無効化する。

cosmetic/規約整形（§3.5）は設計判断ではない。AskUserQuestionに含めず自動適用する。保留0件ならAskUserQuestionはスキップ。

**AskUserQuestionに載せるの禁止（ユーザー裁定 2026-07-23）**: コメントの短縮・文体（convention-guardが自己裁定で完結）、200行超過・ファイル分割（努力目標。Warning備考として報告に1行載せるのみで、修正を強制しない）。質問はアーキテクチャ・パターン選択・スコープといった本質的な設計判断に限る。

## 5. 安全規則（適用は判断ではなく機械的制約）

- syntax/build/import breakを起こさないよう整合させる。
- 編集・移植コードのデバッグ出力（`Debug.Log`/`print`/`console.log`）は削除する。
- 未指示のscope-shrink/rename、無関係なchurnを混ぜない。
- `dist/ build/ node_modules/ vendor/ Library/ Temp/ obj/ bin/`・lockfile・`*.meta`・Prefab/シーン等のUnity YAMLは触らない。
- .csを修正したら `uloop compile --project-path ./moorestech_client` でエラー0を確認。影響範囲のテストがあれば `--filter-type regex` で限定実行する。

## 6. 出所ラベルと偽装の禁止（4カテゴリcontextを書くとき）

- 「許容するトレードオフ」「目指さない」の各行に出所ラベル必須: `[ユーザー裁定: "発言引用" または AskUserQuestion結果 YYYY-MM-DD]` / `[ADR: <spec名>#<台帳項目>]` / `[agent前提]`。欠落は deterministic_checks の `context_source_label` がconfirmedとして検出する。
- ラベル無し・引用不能な行は自動的に `[agent前提]` 扱い。`[agent前提]` は免責力を持たない（観点ファイルは通常のCritical/Warningとして返す）。
- ユーザーのrevert指示を「合意」と誤読しない（revert=現状維持≠agreement）。
- 会話の含意・推論を「合意」として扱わない。合意は発言として存在するか否かの2値。
- 自分の判断を `[ユーザー裁定]` と書き換えない。spec/plan等の文書に選択の記載があること自体は合意ではない（AI自身が書いた文書は特に）— 台帳掲載＋ユーザー承認済みの項目だけが `[ADR:]` を名乗れる。「今回のスコープ外」等の私的判断は「目指さない」欄に `[agent前提]` として記す。
- 規約からの帰結を「合意済み」と書いて代替案を狭めない。
