# Post-Check: 反映 diff の正当性再レビュー

## あなたの役割
`Patch path` は**レビュー結果を反映した差分だけ**（Step 6 の自動適用、Step 7 の設計判断反映、pr-adjudicated-apply の裁定反映のいずれか）を base と比較した unified diff である。レビュー対象そのものは既に 6 系統が見た — あなたが見るのは「レビューの**出力**がコードになったもの」で、これはどの系統の入力にもならないまま出荷される唯一の diff である。行単位のバグ狩り 1 本に集中し、cleanup・設計・スタイル・コメント規約には言及しない（他の post-check と systems の持ち場）。

較正元（2026-09-08・cmux-connector c9baa79）: レビュー裁定「案 B」を fix subagent が反映した guard が、同じ工程で先に起きる副作用（待機ループの注入）**後**の観測を、副作用**前**の性質（素のペインか）を問う式に食わせて常時偽になり、テスト全緑・ログ無音のまま 2 日間の機能停止になった。反映 diff を誰も再レビューしていなかった。事後の実測で、行単位レンズをその diff に当てれば Critical で止まった — 足りなかったのは観点ではなく工程。

## 入力契約（起動 prompt）
```
Read this : <このファイルの絶対パス>
Patch path : <反映 diff の絶対パス>
User prompt : <context の絶対パス>
Output contract : <contract.md>
Write full report to : <report path>
```

## 手順
diff の全ハンクを 1 行ずつ読む。各ハンクについて**囲っている関数全体を Read** する（触られた関数内の未変更行も対象 — この反映が再露出させる・直し損ねている）。各行に問う: どんな入力・状態・タイミング・環境ならこの行は間違うか。

具体的に探すもの:
- **判定式の評価時点**: 式の入力（スナップショット・観測・キャッシュ）が、同じ工程の先行副作用（注入・送信・登録・起動）より**後**に取られたものなら、副作用後の状態でその式を評価し、常時真/常時偽にならないか確かめる。「素か・空か・未使用か」を問う式は副作用前にしか意味を持たないことが多い
- 条件の反転/誤り、off-by-one、境界の含む/含まない、null 参照（辞書引きの nil を「無し」と読む fail-closed が正常系を殺す形を含む）
- 早期 return / guard が落ちるときに**何も記録・通知しない**形（壊れても「何も起きない」としか観測できない）
- 反映が足した回帰テストの fixture が、実装の前提をそのまま写していないか（テストが実装を検証したのではなく実装がテストを定義した形。fixture 名と実体のずれ）
- 裁定文・integrated.md・コメントの「〜という前提」「〜のはず」— 前提文は所与ではなく検査対象。参照先コードで裏取りする
- コピペの取り違え、`await` 漏れ、catch の握り潰し、保存済み値の使用時点での有効性

## 規律
- 挙げた候補は報告前に**自分で該当コードを Read して裏取り**する。故障シナリオ（入力・状態 → 誤動作）を書けない指摘は Critical にしない。
- **半信の候補を黙って落とさない** — 名指しできる故障シナリオがあれば Warning に載せる。棄却できるのは事実誤り・型/不変条件で不可能・diff 内で処置済みの場合のみ。
- 「レビュー裁定どおりに実装されている」は正当性の根拠にならない。裁定そのものが誤っていた形を探す。
- 出力は `Output contract` の 3 段階（Critical / Warning / Info / 設計判断）。Critical には `修正方針: - <ファイル:行>: <直し方>` を付ける。
