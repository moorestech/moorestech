# 採用ロジックバグの反証と実証

統合後の採用 Critical のうち、入力・状態から観測可能な誤動作を名指しできるものだけを扱う。既定では起動せず、明示された `verifyByRepro` が有効なときだけ実行する。

1. 環境ローカル規約を読んで使い捨て worktree を作る。メイン作業ツリーには触れない。許可されたパス以外の現物を読まない。対象状態は HEAD だけでなく `Patch path` の未コミット差分も含めて隔離側へ再現し、変更後の対象ファイルが一致することを確認する。環境ローカル規約のコマンドが作成と資産コピーを担当するときはそれを使う。
2. 指摘の入力・状態を独立に構成した失敗テストを書いて実行する。コンパイル失敗や別の既存エラーをバグの再現として扱わない。Unity のテストは環境ローカルの手順に従う。
3. 期待する誤動作で落ちたら、提示された修正方針を隔離側へ当て、同じテストが通ることを確認する。テストを期待値だけ変えて通さない。区切りごとに隔離側でコミットする。
4. `Write full report to` へ、コマンド・対象リビジョン・失敗と成功のログ行・観測値・修正差分・テストの場所を書く。修正差分は報告へ保存し、メイン側へ適用しない。
5. 自分が起動したプロセスの PID を記録して止め、隔離 worktree を環境ローカル規約に従って片付ける。失敗したら `cleaned=false` と残存パス・PID を報告し、親が気づけるようにする。

結果は指摘ごとに次のいずれかで返す。

- **実証済み**: 同じテストが修正前に意図した理由で失敗し、修正後に成功した。
- **反証済み**: §1.5（`references/integration-rules.md`）の事実誤り・不可能の証明・処置済みなどを構成的に示せた。根拠のコード行・観測値を書く。
- **再現できず**: 環境障害、対象状態の再構成不能、テスト不成立、単に通った等。理由を書く。再現できないだけでは指摘を落とさない。

返答は `status`・`evidence`・`cleaned`・`report_written` の構造化出力だけ。バックグラウンドのポーリングで待たず、全部前景で実行する。
