# postmortem — 事後検証の裁定と再発防止

「体制・工程があったのになぜ防げなかったか」に証拠つきで答え、体制への手当てを**最小介入**で設計・検証する。対象は任意の事案 — コードバグのレビューすり抜け、ユーザー意図の取り違え(grill・計画工程の転写事故)、運用事故、エージェントプロセスの失敗。

## 全事案共通の5原則

1. **実測が先。** 推測(「〜したはず」「見たはず」)で語らず、一次資料(git履歴・セッションtranscript・レビュー/裁定記録・実行ログ)で「誰が・どの工程が・何を・どの入力で見たか」を確定する。全裁定はこの実測に載る。
2. **件別裁定。** 見逃しを4類型(軸違い・枠内最適化・構造的死角・免罪)へ仕分け、帰責(設計の失敗 / 個別の落ち度 / 不可避)を件別に言い分ける。「概ね仕方なかった」型の総括は裁定になっていない。
3. **裁定ゲート(HARD GATE)。** 対策より先に裁定だけをユーザーへ提示し、GO を得るまで適用系作業(ファイル編集・コミット・PR・push)を一切しない。裁定と対策を同ターンに混載しない — 先に対策を出すと裁定が対策に引っ張られる。
4. **対策は最小段ラダー。** バグ修正のみ → 既存観点・既存手順への数行追記(既定) → 新観点・新手順の追加(ユーザー確認必須) → 発火条件・工程の変更。上の段は下の段で足りない理由を言えるときだけ。
5. **対策は実測検証。** 当時の実入力(導入コミットの diff・当時の transcript 断片)をフィクスチャに、対策が事故を止めたかを再実行で確かめる。適用して終わりにしない。

## 事案タイプの選択

- **トラックA: レビュー体制をすり抜けたコードバグ** → 下の詳細手順をそのまま実行する(このスキルの原型で、最も較正済み)。
- **トラックB: それ以外の任意の事案**(意図の取り違え・転写事故・運用事故・プロセス失敗) → トラックAの手順を次の写像で読み替えて実行する。判断に迷う概念(裁定ゲート・ラダー・検証設計)はトラックAの該当 Step を原文で参照する。

## トラックB: 一般事案への写像

- **前提条件の読み替え**: 「技術的な根本原因が確定済み」→「何が起きたかの事実関係が確定済み」。事実調査とこのポストモーテムを混ぜない — 裁定は「事実 X をなぜ体制が見なかったか」という第二階の問い。
- **Step 1.5(再発照合)はそのまま適用する**: 台帳は事案タイプ共通(コードバグも取り違えも運用事故も同じ registry.md)。系統タグが機構ベースなので、トラックが違っても同系統(例: 転写忠実性)は照合に掛かる。
- **Step 1 の読み替え**: 「どのレビュー回がそのコードを見たか」→「どの工程・どのセッションがその事実を見たか、見られたはずだったか」。一次資料はセッション transcript・裁定台帳(`.decisions/` 等)・skill 実行記録(logs repo の `harness/`)。**セッション考古学はまず `../moorestech_logs` の README 手順**(git blame → `map/commit-sessions.tsv` → `claude/` / `codex/` の生ログ)で行う — コミット→セッションの同定は map が唯一の結合層で、codex セッション(codex-implement 等)は logs repo にしか無い(`~/.claude/projects/` 直読みだと「記録なし」と誤結論する)。`~/.claude/projects/` 直読みは同一マシン・進行中セッションの近道としてのみ可。**各工程の入力源を実ファイルで確定する**こと — 「工程がその情報を持っていたか」は発火条件の実測と同じ重みを持つ(実例 — レビューの「ユーザー意図」の入力源が、実装セッションが誤転写済み ADR から自己申告した context.md であり、ユーザー原文はどの観点の入力にも構造的に入っていなかった。この実測だけで裁定が「レンズの落ち度」から「構造的死角」に変わった)。
- **4類型はそのまま適用できる**: 軸違い=その事実を正面から見たが問うた質問の軸が違った / 枠内最適化=誤った前提の枠内で局所を几帳面に改善し、枠自体は誰も問わなかった(**誤りをテスト・台帳・記録として焼き込み既成事実化した形跡を必ず探す** — 誤解釈が e2e アサーションや棄却案記録として固定化されると以後は「正しさ」として保護される) / 構造的死角=その事実がどの工程の観測対象でもなかった(転写の忠実性・原文との突き合わせに担当工程が無い等) / 免罪=見えていたが競合する正しい規約が既製の言い訳を与えた(例: 「裁定済みの `.decisions` は所与であり再審しない」)。
- **横断で必ず確認する癖**(トラックAの3点の一般形): ①下流工程が上流の成果物(ADR・context・台帳)を所与として受け取っていないか — 原文との転写忠実性は誰が観測するか。②観点・工程の発火が代理指標(diff サイズ・ファイル種別)に紐付いて、事故の再現条件を系統的に外していないか。③検証・QA が「体制自身の成果物」に対する自己参照になっていないか(ADR に対する目視 QA は ADR の誤りを原理的に検出できない)。
- **Step 5 検証の読み替え**: フィクスチャは「事故を持ち込んだ当時の実入力」— 導入コミットの diff、誤読された発言の transcript 断片、当時の裁定質問文。後知恵(事故の存在)を context に混ぜない・リーク注記を報告に書く、はトラックAと同一。対策が手順追記(復唱確認・記録規約等)の場合は、当時の入力に手順を適用して事故が止まった経路(再質問が発生する・記録が拒否される)へ到達するかを見る。対話工程(grill・インタビュー・裁定転写)の対策の具体レシピ(決定的瞬間の凍結リプレイ・台帳転写リプレイ・新旧A/B・誤爆側)は [references/interview-stage-backtest.md](references/interview-stage-backtest.md)。**実装者本人のループ**(skill 未起動の単独 fix セッションで、計測→plan→修正と進む中の 1 判断が事故)の対策は同ファイルのレシピ 3(実装判断の凍結リプレイ)で検証する — フィクスチャは事故の判断直前に実装者が手元に持っていた計測出力・前例観察・plan 草稿(実例 — ItemListPanel スクロール事案: 07:16 の計測に `panel h452 / viewport h46` が並んでいた時点を凍結し、新版 webui-design で plan を書かせて「mah の責務(器/中身)を問う項目が plan に載るか」を合否にした)。
- **記録**: 事故→裁定→対策→検証を issue tracker(bd 等)へ。トラックAの Step 6 と同じ。

## トラックA: レビューすり抜け不具合(原型・詳細手順)

### 前提条件

- 各不具合の**技術的な根本原因が確定済み**であること(issue 化されていること)。原因調査とこのポストモーテムを混ぜない — 裁定は「原因 X のバグを体制がなぜ見なかったか」という第二階の問いであり、X が揺れていると裁定も揺れる。
- レビュー体制が skill / スクリプトとして読める形で存在すること(観点ファイル・発火条件・light/full 等のモード定義)。

### Step 1: 「そのコードを、どのレビュー回が見たか」を実測する

推測(「レビューしたはず」)で語らない。全裁定はここの実測に載る:

```bash
git log --oneline --grep="<レビュー skill 名>"        # レビュー実施コミットの一覧
git log --oneline -S"<バグの核心シンボル/文字列>" -- <path>  # そのコードの導入・変更コミット
git show <レビューコミット> --stat                      # そのレビュー回が見た diff のファイル集合
```

コミットを書いた工程・セッションの同定は `../moorestech_logs/map/commit-sessions.tsv` を正とする(`grep <sha>` で agent と session_id が引ける。手順は logs repo の README)。`~/.claude/projects/` の総当たり grep は誤同定・codex セッションの見落としを生む。

突合して各不具合を 3 群に分ける: (a) レビュー回の diff に**入っていた**、(b) 入っていないが**発火条件を満たせば見えた**、(c) どの構成でも**見えなかった**。あわせてレビュー skill 側の実発火条件(既定モード、観点の extensions/keywords ゲート、閾値、investigator の起動条件)を**ファイルを読んで**確定する — 「full なら捕まえた」は発火条件を読まずに言ってはいけない(実例 — 境界・統合系の観点が「full 明示かつ変更ファイル数の閾値超え」でしか発火せず、小さい diff の積み重ねで育った機能では一度も走っていなかった。この事実だけで裁定が「不可避」から「構造的死角」に変わった)。

### Step 1.5: 再発照合 — 過去事案の系統台帳と突き合わせる

今回の事案が**初発か系統再発か**を裁定の前に確定する。正本は累積台帳 `../moorestech_logs/harness/postmortem/registry.md`(形式・タグ運用・照合手順の詳細は [references/recurrence-registry.md](references/recurrence-registry.md)):

1. 台帳を系統タグ・機構の言葉(「転写忠実性」「発火条件の代理指標」等。症状の逆さ書きで引かない)で grep し、同系統候補を挙げる。ヒット無しでも機構の言い換えで 2〜3 回引き直す。
2. ヒットしたら**深掘りは必ず read-only サブエージェントへ委譲する**(本体で台帳の続きを読んで済ませない — 一次資料の全文読みは本体 context を焼き、今回事案の先入観が判定に混ざる)。入力: 今回事案の症状・機構の一行記述＋ヒットブロックの「記録」欄の一次資料パス＋「対策」欄のコミット。出力: **前対策の不発理由の 4 分類判定と根拠**: (a) 発火せず — 発火条件・モードが今回の入力を外した / (b) 発火したが降格・注意希釈で届かなかった / (c) 後の skill 編集で対策が消えた・薄まった(対策追記行の git blame で確認) / (d) 対策が兄弟変種のみカバーし今回の変種は枠外。判定根拠は一次資料(skill 本文の履歴・当時のレビュー実行記録)で取らせる。
3. Step 2.5 の裁定提示に「**再発判定**: 初発(照合済み・近縁なし) / 系統再発(前対策 X が理由 Y で不発)」の行を必ず含める。系統再発は帰責を変えうる — 新規の構造的死角ではなく「既存対策の腐敗・発火漏れ」という別の裁定になる。照合を省いたのか初発なのかを区別できるよう、初発でも照合した旨を書く。

### Step 2: 件別裁定 — 見逃しの 4 類型

各不具合を 1 つに仕分け、**類型ごとに帰責が違う**ことを明示して答える:

| 類型 | 定義 | 帰責 | 見つけ方 |
|---|---|---|---|
| **軸違い** | 当該コードを正面からレビューしたが、問うた質問の軸が違った | 最も避けやすかった落ち度 | レビュー起因の修正コミット・doc 内のレビュー痕跡から「何を議論したか」を復元し、事故の軸と比べる |
| **枠内最適化** | レビューを重ねて局所を改善しながら、枠の外の性質を悪化させた | 最大の落ち度になりやすい。**「レビューが悪化させた」形跡を必ず探す** | 事故箇所の強化系コミット(リトライをしぶとく・ガードを厳しく等)がレビュー由来か確認 |
| **構造的死角** | 発火条件・工程・e2e 規約が、壊れた条件を体制の設計として除外していた | 個人でなく体制の設計の失敗 | 発火条件と検証規約を読み、「事故の再現条件はどの構成でも観測対象に入るか」を問う |
| **免罪** | diff に見えていたが、競合する正しい規約が既製の言い訳を与えた | 安いミス | 事故箇所の近くに「同じ論拠で逆の判断をした例」がないか探す(あれば免罪の証拠) |

裁定の言葉は「設計の失敗 / 個別の落ち度 / 不可避」を件別に使い分ける。全部まとめて一つの結論にしない — ユーザーが求めているのは件別の帰責であり、「概ね仕方なかった」型の総括は裁定になっていない。

**横断で必ず確認する体制の癖**: ①コード内コメントの「〜という前提」をレビューが所与として受け取っていないか(前提は審査対象)。②境界(マシン・プロセス・時刻)を見る観点の発火が diff サイズ等の代理指標に紐付いていないか。③e2e・検証規約が安全のために本番と違う次元(権限・トポロジ・他クライアント)を系統的に外していないか。

### Step 2.5: 裁定ゲート(HARD GATE) — ここで一旦停止してユーザーへ裁定を提示する

Step 2 までの裁定(件別の類型・帰責・実測根拠)をユーザーへ提示し、**GO を得るまで Step 4 以降の適用系作業(観点ファイルの編集・コミット・PR 作成・push)を一切行わない**。段 2(既存観点への数行追記)が「既定」なのは対策ラダー内の選択の話であり、適用を無確認で進めてよいという意味ではない — このスキルの依頼は「まず裁定だけ欲しい」が既定形(実例 — 裁定と同ターンで段 2 適用+PR 作成まで進めて差し戻された。変更内容自体は妥当でも、適用のタイミングはユーザーの裁量)。
GO 前に許されるのは読み取り専用の準備だけ: 対策案の文面ドラフト(提示用)、検証フィクスチャの特定(`git log -S`)、Step 5 の検証設計。検証の実施(agent 起動)は読み取り専用だが計算資源を使うため、裁定提示と同時に「GO 後に検証まで進めてよいか」を添えて確認するのが既定。

### Step 3: 対策の工程配置 — 前段(spec/plan)か後段(diff レビュー)か

- **「書かれていないもの」**(概念の欠落・状態列挙の漏れ・未検証の前提)→ 前段。diff レビューは「書かれたもの」しか原理的に見えない。
- **diff の中に見えている情報**(区別を潰す置換・見えている手抜き)→ 後段。前段の穴があってもレビューの免罪符にはならない。
- 前段へ移すときの副作用に注意: 「spec に書いてないから見ない」が後段で強まる。後段に**前段の前提そのものを疑う観点を最低 1 本**残す。

### Step 4: 対策ラダー — 必ず最小段から(最重要)

事故 1 件につき、下から順に検討し**上の段は下の段で足りない理由を言えるときだけ**:

1. **バグ修正のみ** — 単発の実装ミス。観点新設はそれ自体が過学習。
2. **既存観点への数行追記(既定)** — 既存レビュアーの例示リスト・適用例を実戦で較正する。エージェントは例示に強く引っ張られるので、常時発火系の箇条書きに 1 項目足すだけで探索対象が変わる。トークン増ほぼゼロ・誤発火の概念なし。
3. **新観点の追加 — ユーザー確認必須** — 通過条件は 3 つ全部: (a) 欠陥が**古典的な一般クラス名で言える**(TOCTOU・fail-open 等。言えないなら症状の逆さ書き)、(b) 既存観点に持ち場がない、(c) そのリポジトリで再発確率が高い構造的理由がある。
4. **発火条件・工程の変更** — 構造的死角の類型にのみ対応する重い手。

**系統再発時(Step 1.5 でヒット)は既存対策の修理が第一候補**。同系統に対策を 2 本並べるのが最悪形(注意希釈・観点膨張)。不発理由 (a)〜(d) に対応する修理 — 発火条件の是正 / 出力経路の格上げ / 消えた追記の復元 / 変種を包摂する一般化 — を段 2 以下として先に検討し、並列の新設はそれで足りない理由を言えるときだけ。

やってはいけない: **症状特化 reviewer の追加**(`retry`/`sleep` 等の頻出語 keywords ゲートは恒常的な誤発火トークンを燃やし、事故のたびに足せば観点総数が膨らんで注意希釈で全体が劣化する)。判定質問 — 「この観点は、今回の事故を知らない人に対しても独立に価値があると説明できるか」。No なら段 2 へ下げる。

### Step 5: 検証 — バグを持ち込んだ実コミットで再レビューする

対策(プロンプト追記)は適用して終わりにせず、効くことを実測する:

0. **検証設計シートを対策 1 件ごとに先に埋める(Step 2.5 の裁定提示に同梱する)**。検証を「やってみて出た結果」にせず、合格の定義を実行前に固定する。埋める項目は 3 つ: (i) **対策の置き場が事故時に走った工程か** — 走っていない工程(レビュー・計画 skill 等)へ追記しても当該事故には届かない(Step 1.5 の (a) 発火せず)。事故時の工程列を transcript で確定し、その工程の入力に対策が載る置き場を選ぶ。 (ii) **フィクスチャ＝事故の決定的瞬間の直前状態** — レビュー系は導入コミット diff、対話系は直前までの凍結状態、実装者ループ系はその判断直前の計測出力・読んだコード・plan 草稿(時刻と transcript 行で特定する)。 (iii) **合格＝事故を止めた出力経路への到達** — 「言及した」ではなく「plan の項目になった / 再質問が発生した / Critical に載った」の行動・成果物で書く。 **項目はこの 3 つだけ。** 旧版 FAIL の確認・誤爆側・n≥2 は必須項目ではない — 旧版 FAIL は事故の実記録(当時のレビュー出力・transcript)そのものであり再実行で取り直さない。誤爆側・n≥2 は**新観点の追加(段 3)か、対話・実装判断の揺れを測る対策に限り**、「この事案で何の情報が増えるか」を 1 行書けるときだけ足す(実例 — timber 名前推測事案 2026-08-23: 既存レンズの降格理由 1 行を消す対策に旧版対照・誤爆側・出口リプレイの 3 体を並べ、「表を埋めるため」と判明して全部外した。手順を埋める目的で agent を起こさない)。常設化(既設の回帰網へ 1 件落とせるか)は書けるなら書く。具体レシピは [references/interview-stage-backtest.md](references/interview-stage-backtest.md)(レシピ 1〜3)。
   **「再発防止できた」と言えるのは (i)〜(iii) が全部 PASS のときだけ**。どれか 1 つでも欠けたら表では `部分検証(欠けた項目名)` と書き、`検証済み` と書かない。
1. **フィクスチャは「導入コミット」**。`git log -S` で欠陥を最初に持ち込んだコミットを特定し `git show` で diff 化する。後続の強化・リネームコミットでは不可 — 正しく書かれたレビュアーは「この diff の導入ではない」と棄却する(実測済み。むしろその棄却が出たらレビュアーの精度の証拠として記録する)。
2. **context ファイルは当時の作者のゴールを書く**。後知恵(事故の存在)を混ぜると検証にならない。
3. **リーク対策**。追記文に事故の実例注記を入れた場合、agent への指示に「当該コミットより後の修正コミット・障害記録を根拠にしない — diff と参照先コードのみから判断する」の縛りを必ず入れ、報告時にもリークの疑いを割り引いて明記する(消せない限界として正直に書く)。
4. **誤爆側は新観点(段 3)を足したときだけ**。導入コミットでない類似 diff を渡し、新しい観点が正しく棄却するかを見る。既存観点への追記では省く。
5. 判定は agent の返答 3 行でなくレポート全文で行う。「捕獲」と言えるのは**故障シナリオを diff と参照コードから独自に構成している**場合のみ。
6. **単離合格で終わらせない — 実レビューが大規模 diff を見ていたなら、実入力そのものでフルスケール再実行する**。導入コミット単体のフィクスチャは注意が集中するため「ルールの検出力」しか測れず、実運用条件での発火は別問題(実測 — 単離 676 行で即 Critical 捕獲した追記が、実 PR 9512 行では 2 回連続で備考へ降格した)。実レビューの入力 diff・context は独立レビューの runs ディレクトリ(logs repo)に現存するのでそれを使い、観点の指定モデルと同じモデルで回す。
7. **合格判定は「事故を防いだ出力経路に到達したか」で行う**。備考・低 severity での言及は、統合フローでユーザーまで届かなければ防げていない。Critical、または AskUserQuestion へ載る `設計判断` 等、「当時これがあれば裁定が実装マージ前に来ていた」経路への到達を合格条件にする。
8. **フルスケールで落ちたら、降格の推論文を読んで抜け道を 1 周 1 個ずつ塞ぐ(打ち切り条件付き)**。実測した抜け道 2 種 — (a) 形式論降格: 「前身も未実装」「意図不明」を根拠に帰結を見ずに ok 側へ倒す → 故障シナリオ構成を必須化し、ユーザー可視の破綻なら格上げ、で塞がる。(b) 浅いシナリオ構成: 「機構側に新設対象の語彙が無いから影響しない」→「名指ししない一括機構では語彙の不在を安全根拠にしない。出荷データの実呼び出しの最大作用ケースを当てはめて画面・状態を言う」で塞がる。1 周ごとに再実行し、追記文が事故の輪郭の逆さ書きに近づいたら打ち切って到達点を正直に記録する。フルスケールは実行間で指摘の顔ぶれが揺れる(n=1 は確率保証でない)ことも記録に明記する。

9. **検証カバレッジを表で強く明示する(報告の必須規約)**。適用した対策と検証の対応は 1 対 1 ではない — 検証しやすい対策(後段レビュー系)だけ検証して全体が合格したかのような報告になりやすい。最終報告には対策 1 件 = 1 行の「対策 × 検証状態」表を必ず載せる: `検証済み(合格根拠 1 行)` / `**未検証**(理由 + 検証するなら何をするか)`。未検証の対策が 1 件でもあれば、報告**冒頭の結論行**に「⚠ 対策 N 件中 M 件は未検証(バックテストなし)」を置く。ユーザーは本文を一言一句読まない前提で書く — 限界節・残課題の一文に埋めるのは明示と見なさない(実例 — 前段 grill 側の対策 3 点が未検証である旨を本文の限界列挙でしか述べず、ユーザーの問い直しで初めて伝わった。後段だけの検証合格が全体の合格として読まれた)。

### Step 6: 記録と締め

- **再発照合台帳 `registry.md` へ 1 事案 1 ブロックを必ず追記する**(形式は [references/recurrence-registry.md](references/recurrence-registry.md))。追記漏れは次回の Step 1.5 を盲目にする — 台帳はこのスキル自身が育てる。
- 事故→裁定→対策→検証結果をプロジェクトの issue tracker(bd 等)に残す。検証レポートのパス・テストの限界(リーク疑い等)・未着手の残課題(前段への手当て等)に加え、Step 5-9 の「対策 × 検証状態」表を handoff note にも転記する。
- レビュー skill 側の変更は skill のリポジトリへコミットし、コミットメッセージに「何の事故の較正か」「新観点を足さなかった理由(ユーザー裁定)」を残す。コミットは Step 2.5 で得た GO の範囲内で行い、PR 作成・push はユーザーの明示指示があるときのみ(リポジトリの「push まで全自動」系の一般裁定をこのスキルへ勝手に延長しない)。

## Gotchas(両トラック共通)

- **裁定を出す前に手当ての議論を始めない。** ユーザーの問いは「なぜすり抜けたか・帰責はどこか」であり、対策はその次。先に対策を出すと裁定が対策に引っ張られる。
- **「直近のレビュー回は事故箇所を見ていない」はよくある**。その場合「体制があったのにすり抜けた」の正確な形は「事故箇所を見たのは別のレビュー回だった」— まずそれを言ってから件別に入る。
- **スコープを狭く読んで自己流に流れない。** 「コードバグではないから対象外」と判定して枠組みなしのポストモーテムをすると、実測なしの裁定・裁定と対策の混載が起きる(実例 — 意図取り違え事案を対象外と誤判定し、レビュー実測を飛ばした自己流分析で提出した)。事案が「体制・工程があったのに防げなかった」の形をしていれば本スキルの対象。
- 対策の初回提案は症状特化に寄る(実績 — 「特化 reviewer 3 本」→「一般化 reviewer 1 本」→「既存観点への追記のみ」と 2 回却下されて縮み、最終形だけが採用された)。**最初から段 2 を既定として出す。** 新観点はコスト(恒常トークン・注意希釈)を明示した上でユーザーに判断を渡す。
- doc コメントに残るレビュー痕跡(「クロスレビューで確定」等)は「レビューが厚かった」証拠であると同時に、**何の軸で議論したかの一次資料**。軸違い・枠内最適化の裁定はここから復元する。
- 検証 agent が API 断で落ちてレポート未出力のことがある。レポートファイルの存在を確認してから判定し、無ければ再起動する。
