# playbook — 裁定の枠組みと対策の作り方(選択肢)

SKILL.md の「使える道具」の本体。レビューすり抜け事案で較正した型だが、意図の取り違え・運用事故・プロセス失敗にも読み替えて使える。全部使う必要はない。

## 1. 「その事実を、どの工程が見たか」を実測する

```bash
git log --oneline --grep="<レビュー skill 名>"          # レビュー実施コミット
git log --oneline -S"<バグの核心シンボル>" -- <path>    # 導入・変更コミット
git show <レビューコミット> --stat                        # そのレビュー回が見た diff の集合
```

コミット→セッションの同定は logs repo のコミット↔セッション対応表(moorestech: `map/commit-sessions.tsv` を `grep <sha>`)を正とする。

各不具合を 3 群に分ける: (a) レビュー回の diff に入っていた / (b) 入っていないが発火条件を満たせば見えた / (c) どの構成でも見えなかった。発火条件(既定モード・extensions/keywords ゲート・閾値・investigator の起動条件)は**ファイルを読んで**確定する — 「full なら捕まえた」を読まずに言わない(実例: 境界系の観点が「full 明示かつファイル数閾値超え」でしか発火せず、小さい diff の積み重ねで育った機能では一度も走っていなかった。この事実だけで裁定が「不可避」から「構造的死角」に変わった)。

一般事案への読み替え: 「どのレビュー回が見たか」→「どの工程・どのセッションがその事実を見たか、見られたはずだったか」。**各工程の入力源を実ファイルで確定する**(実例: レビューの「ユーザー意図」の入力源が、実装セッションが誤転写済み ADR から自己申告した context.md で、ユーザー原文はどの観点の入力にも構造的に無かった → 裁定が「レンズの落ち度」から「構造的死角」へ)。

## 2. 見逃しの 4 類型と帰責

| 類型 | 定義 | 帰責 | 見つけ方 |
|---|---|---|---|
| **軸違い** | その事実を正面から見たが、問うた質問の軸が違った | 最も避けやすかった落ち度 | レビュー痕跡・doc コメントから「何を議論したか」を復元し、事故の軸と比べる |
| **枠内最適化** | 誤った前提の枠内で局所を几帳面に改善し、枠自体は誰も問わなかった | 最大の落ち度になりやすい。**「レビューが悪化させた」形跡を必ず探す** | 強化系コミット(ガードを厳しく等)がレビュー由来か。誤りをテスト・台帳に焼き込み既成事実化した形跡 |
| **構造的死角** | その事実がどの工程の観測対象でもなかった(発火条件・工程・検証規約が設計として除外) | 個人でなく体制の設計の失敗 | 発火条件と検証規約を読み、「事故の再現条件はどの構成でも観測対象に入るか」を問う |
| **免罪** | 見えていたが、競合する正しい規約が既製の言い訳を与えた(「前例と同型」「裁定済みは再審しない」) | 安いミス | 近くに「同じ論拠で逆の判断をした例」がないか探す |

帰責は「設計の失敗 / 個別の落ち度 / 不可避 / ユーザー側の与件」を件別に言い分ける。「概ね仕方なかった」型の総括は裁定ではない。

横断で確認する癖: ①下流が上流の成果物(ADR・context・コード内コメントの「〜という前提」)を所与として受け取っていないか — 原文との転写忠実性は誰が観測するか。②観点の発火が代理指標(diff サイズ・ファイル種別・.cs 以外)に紐付いて再現条件を系統的に外していないか。③検証・QA が体制自身の成果物への自己参照になっていないか(ADR に対する目視 QA は ADR の誤りを検出できない)。④「直近のレビュー回は事故箇所を見ていない」はよくある — まずそれを言ってから件別に入る。

## 3. 対策の工程配置

- 「書かれていないもの」(概念の欠落・状態列挙の漏れ・未検証の前提)→ 前段(spec/plan/grill)。diff レビューは書かれたものしか見えない。
- diff に見えている情報(区別を潰す置換・見えている手抜き)→ 後段(レビュー)。前段の穴はレビューの免罪符にならない。
- 前段へ移すと「spec に書いてないから見ない」が後段で強まる。後段に前段の前提を疑う観点を最低 1 本残す。
- 対策の置き場は**事故時に実際に走った工程**。走っていない工程(レビュー・計画 skill)へ追記しても届かない — Skill 未起動の単独 fix セッションなら実装者が読むドメイン skill の実装フロー節が置き場。

## 4. 対策ラダー(必ず最小段から)

1. **バグ修正のみ** — 単発の実装ミス。観点新設は過学習。
2. **既存観点・既存手順への数行追記(既定)** — エージェントは例示に強く引っ張られるので、常時発火系の箇条書きに 1 項目足すだけで探索対象が変わる。恒常トークン増ほぼゼロ。
3. **新観点の追加(ユーザー確認必須)** — 通過条件は 3 つ全部: (a) 欠陥が古典的な一般クラス名で言える(TOCTOU・fail-open 等。言えないなら症状の逆さ書き) (b) 既存観点に持ち場がない (c) そのリポジトリで再発確率が高い構造的理由がある。
4. **発火条件・工程の変更** — 構造的死角にのみ対応する重い手。

上の段は下の段で足りない理由を言えるときだけ。**系統再発時は既存対策の修理が第一候補**(発火条件の是正 / 出力経路の格上げ / 消えた追記の復元 / 変種を包摂する一般化)。同系統に対策を 2 本並べるのが最悪形(注意希釈)。症状特化 reviewer(`retry`/`sleep` 等の keywords ゲート)は足さない — 判定質問「この観点は今回の事故を知らない人にも独立に価値があると説明できるか」。初回提案は特化に寄る実績(「特化 3 本」→「一般化 1 本」→「既存への追記のみ」と 2 回却下されて縮んだ)。最初から段 2 を既定で出す。

## 5. 検証の細則

- **フィクスチャは導入コミット**(`git log -S`)。後続の強化・リネームコミットでは不可 — 正しいレビュアーは「この diff の導入ではない」と棄却する(棄却が出たらそれは精度の証拠として記録)。
- **context は当時の作者のゴール**を書く。後知恵(事故の存在)を混ぜない。追記文に事案の実例注記を入れたら、agent への指示に「当該コミットより後の修正・障害記録を根拠にしない」を入れ、報告にリークの疑いを明記する。
- **cwd は導入コミットに固定**。作業ブランチ HEAD を cwd にすると並走セッションの修正がリークして検証が無効になる(実測)。
- 合否は agent の返答 3 行でなくレポート全文で。「捕獲」は故障シナリオを diff と参照コードから独自に構成している場合のみ。
- 合格は「事故を防いだ出力経路への到達」。備考・低 severity での言及は、統合フローでユーザーまで届かなければ防げていない。
- **単離合格で終わらせない**。実レビューが大規模 diff を見ていたなら、実入力(logs repo の runs ディレクトリに現存)でフルスケール再実行する(実測: 単離 676 行で即 Critical の追記が、実 PR 9512 行では 2 回連続で備考へ降格)。
- フルスケールで落ちたら、降格の推論文を読んで抜け道を 1 周 1 個ずつ塞ぐ(打ち切り条件付き)。実測した抜け道: (a) 形式論降格 — 「前身も未実装」「意図不明」を根拠に帰結を見ずに ok 側へ → 故障シナリオ構成を必須化し、ユーザー可視の破綻なら格上げ。(b) 浅いシナリオ構成 — 「機構側に語彙が無いから影響しない」→ 名指ししない一括機構では語彙の不在を安全根拠にせず、出荷データの最大作用ケースで画面・状態を言う。追記文が事故の輪郭の逆さ書きに近づいたら打ち切って到達点を正直に記録する。フルスケールは実行間で指摘の顔ぶれが揺れる(n=1 は確率保証でない)ことも明記。
- 検証 agent が API 断で落ちてレポート未出力のことがある。ファイルの存在を確認してから判定する。

## 6. 記録と締め

- registry.md へ 1 事案 1 ブロック追記(形式は recurrence-registry.md)。
- issue tracker に 事故 → 裁定 → 対策 → 検証結果、検証レポートのパス、限界(リーク疑い等)、残課題、「対策 × 検証状態」を残す。
- スキル変更は GO の範囲内でコミット。PR・push はユーザーの明示指示があるときのみ(「push まで全自動」系の一般裁定をこのスキルへ延長しない)。
