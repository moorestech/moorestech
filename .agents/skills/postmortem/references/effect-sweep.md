# effect-sweep — 対策の効果を追う月次の一括調査

台帳 `registry.md` の各対策が、配備後の本番で効いたかを月に 1 回まとめて逆引きし、台帳の状態欄を更新する。個々のポストモーテムは配備確認までで閉じ、効果の判定はここが受け持つ。読み取り調査であり、スキル・コード・レビュー結果は変更しない。

## 対象

- 状態が「効いた」「未配備」以外の全事案と、前回の調査以降に配備された事案。
- 「未配備」は配備の有無だけを確かめ直す(入っていれば配備欄を埋めて対象に戻す)。
- 見る範囲は前回の調査日以降に増えた本番記録(レビュー run・セッションログ・issue・新しい事案)。初回は配備日以降の全部。

## 1 事案ごとの手順

1. **対策を確定する**: 台帳の対策・狙い・対象の見分け方と、対策コミット(`git show`)を読む。狙い欄が無い古い事案は、ここで狙いと検索語 2〜5 個を書き出す。
2. **出番を絞る**: 見る範囲の本番記録のうち、対象の見分け方に当たるものだけを残す。0 件なら「出番なし」。
3. **使われた形跡を追う**: 残った記録の生出力を検索語・元事案名で引く。指摘があれば、統合 → 指摘カード → 裁定 → 適用結果 → 実コミット差分まで辿り、修正か判断の出口に届いたかを確かめる。
4. **再発を逆引きする**: 見る範囲の issue・人のレビュー指摘・新しい事案・裁定記録を、同じ機構と狙い欄の変種で引く。
5. **状態を 1 つ決める**(複数当たるなら主状態 + 副状態):

| 状態 | 条件 |
|---|---|
| 効いた | 実在する対象欠陥を指摘し、修正か判断の出口に届いた |
| 発火したが未確定 | 指摘は出たが、欠陥が実在したか・出口に届いたかが不明 |
| 再発 | 配備後に同じ機構の事故が起きた。狙い欄で「対象外」とした変種の発生は副状態に書く |
| 発火なし | 対象欠陥が実在したのに、使われた形跡が無い |
| 出番なし | 対象になる入力が来ていない、または来たが対象欠陥が無かった |
| 未配備 | 本流・スキル正本に内容が入っていない |
| 記録不足 | 判定に要る記録が残っていない |

バグを捕まえる対策でないものは、狙い欄の振る舞いを数える(例: 該当依頼 12 件中 11 件で grill が先に起動 → 効いた・漏れ 1 件のセッションを添える)。

## 判定の規則

- 検索に当たっただけで「効いた」にしない。手順 3 の出口まで照合する。
- 同じ欠陥を他の観点も指摘していれば、その対策単独の手柄にしない(併記はする)。
- 元事故の再生で合格した記録は、本番の実績に混ぜない。
- 自動推奨で採用された裁定は、人が確認した裁定と分けて書く。
- 判定ごとに根拠のファイルパスと行番号を残す。推測は推測と書く。
- 前回の状態を覆すときは、どちらが正しいかを根拠つきで書く。

## 進め方

- 本体は取りまとめに徹し、事案を年代・工程で 3〜4 群に分けて調査役 subagent に並列で渡す。各調査役は 1 事案 1 ファイルで書く。
- 全群が終わったら別の検証役を 1 本起こし、「効いた」「再発」と、前回から状態が変わった全件を一次資料で照合し直させる。検証役は判定を覆してよく、覆したら理由を残す。
- 重い読み取りが続くので、外部実装者(codex-implement 等)へ丸ごと委託してよい。

## 出力

- logs repo の `harness/postmortem/sweeps/<YYYY-MM>/`(logs repo が無ければ `~/.agents/records/postmortem/sweeps/<YYYY-MM>/`): `report.md`(冒頭に一言結論・全事案の状態表・状態別件数・捕捉実績率と再発率)、`cases/`、`verification.md`。
- 捕捉実績率 = 「効いた」/ 配備済み事案数、再発率 = 「再発」/ 配備済み事案数。分母の定義と観測期間を必ず添える。検出率とは呼ばない(見逃しの総数が分からないため)。
- 台帳の状態欄を更新する(最終確認日と report.md のパス)。過去の検証欄・記述は書き換えない。
- 次の 3 つは issue を起票する: 「再発」「発火なし」→ 前対策の修理(不発理由の 4 分類を添える)/「未配備」→ 配備 / 指摘と裁定が済んだのに修正がコードに無い → 修正。
- 成果物は生成直後にコミット・push する(自動同期任せにしない)。
