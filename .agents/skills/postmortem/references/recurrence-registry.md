# recurrence-registry — 再発照合の累積台帳

Step 1.5(再発照合)と Step 6(台帳追記)の詳細規約。正本の台帳はコード repo に置かず、レビュー実行記録と同じく logs repo に置く: `../moorestech_logs/harness/postmortem/registry.md`。

## 台帳の形式(1 事案 = 1 ブロック・新しい事案ほど上)

```markdown
## YYYY-MM-DD <事案slug>
- 系統タグ: <カンマ区切り。例: 転写忠実性, プレビュー不完全, 発火条件の代理指標>
- 症状: <一行>
- 裁定類型: <軸違い/枠内最適化/構造的死角/免罪。件別なら列挙。遡及分は「(簡易・遡及)」>
- 対策: <commit sha> <追記先観点・手順名> <一行要約>
- 検証: <合格(単離/フルスケール) / 未検証(理由) / (遡及・不明)>
- 記録: <bd id・記録ファイルパス・PR 番号など一次資料への参照>
```

## 系統タグの運用(照合の要)

- **機構ベースで付ける** — 「なぜ体制がそれを見なかったか」の機構の名前。症状の逆さ書きタグ(「研究UI取り違え」等)は照合に使えないので禁止。症状は事案 slug と症状欄に書く。
- **固定分類にしない**。既存タグで足りなければ新タグを作ってよいが、同じ機構には必ず同じタグを使い回す(照合はタグ grep なので表記ゆれが盲点を作る)。台帳を読んで近いタグがあればそちらへ寄せる。
- 種タグ(SKILL 本文「横断で必ず確認する癖」由来): 転写忠実性 / 発火条件の代理指標 / 自己参照QA。

## Step 1.5 の照合手順

1. まず台帳を grep(系統タグ・機構語)。ヒット無しでも今回の機構を 2〜3 通りに言い換えて引き直す(タグの言い換え漏れ対策)。
2. ヒット時の深掘りは**必ず read-only サブエージェントへ委譲する**(本体で一次資料を読み進めない)。入力は今回事案の一行記述＋該当ブロックの「記録」欄の一次資料と「対策」欄のコミット。サブエージェントに**前対策の不発理由を 4 分類で確定**させる:
   - (a) **発火せず** — 発火条件・モード・閾値が今回の入力を系統的に外した
   - (b) **発火したが届かず** — 指摘は出たが降格・注意希釈で防止経路(Critical/設計判断)に到達しなかった
   - (c) **消失・風化** — 後の skill 編集で対策追記が消えた・薄まった(追記行の git blame で確認)
   - (d) **変種枠外** — 対策は兄弟変種のみカバーし今回の変種を包摂していなかった
3. 判定は推測でなく一次資料で取る(SKILL 5 原則 1 と同じ重み)。「前対策があったのに効かなかった」は裁定の帰責を変えるため、Step 2.5 のゲート提示に「再発判定」行として必ず載せる。
4. 完全な初発でも「初発(照合済み・近縁なし)」と明記する — 照合を省いたのか初発なのかを後から区別できるようにする。

## Step 6 の追記規約

- 1 事案 1 ブロックを台帳の先頭側へ追記する。裁定が件別に割れた場合も事案としては 1 ブロック(裁定類型欄に列挙)。
- 対策が複数あれば対策欄を複数行にしてよい。検証欄は Step 5-9 の「対策×検証状態」表と整合させる(未検証を合格に見せない)。
- 追記は postmortem の締めの一部であり省略不可。台帳が育たないと Step 1.5 が盲目になる。

## ブートストラップ(2026-08-20 実施)

初期台帳は次の 2 層で構成した(ユーザー裁定): ①正式な postmortem スキル実行分は全記録から完全ブロック化、②スキル導入以前の散在「再発防止」コミット(webui-design 較正・playtest 再発防止・e2e mock host 規約等)は一行要約の遡及簡易ブロック(裁定類型 = 簡易・遡及)。遡及分は当時の裁定が無いため類型・検証欄が粗いが、系統タグは照合可能な精度で付与済み。純粋なバグ修正(体制への手当てが無いもの)は対象外。
