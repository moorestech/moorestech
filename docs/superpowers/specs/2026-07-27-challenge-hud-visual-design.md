# チャレンジHUD表示改善 設計

## 目的

常駐チャレンジHUDを、moorestech Web UIの「世界の上に浮く、面を持たないHUD」へ揃える。現状露出している内部i18nキー `challenge.current`、Mantine既定の灰色カード、合成boldを除去し、進行中の目標をゲーム画面上で自然に読める表示へ置き換える。

## 非目標

- チャレンジの進捗値・報酬・アイコンを新たに通信しない
- チャレンジ一覧画面の再設計は行わない
- 完了アニメーションや新しい装飾モチーフを追加しない
- Unity側の旧uGUIチャレンジHUDを変更しない

## 調査結果

- `CurrentChallengeHud.tsx` は Mantine `Paper` と `Text fw={700}` を直接使い、`.hud` には位置と余白しか定義していない。そのためMantine既定の灰色カードと角丸がそのまま表示されている。
- `t("challenge.current")` は日本語・英語のどちらの辞書にも存在せず、内部キー自体が画面へフォールバック表示される。
- `webui-design` は常時表示HUDに面を持たせず、既存色トークンのみで「浮いている」表現にすることを要求している。
- 現行topicは `guid`、`title`、`categoryGuid` のみを持つ。進捗ゲージやアイコンを表示する根拠データはない。
- blockingスキット中の非表示と、チャレンジ0件時の非表示は既に正しいため維持する。

## 比較した方式

### A. 面なしの見出し・罫線・目標一覧（採用）

左上に小さな従属見出し「現在のチャレンジ」、既存 `FadeRule`、目標名を縦に配置する。背景、枠、角丸、光彩、アニメーションは持たない。

- 長所: 常時表示HUDの原則と一致し、目標の意味も失わない
- 長所: 既存の文字色と装飾語彙だけで構成できる
- 短所: 世界背景によってはカード面よりコントラストが弱い
- 対応: 既存HUDと同族の最小限の文字影で可読性を補う

### B. 目標名だけを表示

- 長所: 最も軽量
- 短所: 複数の一時表示が重なる場面で、何の文章か判別しにくい

### C. `GamePanel` に収める

- 長所: パネル画面との外観統一は容易
- 短所: 常時表示HUDに面を持たせるため、デザイン哲学の役割分担に反する

## 表示設計

`CurrentChallengeHud` はMantine表示部品を使わず、意味を持つHTML要素と `FadeRule` で構成する。

1. ルートは画面左上の固定位置に置き、`pointer-events: none` でゲーム入力を透過する。
2. 見出しは `t("現在のチャレンジ")` を通し、`--text-muted`、小さめの文字、字間で従属情報として示す。内部実装キーは表示しない。
3. 見出し直下に共有 `FadeRule` を1本だけ置く。
4. 目標名はtopicの `title` をそのまま使い、`--text-high-contrast` で表示する。合成boldは使わず、見出しとのサイズ差で階層を作る。
5. 複数の進行中チャレンジは順序を保って縦積みする。箇条書き記号や新しい装飾は足さない。
6. 幅、位置、間隔、文字サイズは `tokens.css` の `--challenge-hud-*` 固定長トークンで管理する。画面割合の指定は使わない。
7. 長文は固定最大幅の中で自然に折り返す。単語単位で折り返せない長い文字列も領域外へ溢れさせない。
8. 既存どおり、topic未受信・0件・blockingスキット中はルートごと描画しない。
9. 全画面modalとPlaceBlock/DeleteBarでは画面固有UIへ情報を集約してHUDを描画しない。GameScreen、未知・Debug、通常TrainHUD、backgroundスキットでは描画を維持する。

HUD固有CSSはチャレンジ一覧画面のCSSから `CurrentChallengeHud.module.css` へ分離し、一覧画面のデザイン負債を今回の変更へ混ぜない。

## デザイン哲学への追記

`webui-design` にチャレンジHUDのホワイトリストを追加する。

- 常時表示HUD族であり、パネル面・枠・角丸を持たない
- 「従属見出し → FadeRule → 高コントラストの目標一覧」の構成
- 新しい色相、アイコン、ゲージ、箇条書き装飾、アニメーションを追加しない
- 固定長トークン、入力透過、blockingスキット中非表示
- `FadeRule` をパネル内だけでなく、面なしHUDの見出し区切りにも利用可能とする

## データフロー

```text
challenge.current topic
  → Appの画面所有判定
  → modal・PlaceBlock・DeleteBarを除外
  → CurrentChallengeHudで未受信・空・blockingを除外
  → 受信順の目標タイトル一覧を描画
```

topic契約、Unity publisher、状態所有、通信経路は変更しない。

## 反例と対処

最も強い反例は「複数の長いチャレンジが同時にcurrentになり、左上から画面中央へ横溢れする」状態である。固定最大幅、通常折返し、長語の強制折返し、縦方向の固定間隔によって横溢れを防ぐ。描画件数をUI側で切り捨てるとサーバー状態を隠すため、件数制限は設けない。

## 検証

- コンポーネント検査: Mantine `Paper`、`Text`、`fw`、`challenge.current` をHUDから除去したこと
- E2E: 1件表示、完了後0件非表示、blockingスキット中非表示
- E2E: 複数件を受信順で表示
- Playwright目視QA: 日本語の単一目標、複数目標、長文目標を1280×720 mock-hostの明暗を含む世界背景上で撮影し、問題がなくなるまで修正と再撮影を反復
- 目視QA: 背景・枠・角丸がなく、罫線と文字だけが浮いていること
- 目視QA: 14状態のmanifestと計測値を生成し、GameScreen、明暗背景、長文、modal、操作モード、スキットで重なり・折返し・入力透過を確認
- Web UI: `pnpm lint`、`pnpm test`、対象Playwright E2E、`pnpm build`
- `.cs` は変更しないためUnityコンパイルは不要
