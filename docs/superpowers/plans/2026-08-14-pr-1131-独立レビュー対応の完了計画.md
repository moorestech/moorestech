## Phase 1: コンパイルとテストの検証（完了）

### ブロッカーの真因

`uloop compile` が繋がらなかった原因は Unity 側ではなく **本ブランチのコンパイルエラー**だった。

Unity はスクリプトのコンパイルエラーがあると `[InitializeOnLoad]` を実行しない。
uLoopMCP のサーバ起動は `McpServerController` の静的コンストラクタ（`[InitializeOnLoad]`）から
`RestoreServerStateIfNeeded()` で行われるため、**コンパイルエラー → サーバ起動せず → `uloop` が繋がらない**。
そして `uloop compile` はそのサーバを必要とするので、自力では抜け出せないデッドロックになる。

前セッションで疑った経路（モーダル固着・ロックファイル・`isServerRunning` の永続値・ポート競合）は
いずれも無関係で、`Window > Unity CLI Loop > Server` の手動クリックも不要だった。

### 実際の解除手順

1. `uloop launch ./moorestech_client` で Unity を起動（クラッシュ由来の `Temp`/`UnityLockfile` は自動清掃される）
2. `Library/../Editor.log` を `error CS` で見てコンパイルエラーを特定する（**サーバ不要の唯一の観測点**）
3. エラーを直し、Unity を一度バックグラウンドへ回してから前面化して Asset Refresh を発火させる
4. 再コンパイルが通ると `[InitializeOnLoad]` が走り、8702 が listen 状態になる

実際に見つかったエラーは2件、どちらも本ブランチの新規コード:

- `ScrollStepAccumulatorTest.cs` のメソッド名が数字始まり（C#識別子として不正・CS1519）
- `wheelOwnedByTool` 追加時に取り残した `PlacementModeDtoFactory.Create` の呼び出し6箇所（CS7036）

> **注意**: Asset Refresh のために Unity を前面化すると、実OS入力が注入入力を毎フレーム上書きし、
> PlayMode の入力注入が効かなくなる（スキルの絶対規則2）。実際1本目のシナリオがこれで失敗した。
> **コンパイルを回した後は必ず Unity をバックグラウンドへ戻してから PlayMode を回すこと。**
