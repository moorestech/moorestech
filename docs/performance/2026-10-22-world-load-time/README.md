# ワールド読み込みに約2分かかる件の調査ログ（2026-10-22）

## 結論
- ベースラインワールド（`2026-10-22-world_1`）を「ローカルでプレイ」で開くと、定常状態になるまで**約110秒**かかる。
- **うち約44秒（約4割）は、読み込み中に溜まった受信イベントの後処理。** 重い処理でフレームが止まっている間にも、サーバーはブロック状態イベントを毎秒約1.7万件送り続けている。止まりが明けると、溜まった数十万件をメインスレッドで1件ずつ全部処理する。その処理がまた次のフレームを止めるので、悪循環になる。
- 残りの大きな塊は、サーバー起動（セーブ読み込み）約12.6秒、MainGame シーン読み込み約12秒、ブロック15,082個の生成約12秒。
- 計測は Editor（Debug 最適化）なので、絶対値はビルド版より大きい可能性がある（推測）。

## 計測方法
- **タイムライン**（`tl-start.cs` → `tl-collect.cs`）：開始ボタンを押す直前から、全ログの時刻と、2秒ごとの fps・Renderer 数・シーン名を記録した。生データは [timeline-raw.txt](timeline-raw.txt)。
- **重いフレームの内訳**（`../benchmark/snippets/profiler-start.cs` → `heavy-collect.cs`）：開始から120秒間 Profiler を記録し、1秒以上かかったフレームのメインスレッドを上位7階層まで書き出した。ProfilerMarker 入りのコミット（09b546dc98 相当）で計測。生データは [heavy-frames-raw.txt](heavy-frames-raw.txt)。
- 2つは別々の読み込み回の計測なので、秒数は数秒ずれる。

## 改善の候補（未着手）
1. **溜まったブロック状態イベントは、ブロックごとに最新の1件だけ処理する**（同じブロックの古い状態は捨てる）。ブロック状態は「最新値で上書き」する性質なので、途中の値を全部適用する必要はない。読み込み中に溜まった数十万件が、ブロック数（約1,750件）まで減る見込み（推測）。定常時の改善候補「tick 単位でまとめて送る」（[低fps調査ログ](../2026-10-22-windows-desktop-low-fps/README.md#改善の候補未着手要-grill)）と同じ基盤の話になる。
2. **読み込みが終わるまでは、サーバーからブロック状態イベントを送らない。** 各ブロックは購読時に `RequestBlockState` で初期状態を取り直しているので、それ以前のイベントは不要な可能性がある（要確認）。
3. サーバー起動・シーン読み込み・ブロック生成（各約12秒）を、メインスレッドの1フレームに詰め込まず分割する。ただし合計時間はあまり減らない。体感（固まって見える）の改善が主になる。
