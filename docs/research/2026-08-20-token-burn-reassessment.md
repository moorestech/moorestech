### オーケストレータが空転した仕組み（transcriptから）

- 派遣プロンプト（orchestrator-steps.md）は「回収はファイルハンドオフで行いオーケストレータのコンテキストを空ける。**この方式で消費はほぼゼロになる**」としているが、**読まなくても待つだけでターンが回る**。各サブエージェント完了の通知、`Monitor` のイベント、自分で打った `echo` の結果、そのすべてが1ターン（=全コンテキスト再送）を発生させる。
- `Monitor` を11回使っているが、渡したコマンドが `while …; do sleep 5; echo "waited"; done` — **5秒ごとに1行出すループを監視させた**ため、Monitorが「イベントごとに通知」仕様どおり5秒おきに起こしてくる。Monitorを使った区間がむしろ高頻度になっている。
- その合間に `echo i9` `echo i10` … `echo m22` と**連番の no-op Bash** を打ち続けた。poll-guard（`.dev-hooks/poll-guard.mjs`）は「直前と完全一致するコマンドが3回連続」で拒否する設計なので、連番化で毎回すり抜けた（bd `moorestech-2xm` が指摘した穴の実例）。
- モデルの自己申告も「I'll use a single bounded Monitor loop instead of repeated polling」「I'll set up a monitor loop … rather than manual filler calls」と**2回も自覚して宣言した直後に再発**している。指示文言では止まらない。

同じ構造は PR1175 run（オーケストレータ $234 / 全体 $483）、PR1189 8/19 19:51 run（$82 / $191）でも再現。**オーケストレータ待機だけでレビュー1本の30〜48%**。

## 5. 対策（効果順）

1. **pollerのレビュー同時起動を1本に制限する**（`poller.py` `launch_review` 前段に「実行中レビューがあれば見送り」を入れる。applyのスロット方式と同じ）。1本ずつなら5時間枠内で完走できる公算が高く、上限死→全損→やり直しの連鎖が止まる。最も簡単で最も効く。
2. **オーケストレータの待機を「イベント駆動1回」にする。** `Monitor` には「完了条件を満たすまで何も出力せず、満たした瞬間に1行だけ出す」コマンドを渡す（`until [ $(ls agents | wc -l) -ge 38 ]; do sleep 15; done; echo done`）。5秒ごとに echo するループは禁止と orchestrator-steps.md に明記。これで$160〜230/run（30〜48%）がほぼ消える。
3. **poll-guard を「no-op Bash（echo/sleep/true/ls 単独）の連続」「ListAgents/Monitor の連続」にも拡張**し、連番echoで逃げられないようにする（bd `moorestech-2xm` の完遂）。2を指示しても再発する証拠が上記のとおりあるので、機械的遮断が要る。
4. **レビューの途中成果を再利用する**（前レポート対策5）。`agents/*.md` は既にファイルに落ちているので、再起動時に既存の報告があるエージェントは再派遣しない、だけでも2回目以降の全損を防げる。
5. p99h（死因判定・空起動通知）は引き続き直す。ただし$への効果は小さい。
6. SKILL.md（moores-code-review）の「sonnet委譲の監督$7.1」を実測値で訂正する。誤った前提がレビュー設計の判断材料になっている。
