## 得られたことと得られなかったこと

| 項目 | 得られた知見 | 残る欠落 |
|---|---|---|
| クラッシュ地点 | Unity通常描画のcommand-list `Close` 相当が `E_FAIL (0x80004005)` を返す経路 | 最初の不正操作と対象list/resource |
| GPU同期 | 元ログに3件のFence目標未達。未達をログ後に復帰する実装を確認 | 原Fence/eventの同一性、未完了の資源を実際に再利用したか |
| 録画 | 元ログにENOMEM/BrokenPipe/録画Unavailable。別CPU試験でバッファ返却漏れ | 元writerの例外位置、pool/queue状態とGPU失敗へのつながり |
| 最終操作 | 最後のPauseとserver capture要求・snapshotを確認 | 撮影命令と失敗したD3D12 listの対応 |
| CEF | 共有資源、allocator再利用、呼出しスレッドに調査すべき箇所 | 原実行での契約違反・使用中再利用とfatalへの接続 |
| 再現試験 | 通常操作・録画子終了・resize・診断付き撮影の結果を保存 | 元と同じfatalの陽性試行 |
| ビルド | 主要対象ソースやバイナリの部分一致、ESC移動ロック差 | dirty差分を含む元配布全ビルドの一致 |

## この調査で使う「再現」の意味

1. 録画ENOMEMや黒画面だけが起きた場合は、その症状の再現である。
2. 元と同じ `Close → E_FAIL → fatal stack` が取れれば、同署名クラッシュの再現である。
3. 最初の不正操作、対象オブジェクト、失敗命令を結び、対照試験でも説明できて初めて原因同定へ進める。

本調査は2と3に到達していない。コード上の問題や独立した小試験の陽性を、元クラッシュ再現の代わりに数えない。

## 特に撤回・限定した初期推論

- 「Device failedなのでTDR／デバイス除去」：確定していない。
- 「ffmpegが約6GBを消費し、枯渇の約3分後にESC」：所有者も時間差も確定できない。
- 「クラッシュ時の空きcommitがあるので先行OOMは無関係」：間接的影響は除外できない。
- 「GPUメモリ約3GBは通常より減ったのでeviction」：同じ機器・条件のベースラインがない。
- 「Fence未達なので使用中allocatorのResetが確定」：対象と完了の対応が欠ける。
- 「正常試験で落ちなかったのでCEF／撮影／録画を除外」：成立条件が揃っていない。
- 「Monoが成功時に古いBrokenPipeを返した」：照合済み実装から当該候補を除外した。
- 「新Unityに関連修正があるので更新で直る」：静的版差は原実行での発生を証明しない。
