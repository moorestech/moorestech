# 全数レビューをやめた後、何を見れば品質が分かるか

2026-09-23〜24 のユーザーと Claude Code の壁打ちの振り返り。出発点は「コードレビューは、無作為抽出検査のように危なそうなものだけたまに読めばよいのでは」という問い。ソフトウェア工学が生産工学に寄っていく感覚を、このPJTの AI コーディングの変遷に当てはめて整理した。

## 結論：低頻度で回す運用

| 頻度 | やること |
| --- | --- |
| 月数本 | **保守性の観点で「変なことが起きていそうな」PRを精読する。** 狙いはバグではなく定性的な設計不良。エージェントが自分で判断した箇所（前例なし・新しい抽象・複数システムにまたがる変更・規約衝突）を狙い撃ちする |
| 定期 | **過去のエージェントの成果物を、新しいモデル・新しい基準でサブシステム単位に再点検させる。** 人とAIのどちらが書いたかが混ざっていても、エージェントが読むなら問題にならない |
| 随時 | **規約を棚卸しする。** 古いモデルの失敗の仕方に合わせた観点は、外して数本作らせ、差が出なければ廃止する（除去実験） |
| 毎回 | **結果を一行でも残す。** 何を読み、何が見つかり、観点を足したか削ったか。これがないと、半年後にまた「良くなっているのか分からない」に戻る |

## 議論の流れ

1. **問い：** レビューは抜き取り検査でよいのでは。ソフトウェア工学が生産工学に寄っている気がする。
   → 方向には同意。ただし行き着く先は、抜き取り検査より「工程管理」の方。このPJTはすでにその移行をかなり進めている。
2. **現状認識：** 不具合が多いとは感じないが、レビュー観点の追加・修正をほとんどしなくなった。不良が減ったのか、見ていないだけなのか判別できない。
   → 全数レビューをやめたことで、観点を追加する材料になっていた情報も止まっている。観点の追加がないことは、良い兆候とも悪い兆候とも言えない。少量でも測れば判別できる。
3. **選び方①：** 不良の出そうなPRを作為的に選ぶ方が判別できるのでは。
   → 発見の効率は上。ただし勘で選ぶと死角が残り、時期によって基準が揺れる。層別抽出（層の基準は機械的に固定し、層の中は無作為に選ぶ）を提案した。
4. **選び方②：** 高リスクに問題がなければ低リスクも大丈夫なのだから、高リスクだけでよいのでは。
   → バグが目的なら概ね同意。ただ保守性の劣化は、むしろ小さく「安全そう」なPRに積もる。
5. **目的の再定義：** バグは注視しない。今のエージェントは、人間が静的チェックで分かるバグをもう埋め込まない。定性的な設計不具合の方を見たい。
   → 同意。選び方の軸が「壊れると痛い領域」から「エージェントが判断した箇所」に変わる。
6. **単位と時間軸：** どこがAIでどこが人間の名残か分からないので、PR単位でもよいのでは。モデルもハーネスも変わるので、旧基準でダメだったものが今はよいこともある。
   → 人が「工程」を評価するならPR単位が素直。規約にも賞味期限があるので、監査は「観点を足す」と「観点を削る」の両輪にする。
7. **機構化：** 過去のエージェントが作ったシステムを、今のエージェントがチェックする機構が要るかもしれない。
   → 有望。ただし「今の規約で採点させない」「好みの違いを除外する」「結論は人が裁定する」の3点を守る。

## このPJTの変遷と生産工学

成果物を検査する段階から、工程を直す段階へすでに移っている。デミングの「検査への依存をやめよ」とほぼ同じ流れ。

| このPJTで起きたこと | 生産工学の言葉 | 実体 |
| --- | --- | --- |
| 初期は人が全PRをレビュー | 全数検査 | — |
| レビューの指摘を規約とチェックリストにまとめる | 作業標準書 | `AGENTS.md` の設計原則・`lens-digest.md` |
| 規約だけでは守られず、機械的に拒否する | ポカヨケ | `main-worktree-guard.mjs`・コンパイル必須ゲート・200行規約 |
| 事故のたびに工程を直す | なぜなぜ分析 | `postmortem` スキル・`.decisions/` |
| レビューそのものを採点する | 検査員の精度管理 | pr-independent-review の shadow 台帳 |
| 複数のレビュー観点で並列に見る | 多段検査 | `moores-code-review` の観点群 |

> **製造と違う点：** 製造は仕様が決まっている前提だが、ソフトウェアは仕様そのものが揺れる。人が見るべき場所は「コード」から「何を作るか」（grill・裁定）へ移っており、そこは抜き取りにできない全数工程として残る。

## 判別できない問題

全数レビューしていた頃は観点の追加・修正が頻繁だったが、今はほとんどない。考えられる説明は2つあり、今の情報では区別できない。

- **仮説A：本当に減った。** モデルとハーネスの進化、規約とポカヨケの蓄積で、設計不良そのものが出なくなった。
- **仮説B：見ていないだけ。** 不良は出ているが、読んでいないので観点追加の材料が上がってこない。

区別するには、少量でも実際に読み、見つかったものを分類して記録するしかない。

| 監査の結果 | 読み取れること | 打ち手 |
| --- | --- | --- |
| ほとんど見つからない | 仮説A | 頻度を下げてよい |
| 見つかり、既存の観点で拾えたはずのもの | 観点はあるが、レビューの実行側に穴がある | レビューの実行やハーネスを直す |
| 見つかり、どの観点にも当てはまらないもの | 仮説B、かつ観点が足りない | 観点を足す（以前の頻繁な観点追加の代わり） |

読む以外の補助として、**変更のしにくさの記録**が効く。保守性は読むより触ったときに分かるので、新機能で「想定外の箇所まで波及した」と感じたら一行メモを残す。

## 何を読むか

### 設計不良を狙うときの目印

設計不良は「壊れると痛い領域」（セーブ形式・同期）とはあまり関係がない。出やすいのは**エージェントが自分で判断した箇所**。

- 前例がない、初めての種類の実装（新しいクラス構造・新しい同期の形）
- 新しい抽象・interface・モジュールを足したPR
- 複数のシステムにまたがる変更
- 規約同士がぶつかり、エージェントがどちらかを選んだPR
- 逆に、前例をなぞっただけのPRは、大きくても読む価値が低い

勘だけで選ぶと、自分の見立ての外にある新種の不良は選ばれない。観点の追加が止まっている今は、この死角が一番怪しい。狙い撃ちを基本にしつつ、目印の基準は言葉にして固定しておく。

### PR単位かサブシステム単位か

読む人と目的で使い分ける。

| | PR単位 | サブシステム単位 |
| --- | --- | --- |
| 誰が読む | 人 | エージェント |
| 何を評価する | 今のモデル＋ハーネスという「工程」 | 積み重なった結果としての「全体の形」 |
| 利点 | 特定の時点の工程に対応する。モデルとハーネスの時期を添えて記録すれば、どの変化で良くなったか辿れる | 1本ずつは正しいPRが10本積み重なって責務がぼやける、という差分に出ないずれが見える |
| 弱点 | 全体のずれは見えない | 人とAIの時代が混ざる（エージェントが読むなら問題にならない） |

## 規約の賞味期限

`AGENTS.md` の設計原則や `lens-digest.md` は、当時のモデルの失敗の仕方に合わせて作ったもの。モデルとハーネスは日々変わるので、今は不要な縛りになっていたり、むしろ良い設計を妨げている観点があり得る。

- **足す：** 監査で新しい種類の不良を見つけたら、観点を追加する。
- **削る：** 発火しない観点は、「不要だから」なのか「効いているから」なのかがまた判別できない。確実なのは、**規約を1つ外して数本作らせ、差が出るかを見る**こと（除去実験）。差が出なければ廃止できる。

## 過去の成果物を今のエージェントが再点検する機構

人手の監査を補うものとして有望。設計時に守りたい3点：

- **今の規約で採点させない。** `AGENTS.md` を物差しにすると、規約に沿っているかの確認で終わる。聞くのは「今の自分ならこう作るか、それはなぜか」。規約そのものへの異議も出してよいことにする（規約の棚卸しと兼ねられる）。
- **作り直し地獄を防ぐ。** モデルが変わるたびに「自分ならこう書く」は必ず出る。好みの違いは除外し、実際のコストの根拠（変更時の波及・バグの発生・理解のしにくさ）があるものだけを指摘させる。
- **結論は人が裁定する。** 自動では適用せず、提案として扱う。裁定を `.decisions/` に残せば、それが規約更新の材料になる。

対象の選定は、コミットの `Co-Authored-By` にモデル名が残っているので、**古いモデル世代が作ったものから優先する**ことが機械的にできる。ハーネスの時期は記録がないので、コミット日付で近似する。まず手動で数本試して指摘の質を見てから、定期実行に載せる。
