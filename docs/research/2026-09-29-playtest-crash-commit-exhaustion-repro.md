# プレイテストのクラッシュ報告: コミット枯渇による再現（2026-09-29）

[2026-09-27 の原因分析](2026-09-27-playtest-crash-d3d12-device-lost.md) の続き。遠隔実行（ADR 0072）入りの配布ビルドを使い、「待って再現する」のではなく「きっかけを特定して意図的に起こす」方針で調べた。

## 要約

- **報告者の PC は、クラッシュ前に Windows のコミット上限（全プロセスが確保できるメモリの総量）に達していた。** 報告同梱の `crash.dmp` にピーク＝上限の記録が残っていた。物理メモリは 15.7GB 空いており、RAM が満杯だったわけではない。
- **ゲーム単体で約 13GB のコミットを起動直後から持っている。** 大半はテクスチャ（推定 8GB）の GPU メモリで、Windows はこれをグラフィックボードの VRAM 量に関係なくコミットとして数える。
- 検証機を報告者と同じ条件（コミット上限 約39GB）にし、コミットだけを使い切ると、**クラッシュ直前の録画停止（ffmpeg の `Cannot allocate memory`）が毎回ログの文面まで同じ形で再現した（2/2）。**
- 1 回は Windows の画面合成（DWM）もメモリ枯渇で落ち、ゲームの描画が止まった。報告者ログの `GetFrameStatistics is broken` の再出現と辻褄が合う。
- **最後の `d3d12: Device failed error (80004005)` によるクラッシュそのものは、まだ再現していない。** 上限到達の瞬間にどのプロセスがメモリを要求するかで、壊れるもの（ffmpeg / DWM / CEF / GPU ドライバ）が変わる。

## 報告者の crash.dmp が示すこと

`crashDumps/crash.dmp` の SystemMemoryInfo と ProcessVmCounters を読んだ（WinDbg 不要。ストリームを直接読める）。

| 項目 | 値 | 意味 |
|---|---|---|
| システムのコミット | 33.03GB / 上限 38.97GB | |
| **コミットのピーク** | **38.97GB（＝上限）** | 起動以来、一度は上限に達した |
| 物理メモリの空き | 15.7GB | RAM 自体は満杯ではない（外部表示の 21.7/32GB と一致） |
| ページファイル | 約 7.3GB | 上限 = 物理 31.7GB + 7.3GB。小さい |
| ゲームの PrivateUsage | 13.63GB（ピーク 13.67GB） | ゲーム自身は直前に跳ねていない |
| ゲームが属するジョブの PrivateCommit | 24.3GB（ピーク 30.3GB） | Steam 系も含むため、誰が跳ねたかは特定できない |

ピークは PC 起動以来の最大値なので、上限到達がクラッシュ直前だったとは断定できない。ただし直前の ffmpeg の確保失敗とは整合する。

## ゲームのメモリの内訳（検証機 RTX 2060 6GB）

- プロセスの PrivateBytes は約 12.9GB。ロード中の 1 分で 6.4GB → 13GB に増え、以後は横ばい。
- Unity が把握している分は reserved 2.2GB、Mono ヒープ 0.6GB のみ。
- GPU Process Memory は dedicated 5.0GB / total committed 8.3GB。VRAM 6GB を超えた分もコミットに乗る。
- テクスチャ推定合計 8GB。起動時に全部ロードされ、マップ移動では増えない。大きいもの:

| テクスチャ | 推定 |
|---|---|
| `SplatAlpha` 2048² RGBA32（無圧縮）× 45 | 960MB |
| 空の Cubemap 4096 RGBA | 511MB |
| 4096² DXT5 の岩（ThinMesa / Boulders / BigMesa / StratMesaSharp 等）× 多数 | 各 100〜255MB |

## きっかけ探し（陰性だったもの）

すべて検証機・報告者セーブ・FPS 上限なし（約 90〜140fps）で、遠隔実行から操作した。

| 試したこと | 結果 |
|---|---|
| マップ全域 36 地点へテレポート（各 4 秒） | テクスチャ量・個数とも不変 |
| 録画の ffmpeg だけを強制終了 | GPU の異常なし |
| 解像度・全画面モードの切り替え 20 回 | 異常なし |
| ポーズメニューを 15 回開く（開くたびにバグ報告の記録確保が走る） | +130MB（約 8.5MB/回）、異常なし |
| Job Object でゲーム単体のコミットに上限をかけ、ゲーム内で RT を積む | `D3D12Fence::Wait` の警告は出たが、Unity の eviction ダンプ → Mono の OutOfMemory で落ち、報告者と終わり方が違う |

最後の試験で、Fence 警告は原因を特定する材料にならないことが分かった。ゲーム単体への上限では GPU ドライバや他プロセスは失敗しないため、PC 全体の枯渇とは別物になる。

## 再現（PC 全体のコミット枯渇）

### 条件

- 検証機のページファイルを自動管理から固定 7GB に変えて再起動した。コミット上限は 39.8GB（報告者は 38.97GB）。
- 配布ビルド `playtest-20260929-1441` を Steam から `--remoteExec` 付きで起動した。報告者セーブ（`tick_43786.json`）を使い、遠隔実行で `vSyncCount=0` / `targetFrameRate=-1` にした。
- 別プロセスで `VirtualAlloc(MEM_COMMIT)` だけを行い、物理ページには触れずにコミットの空きを 0 付近まで下げて保持した（一定時間で自動解放）。9/27 に OS ごと固まったのは物理ページまで触っていたためで、今回は物理メモリが十数 GB 空いたままになる。報告者の状態に近い。

### 結果

| 起きたこと | 報告者 | 試行 1 | 試行 2 |
|---|---|---|---|
| `[ffmpeg] ... Error during demuxing: Cannot allocate memory` → `ERROR_BROKEN_PIPE` → 録画停止 | あり | あり | あり |
| DWM が `0xc00001ad`（fatal memory exhaustion）で落ちて再起動 | ログから推測 | あり | なし |
| CEF（`cef-unity-rust-helper.exe`）が `0xe0000008`（Chromium の OOM）で落ちる | 不明 | あり | なし |
| その後のゲーム | 数分後に `Device failed` でクラッシュ | 描画が止まってフリーズ | 生存 |

- 試行 1 では、コミットを埋めてから 8 秒後に DWM が落ち、以後ゲームは 1 フレームも描かなかった。同時刻に常駐の音量ミキサー（EarTrumpet）も OOM で落ちている。GPU ドライバのリセット（TDR）はイベントログに無い。
- 試行 1 では、私が同時にゲーム内で RT 確保とポーズ確保も回していた。試行 2 は通常操作だけにした。
- 空き 2GB・500MB での保持では何も起きなかった。落ちるのは空きが 0 付近になり、誰かが新しく確保しようとした瞬間。

## 見立て

報告者の PC では、ゲームの約 13GB と他のアプリで、小さいページファイルのコミット上限に達した。その瞬間に確保しようとした ffmpeg が止まり、DWM の再起動などで画面出力が乱れ、最終的に D3D12 デバイスが失われた。最後の段（デバイスロスト）はまだ直接確認できていない。

FPS 上限なし・ノート PC の画面出力経路（Optimus）は、増幅要因または別経路の候補として残る。検証機（デスクトップ）では Optimus の経路は試せない。

## 次の手

1. 同じ条件で 5〜10 回くり返し、再現率を出す。DWM はウィンドウ操作で確保するので、枯渇中にウィンドウ切り替えを混ぜる。
2. 安定して再現できたら、FPS 上限あり・テクスチャ削減（`QualitySettings.globalTextureMipmapLimit` 等）で防げるかを実測してから、対策を決める。
3. 次のクラッシュ報告で原因を確定できるよう、PC 全体のコミット使用量と上限・ゲームと子プロセスのメモリ・GPU メモリ・FPS の時系列を報告に同梱する案がある（機能追加なので grill を通す）。

## 検証機の状態と再現手順のメモ

- **ページファイルは固定 7GB のまま。** 検証が終わったら `AutomaticManagedPagefile=True` に戻して再起動する。
- `world_1` は報告者セーブのまま。元のワールドは `world_1.pre-repro`、9/29 の smoke 分は `world_1.smoke-20260929-1441` に退避してある。
- ComfyUI（tara-tari-studio の画像生成バックエンド）が同居している。メモリを空けたいときは停止せず `POST /free {"unload_models":true,"free_memory":true}` でモデルだけを外す。ログオン時タスク `\ComfyUI-Krea2` で自動起動する。
- 再起動後はロック画面になるが、対話セッションからキー入力を送れば解除される（自動ログオンなのでパスワード不要）。
- 検証用のスクリプトは検証機の `C:\moorestech-repro\r2\` にある:
  - `watch.ps1`: 5 秒ごとに温度・電力・コミット・メモリを記録し、閾値で停止する
  - `commithog.ps1`: 物理ページに触れずにコミットを埋める
  - `joblimit.ps1`: Job Object でプロセス単位のコミット上限をかける。一度かけた上限は緩められない（新しくかけると入れ子になり、厳しい方が効く）
- ログは同じ場所に `player-commitcap-crash.log` / `player-trial1-hang.log` / `player-trial2.log` として残してある。
- ゲーム内の `System.Diagnostics.Process` の値は Mono では 0 になる。プロセスのメモリは PowerShell 側で測る。
