判定: どちらも UITK で作れた。
  • ノード編集: React Flow の基本操作（ポート接続・付け替え・範囲選択・方眼吸着・大きさ変更・ミニマップ・元に戻す）が、C# 約1,200行ですべて動いた。
  • ベクター編集: 矩形・楕円・ペン（ベジェ曲線）・回転込みの取っ手・スマートガイドが、約1,500行で動いた。
  • Web と違って自前で持つもの:
    • 線や図形の当たり判定（Painter2D に無い）
    • 描き直しを小さく保つ層の分け方
    • 重さの勘所（usageHints と translate）
  • 数の上限の目安:
    • ノードは 2,000 個（要素 約2万）でも 1 つのドラッグは 1.2ms で軽い。ただし全部を同時に動かすと 82ms。
    • 図形は 5,000 個でもパン・ズームは滑らか（1.7ms）。ただし図形の層を描き直すたびに 50〜86ms かかる。全部を同時にドラッグすると約 20fps に落ちる。1,000 個なら描き直しは 11〜14ms。
  • 未着手: ブール演算・テキスト編集・SVG 書き出し。

2. ベクター編集（Figma 風）

図形数と負荷

全図形を1枚の層に Painter2D で描き、ビューの拡大・平行移動は要素の変形（GPU）で当てる。ドラッグ中は、動かす図形だけを操作層へ移して毎フレーム描く。

場面1,000図形5,000図形
パン・ズーム（GPU で拡大するだけ）0.7ms/フレーム1.7ms/フレーム
静止層を1回描き直す（ドラッグの開始・終了、描き直し方式でズームが止まった瞬間）11〜14ms50〜86ms
うち描画コールバック（パスを積む時間）約2ms9〜12ms
全部ドラッグ中（毎フレーム全部を描き直す）約12ms/フレーム約50ms/フレーム（約20fps）
  • 描き直しの費用は図形数にほぼ比例する（1図形あたり約11µs）。同じ内容を5フレームおきに描き直させても毎回同じだけかかった。描画コールバックでパスを積む時間は2割弱で、残りは UITK の描画更新（UIElementsRepaintPanels）の中でかかる。内訳（塗りの三角形分割・メッシュの転送）までは切り分けていない
  • 1,000図形なら、ドラッグの開始・終了の引っかかりは1フレーム落ちる程度で済む。5,000図形級なら、層を空間で区切って（タイル化）一度に描き直す量を減らす設計が要る

拡大したときの画質

「GPU で拡大するだけ」（等倍で描いた形を要素の変形で拡大）と、「拡大時に描き直す」（今の倍率で描き直す）を、同じ場所で撮り比べた。

  • 縁のぼけは、どちらの方式でも出なかった。10倍までは「GPU で拡大するだけ」で十分で、描き直しの負担も無い
  • 64倍では描き直しが要る。描き直す範囲は表示範囲の3倍に絞り、ズームが止まって0.15秒後に描く
  • 鋭い角の形が倍率で変わるので、拡大の方式を途中で切り替えると角の見た目が跳ねる

3. Web と比べて自前で持ったもの

機能Web での手段UITK でやったこと
線・図形の当たり判定SVG の要素ごとのイベント、isPointInPath図形ごとに単位座標へ戻して内外判定。パスは折れ線にして偶奇則と線までの距離（約80行）
描き直しの範囲を絞るReact Flow の仮想化、canvas の部分再描画静止層と操作層、動く辺だけの層、ミニマップの間引き
元に戻す・やり直す状態管理ライブラリコマンド方式の履歴（73行、両デモで共通）
スマートガイド（Figma 独自）辺・中心の9本ずつを総当たり（約60行）

テキスト編集・SVG 書き出しcontenteditable / 標準未検証

4. 移行計画への示唆

  • 研究ツリー・レシピ木のようなノード図は、今回のノード編集の部分集合で足りる。数百ノードなら最適化なしでも余裕がある
  • どの画面でも、拡大縮小する親要素には UsageHints.GroupTransform、頻繁に動く要素の位置は translate、半透明のパネル背景は避ける。この3点は共通部品の規約に入れる
  • 地図や配線図のように数千の図形を描く画面を作るなら、最初から層分けとタイル化を前提にする
