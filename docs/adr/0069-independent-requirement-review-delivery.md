# 0069: 要求原文を独立検査へ全文配達する

Status: Proposed（検証・PR提出の対象。通常運用への採用・マージは未裁定）

## 背景と依頼

出所: ユーザー裁定 2026-09-22「ok、そしたら検証からPR作成まで実行して」「なんで別の案を考えなかったの」「じゃあ進めて」。これは代案の検証・PR作成の委任であり、以下の設計詳細やマージの承認ではない。

従来の計画引継ぎ表・結果追跡の追記だけでは、指定手段を確認して要求結果を達成扱いする挙動が残った。中間担当の要約にも同じ誤解が入り、後段がそれを保証済みとして採用した。別担当による報告の再監査も同じ誤結論を維持した。

原文要求を機械的に分担し、全context・全patchを起動promptへ直接入れた試行では、未変更の描画末端・独立集計・公開APIの迂回をそれぞれ検出した。ただし重大度の希釈、未読経路の確認済み化、非同期の再選択ケースの見逃しも残る。検出率・完全性を保証できる証拠ではない。詳細は logs repo `harness/postmortem/2026-09-22-pr1394-boundary/`。

旧検証の「橋脚色を無条件Critical」「単体橋脚を送信停止」は当時要件から一意に導けない。旧未達記録は残すが、元の仕様違反と同一視しない。

## 候補の設計

以下はすべて **出所: agent前提（固定入力のC/CI試行と既存reviewerの責務に基づく）**。未回答の追加負担に関する質問を、承認済みとは扱わない。

1. 既存 `core-any-user-intent-fulfillment` の責務内で、要求ごとの独立検査を実行する。新しいドメイン専用レンズを追加しない。既存の裁定引用・出所検査を残す。
2. reviewerから起動する専用ランナーが、原文・全context・全patch・汎用検査手順を各workerの開始promptへ直接配達する。既存Workflow/inline fallbackのreviewer起動契約を変更しない。原文の言い換えや期待欠陥のヒントは渡さない。
3. 構造化contextのゴールをMarkdownの原文単位で分ける。見出し・継続行・出所ラベルを保持する。構造化ゴールのない自由文は全体1単位とする。分割不能・空入力は理由を出して停止し、0件合格にしない。
4. 全workerへ同じ固定checkoutと全入力を渡す。他workerの判断・将来修正・採点基準は渡さない。入力SHA-256、checkout HEAD、モデル、単位の範囲、各報告と起動結果を保存する。
5. workerは要求される観測結果/禁止を逐語の要求に結びつけ、具体例を最終利用点・公開境界まで追う。根拠を読んだ範囲を明記する。現在の呼出例は型保証の代替にならず、要求に書かれていない強い保証を足さない。
6. 判定は反例あり・静的根拠あり・確認不能・解釈要裁定・コード検査対象外を区別する。反例ありはCritical、確認不能はWarning、正当な解釈で合否が変わる場合は設計判断とする。型で禁止する要求を「現在使っていないからよい」と弱めるのは解釈分岐ではない。
7. ランナーは件数と欠員を機械照合する。報告欠損・不正形式・プロセス失敗は未完了を明示して非0終了し、成功扱いしない。失敗後は同じ入力の完了成果物を保持して未完了単位だけ再開する。コード上の正しさまで機械的に証明したとは呼ばない。
8. 既存reviewerは原文検査の報告を削除・弱めず引き渡し、裁定引用検査を追記する。統合側の通常の実コード照合・裁定は維持し、未確認や設計判断を「Criticalなし＝全要求達成」に潰さない。

## 適用範囲・費用

出所: agent前提（ユーザーの継続委任、AGENTS.mdの未決事項は記録して進む規定）。まず隔離ブランチ上の候補として全要求を検査する。9要求なら既存親reviewerに加え9 workerが必要になり、各workerへ全差分を送る費用が発生する。この追加負担はPRで開示し、通常運用への採用はユーザーの判断に残す。選択された要求だけを調べて全件検査と呼ぶ方式にはしない。

グローバル `all-code-review` とrepo `moores-code-review` の両方に同じ機構を置く。グローバル側のlight/fullの選択、他reviewer、既存裁定検査は変更しない。ゲームコード・Unity・別repoマスタは対象外。

既存のpriority指定によりglobalの既定lightでも追加workerが発火する。既存の親reviewerからbackground taskを一度起動して待機する方式を候補とし、外側Workflowは再構築しない。子プロセスの終了所有・run lock継承・原子的な記録保存で、中断と再開による二重起動を防ぐ。nested CLIと最終報告までの伝達は本番契約での検証が必要で、旧CI試行だけでは実証済みでない。

## 未確認・曖昧さの扱い

出所: agent前提（既存出力契約とユーザーの検証依頼）。欠陥検出と未確認の正しい申告は別に採点する。重要な要求が未確認・要裁定なら完了を宣言せずDraftへ明示する。元の要求を超える検証・納品作業の実行証跡検査は追加せず既存工程に任せる。

統合規則と最終出力契約にも要求IDごとの未確認・欠員・解釈待ち・対象外を残す欄を接続する。未確認をコード欠陥や設計質問へ自動昇格させず、必要な検証/情報を記す。判定の訂正は既存の実コード照合に従い、元IDと根拠を残す。

## 検証・候補の状態

出所: agent前提（postmortem/skill-improvement規約）。配線テスト、原文単位/入力配達/欠員/再開のテスト、selector、当時全diff、本番同一契約、別分野の陽性/陰性を確認する。試行回数は各条件n=1を基本とし、追加試行は改善点と情報利得を先に記録する。合成対照を自然事例のholdoutと呼ばない。

過去のB/C/CI/D試行は候補設計の根拠であり、本番配線後の検証の代用にはしない。見逃しと誤検知は残したまま報告する。計画段階の候補は別に検証し、レビューだけの成果で両工程が成立したとは報告しない。

独立性の限界: workerは新しいセッションと固定入力を使うが、閲覧範囲の指示は機械的なファイルアクセス隔離ではない。実装中の否定系テストが誤ってCLIへ到達した試行で、禁止したGit履歴のReadを実ログから確認した。本番契約の試行ではtool利用先を監査し、範囲違反をした結果を独立検証成功に数えない。テスト側には本番CLIを起動前に拒否する独立ガードを追加した。このダミー入力の事故を有効性検証の成功例には含めない（詳細: logsのaccidental-test-launch-audit.md）。
