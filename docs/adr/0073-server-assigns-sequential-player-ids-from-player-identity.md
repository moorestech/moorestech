# 0073. プレイヤーIDはサーバーがプレイヤー身元からワールド単位で連番採番し、接続の紐づけだけを信じる

日付: 2026-09-27
状態: 採択（`.decisions/2026-08-14-プロトコルのplayerId自己申告は既存多数派として放置する.md` と、AGENTS.md「既知の制約」の自己申告playerIdの項を置き換える）

## Context

プレイテスト報告（Steam 76561198319362448、報告ID 20260926_145808_e35a893b）のシングルプレイのセーブに、プレイヤーが2人いた。ID 1 はスポーン座標のままで初期装備だけを持ち、ID 1623179277 が本人だった。`InInventoryItemChallengeTask` が先頭のプレイヤーしか数えていなかったため、原木のチャレンジが達成されなかった（PR #1427 で修正済み）。

ID 1 の出どころは、クライアントの `InitializeProprieties.DefaultPlayerId = 1` だけだった。採番は `SetPlayerId`（MainMenu シーンの Start）が `Random.Range(2, int.MaxValue)` で行い、`PlayerPrefs` に保存する。ところが全データリセット（`ResetAllDataConfirmPopup`）は `PlayerPrefs.DeleteAll()` でこの保存値も消す。リセット直後に同じメニューから開始すると、`LocalGameLauncher` は何のログも出さずに ID 1 で接続する。次に起動すると新しいランダムIDが採番され、同じワールドに別人として入る。

問題の本体は次の3つにある。

- プレイヤーの状態はワールドのセーブにあるのに、その鍵（プレイヤーID）はPCの `PlayerPrefs` という別の寿命の場所に置かれている。
- ランダム採番は衝突しても誰も気づけない（衝突確率は約21億分の1で、誕生日のパラドックスでは約5.5万人で50%）。
- 各パケットがペイロードで playerId を自己申告するため、誰でも他人を名乗れる。

## Decision

- **既定のプレイヤーIDという概念を撤去する。** `DefaultPlayerId`・`SetPlayerId`・`PlayerPrefs` の `PlayerId` キーを消す。身元が分からない接続は、理由をログに出して拒否する。
  出所: ユーザー裁定 2026-09-27 原文「そもそも、デフォルトプレイヤーidって概念を消すのと、プレイヤーの採番も変えたいかも 誕生日パラドクス問題あるよね」

- **プレイヤー身元はクライアントが決める。配布版はSteamID、Steamが無い環境は端末固有値から決定論的に作る。** 端末固有値には `SystemInfo.deviceUniqueIdentifier` を使う（MACアドレスは、Wi-Fiのランダム化やNICの抜き差しで変わるため採らない）。
  出所: ユーザー裁定 2026-09-27 原文「Steamがない時→MACアドレスなど固有IDから決定論的に」→ `deviceUniqueIdentifier` の提案に「1 ok」
  棄却案: MACアドレスから作る

- **配布版でSteamIDが読めなければ、開始を止める。** 理由を画面とログに出す。端末IDへは切り替えない。
  出所: ユーザー裁定 2026-09-27 質問「配布版（Steam経由）でSteamIDの読み取りに失敗したとき、身元をどう扱いますか？」→ 選択「開始を止める」
  棄却案: 端末IDに切り替えて開始する／端末IDで入り、次にSteamIDが読めたときに統合する

- **プレイヤーIDは身元とは別物で、サーバーがワールド単位で 1, 2, 3… の連番で採番する。** 身元とプレイヤーIDの対応表はワールドのセーブに持つ。パケットで運ぶのは小さいintのプレイヤーIDだけにする（通信量も減る）。
  出所: ユーザー裁定 2026-09-27 原文「GUIDとは別に固有のプレイヤーIDを連番で採番する（通信量を減らす目的もある）」

- **サーバーは、ハンドシェイクで接続に紐づけたプレイヤーIDだけを信じる。** 各プロトコルのペイロードから playerId を外し、`PacketResponseContext` に紐づいたIDを使う（該当は `Server.Protocol/PacketResponse` 配下28本）。
  出所: ユーザー裁定 2026-09-27。初回の質問「接続後のパケットに載せるプレイヤーIDを、サーバーはどう扱いますか？」には「自己申告のまま」と回答。直後の原文「技術的負債は極力残さないように」を受けて再質問し、選択「接続の紐づけだけ信じる」
  棄却案: 自己申告のまま据え置き、なりすまし対策は別件化する

- **リモート接続で名乗られた身元は、今回は検証しない。** Steam認証チケットでの本人確認は、リモートのマルチプレイを出すときの課題として bd moorestech-3eonp に積む。
  出所: ユーザー裁定 2026-09-27 質問「リモート接続で名乗られたSteamIDを、サーバーは検証しますか？」→ 選択「今回は検証しない、別件で積む」
  棄却案: Steamの認証チケットで検証する

- **接続中と同じ身元が、もう1つ接続してきたら後から来た方を拒否する。** 理由は応答とログに出す。
  出所: ユーザー裁定 2026-09-27 質問「すでに接続中の身元と同じ身元が、もう1つ接続してきたらどうしますか？」→ 選択「後から来た方を拒否」
  棄却案: 先の接続を切って後を通す

- **開発用に身元を上書きする経路は作らない。**
  出所: ユーザー裁定 2026-09-27 質問「開発中に同じPCで複数のクライアントを起動してマルチプレイを試すための、身元の上書きを用意しますか？」→ 選択「用意しない」
  棄却案: 配布版以外だけ起動引数で上書きできるようにする

- **旧セーブの変換では、旧プレイヤーを全員「持ち主未定」で残し、最初に接続した未知の身元へ、いちばん遊んでいた旧プレイヤーを結びつける。**
  出所: ユーザー裁定 2026-09-27 原文「案Bが良い気がする」（提示した案b: 旧プレイヤーを全員持ち主未定として残し、最初に接続した身元へ、いちばん遊んでいたプレイヤーを結びつける）
  棄却案: 中身の無いプレイヤーを削除し、残った1人を最初に接続した身元へ結びつける（案a）

- **「いちばん遊んでいた」は持ち物の総数で決める。** メイン・つかみ中・装備のアイテム個数の合計が最大の者を選ぶ。同数ならスポーンから遠い方、それも同じならプレイヤーIDが小さい方。
  出所: ユーザー裁定 2026-09-27 質問「旧セーブから『いちばん遊んでいたプレイヤー』を選ぶ基準はどれにしますか？」→ 選択「持ち物の総数」
  棄却案: スポーンからの距離／今後はプレイヤーごとのプレイ時間を記録する

- **旧セーブのランダムなプレイヤーIDは、変換時に連番へ振り直す。** 対象は、プレイヤーIDを鍵に持つ全節（`playerInventory`・`entities` のプレイヤー・`playerRidingStates`・`hotbarAssignments`・`remainingPlacementCounts`・`constructionPayers`・`miningCooldowns`）。
  出所: ユーザー裁定 2026-09-27 質問「旧セーブのランダムなプレイヤーIDを、変換時に1, 2, 3…へ振り直しますか？」→ 選択「振り直す」
  棄却案: 旧IDはそのまま残し、新規採番だけ連番にする

- **プレイヤーとベルト上アイテムが EntityInstanceId 空間を共有している件は、今回触らない。** bd moorestech-pejkw に積む。
  出所: ユーザー裁定 2026-09-27 原文「4そのままでもいいかね」

### agent前提（ユーザーの「残りいい感じにして」（2026-09-27）を受けて agent が決めた細部。ユーザー裁定ではない）

- 身元は種別を接頭辞にした文字列で表す。`steam:<SteamID64>` と `device:<deviceUniqueIdentifierのSHA-256の16進>` の2種。端末の生の識別子は、リモートのサーバーやセーブへ出さない。
  出所: agent前提（リモート接続では身元がサーバーのセーブに残るため、生のハードウェア由来値を外へ出さない。接頭辞で出どころを区別しておけば、SteamIDと端末値が衝突しない）

- 身元の種別は「Steamで配るビルドかどうか」で決める。これはビルド時に焼き込んだ目印で判定し、実行時のSteamの状態では決めない。Steam配布ビルドはSteamだけを使い、それ以外（Editor・開発ビルド・展示会用のローカル配布ビルド）は端末値だけを使う。1つの起動の中で種別が切り替わることは無い。目印は build-info.json（`BuildInfoWriter`）に、Steamへ上げるビルド（`scripts/playtest/release-playtest.sh` の経路）だけが立てる項目として持たせる。
  出所: agent前提（既存の `PlaytestLaunchProfile.Decide` は、Steamが起動していないと配布版でも DeveloperMode に倒す（`PlaytestLaunchProfile.cs:84`）。これに乗ると配布版のSteam失敗が端末値へ落ち、「開始を止める」の裁定と矛盾する。また展示会用の配布ビルドはSteamを使わないので、「配布版＝Steam必須」とも言えない）

- 採番は、ワールドのセーブに持つ「次のプレイヤーID」から 1 始まりで払い出す。欠番は再利用しない。
  出所: agent前提（再利用すると、削除済みプレイヤーの残り状態と取り違える余地が残る。0 と負値は、既存の未設定・ブロードキャスト（`NotificationService.BroadcastPlayerId = -1`）と重ならないよう使わない）

- 対応表・持ち主未定の結びつけ候補・次のプレイヤーIDは、ワールドのセーブの新しい節 `players` に持つ。セーブ形式を変えるので、`WorldSaveAllInfo.CurrentVersion` を 2→3 に上げ、`SaveMigrationStepV2ToV3` と変換テストを同じPRに入れる。持ち主未定は、身元欄が空の対応として表す。
  出所: agent前提（AGENTS.md「互換性とパフォーマンス」のセーブ形式の例外規約と moorestech-save-migration スキル）

- ハンドシェイクの要求には身元を載せ、応答で採番したプレイヤーIDか拒否理由を返す。クライアントは応答を受けてから `PlayerConnectionSetting` を作る。拒否されたら、既存の初期化失敗の経路（理由を表示してメインメニューへ戻る）に乗せる。
  出所: agent前提（既存の `InitializeScenePipeline` の初期化失敗経路を前例とする。今の `PlayerConnectionSetting` は接続前に作っていて、サーバー採番とは順序が合わない）

- ハンドシェイク前の接続から来たハンドシェイク以外の要求は、理由をログに出して無視する。
  出所: agent前提（AGENTS.md「fail-closedの経路は理由をログへ必ず出す」）

- バグ報告の再現ツールは、再現用に複製したワールドの対応表の上で、報告者の身元（バンドルの manifest の SteamID から `steam:<id>`）に結びついたプレイヤーを、開発機の身元へ付け替える。ゲーム本体には上書きの経路を作らない。
  出所: agent前提（開発機の身元は報告者と違うため、そのまま読むと報告者のプレイヤーではなく新しい空のプレイヤーで再現してしまう。複製したワールドのデータを書き換えるだけなら、「開発用の身元上書きは用意しない」という裁定と両立する）

- 旧セーブで、最初の未知の身元へ1人を結びつけた後に残った持ち主未定のプレイヤーは、そのまま保管する。以後に来る未知の身元には新しいプレイヤーIDを払い出し、持ち主未定の者を自動では割り当てない。
  出所: agent前提（案bの裁定は「最初に接続した身元へ1人」までで、2人目以降に他人のデータを自動で渡すと取り違えが起きうる。自動割当を1回に限れば、取り違えの範囲も1回に閉じる）

- Steam身元と端末身元は別人として扱い、自動では結びつけない。同じPCでも、Steam配布ビルドと展示・開発ビルドで同じワールドを遊ぶと別のプレイヤーになる。
  出所: agent前提（両ビルドで同じワールドを遊ぶ運用は無い。結びつけの確認UIを作るのは、使われない経路を作らないという「開発用の身元上書きは用意しない」の裁定の趣旨に反する）

- Steamを使わないビルドで `SystemInfo.deviceUniqueIdentifier` が有効な値を返さない（空、または Unity の `SystemInfo.unsupportedIdentifier`）ときは、理由を表示してログに出し、開始を止める。代わりのランダムGUIDは作らない。
  出所: agent前提（代わりの保存値を作ると、それが消えたときに今回の幽霊プレイヤーと同じ現象が再発する。Steamが読めないときの「開始を止める」の裁定と揃える）

- 旧プレイヤーの自動割当を間違えたときや、端末が変わって身元が変わったときに、既存プレイヤーへ身元を結び直す操作は今回は用意しない。必要になったら、開発者がセーブの `players` 節を直接直す。
  出所: agent前提（今回の目的は重複を生まない採番で、復旧のUIは使う場面がまだ無い。`players` 節は意味の読めるJSONなので、手で直せる）

- 全データリセットは今後もワールドを消すが、身元には影響しない（身元は `PlayerPrefs` に置かないので）。
  出所: agent前提（本ADRの身元の決め方からの帰結）

- AGENTS.md「既知の制約」の自己申告playerIdの項を削除し、`.decisions/2026-08-14-プロトコルのplayerId自己申告は既存多数派として放置する.md` は本ADRで置き換えられた旨を追記する。moores-code-review の server-state-sync レンズにある「既存多数派パターンはWarning止まり」の注記のうち、playerId自己申告を例にしている箇所も更新する。
  出所: agent前提（置き換えた裁定を文書に残すと、レビューが旧前提で判定するため）

## Consequences

- 同じSteamアカウントなら、別のPCへセーブを移しても同じプレイヤーとして入れる。別のSteamアカウントで他人のセーブを開くと新しいプレイヤーになり、元のプレイヤーは残る。
- Steamがオフラインだと、配布版は開始できない（ADR 0070 の「オフラインでも遊べる」は、プレイテストの送信について言ったもの。本ADRで、配布版の開始にSteamの身元が必須になる）。
- 同じPCで開発用のクライアントを2つ起動すると、2つ目は二重接続として拒否される。
- 旧セーブの本人ではない旧プレイヤー（今回の幽霊）は、持ち主未定のまま残り、全員宛ての報酬（`giveItem` の `allPlayers`）は受け取り続ける。
- 28本のプロトコルと、playerIdを直接作っているテストのすべてが変更対象になる。
