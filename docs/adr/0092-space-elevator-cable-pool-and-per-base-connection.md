# 宇宙エレベーターはワールドのケーブルプールと拠点ごとの接続で機能させ、打ち上げ成果は軌道到着サービスに委ねる

Tier9 の宇宙エレベーター拠点は、ロケットで打ち上げたグラフェンケーブルを使って「接続」すると、燃料・筐体なしで GPU 衛星を軌道へ運べる2つ目の打ち上げ口になる。発射台は行き先を設定せず積荷を自動で打ち上げる（S2）ため、ケーブルは特定の拠点ではなくワールドに1つのケーブルプールへ積み、拠点ごとの接続でプールから1エレベーター分を消費し、接続済み拠点の撤去でプールへ戻す。打ち上げ成果（計算データ）の量は発射台と同じでなければならないため、拠点は S2 の軌道到着サービスへ成果を問い合わせて出力口に入りきるかを確かめ、「届いた」と伝えて返ってきたアイテムを出力口へ入れるだけにする。

## 決定

- **ケーブルプールはワールド単位の状態として S3 が持ち、セーブする。** S2 の軌道到着サービスが流す「軌道到着（積荷アイテム・個数）」を購読し、積荷がグラフェンケーブルならプールへ足す。打ち上げ総数は持たない。
- **接続は拠点ごとのボタン操作。** 押した時点でプール残量が1エレベーター分以上ならその分を引いて拠点を接続済みにする。足りなければ接続できず、理由を UI に出す。押せるかどうかもプールが判定する: プールは残量が変わるたび（と拠点の設置時）に各拠点へ「接続できる／ケーブル不足」を送り、拠点の状態に載せる。UI は状態を表示するだけで、残量と1エレベーター分を自分で比べない。接続済みの拠点を撤去すると1エレベーター分をプールへ戻す。未接続の拠点の撤去はプールに影響しない。
- **昇降機は1拠点1台。** GPU 衛星を1つ受け取り、電力を使って一定時間かけて昇る（電力不足なら遅くなる）。昇り切ったら軌道到着サービスへ衛星を渡し、返ってきた打ち上げ成果を出力口へ入れる。昇り始める前と渡す直前に、軌道到着サービスへ成果を問い合わせて出力口へ入りきるかを確かめ、入らなければ衛星を入口に残す／頂上で待たせ（待つ間は電力を使わない）、理由を UI に出す。打ち上げ後に成果を預かる保留は持たない。昇降中の衛星は拠点のセーブに入れ、撤去時はプレイヤーへ返す。
- **何を運ぶか・どのケーブルを数えるかはマスタに書く。** 拠点のブロックパラメータに「昇降機が運ぶ積荷（GPU衛星 Lv1〜Lv5）」「接続に使うケーブルのアイテム」「1エレベーター分の本数」「昇降時間」「昇降中の電力」「出力口のスロット数」を持つ。プールはこのケーブルのアイテムの軌道到着だけを数える。運ぶ積荷とケーブルが軌道到着の表に無い、運ぶ積荷にケーブルが含まれる（ケーブルを昇降機で運べるとロケット無しでプールが増えるため）、または衛星1機の成果が空の出力口にも入りきらない（頂上で永遠に待つため）ときは、サーバー起動時に止める。
- **クライアント同期はブロック状態の3点セット。** 拠点のブロック状態に「接続済みか・昇降の進み・プール残量・状態（接続できる／ケーブル不足／昇降中・待ちの理由）」を載せ、プールの増減で全拠点の状態変化を通知する。1エレベーター分の量はマスタの値なので状態に載せず、クライアントがマスタから読む。接続ボタンは拠点 UI から専用プロトコルで送る。
- **見た目は仮モデル。** 土台＋ケーブル＋昇降機を基本図形で組み、接続でケーブルが現れ、昇降中は昇降機がケーブルを昇る。

## 呼び出し側の線引き

- 拠点が知ってよいのは「プールに接続を頼む・撤去時に返却を頼む」と「軌道到着サービスへ成果を問い合わせて出力口に入りきるかを確かめ、衛星を渡して返ってきたアイテムを出力口へ入れる」まで。プールの残量判定・1エレベーター分の量の引き算・計算データの量は知らない。プールは「接続できた／足りない」を返し、残量が変わるたびに各拠点へ「接続できるか」を送る。UI は拠点の状態を表示するだけで、接続できるかを判定しない。
- プールは発射台の内部を知らない。S2 の通知を購読するだけで、どの発射台が打ち上げたかは見ない。

## Considered Options

- 接続はワールドで最初の1回だけ（以降の拠点はそのまま動く）／進捗は共通で拠点ごとに押すが追加のケーブルは不要／拠点ごとに規定量のケーブルが要り発射台に行き先を指定する: ユーザーが提示選択肢を採らず、プールからの消費と撤去での返却を指定した。
- 衛星はいくつでも同時に昇れる（遅れるだけ）: 処理量に差が出ずロケットが不要になる。不採用。
- 拠点を反物質の供給源にする／接続を反物質爆弾研究の解放条件にする: エレベーターの機能は衛星の打ち上げであり爆弾はストーリー側の話、としてユーザーが不採用。

## 出所

- 接続は宇宙エレベーターが機能するためのもの、エレベーター経由でも GPU 人工衛星を打ち上げられる: ユーザー裁定 2026-10-23 原文「爆弾を規定量はストーリーの話しであって、宇宙エレベーターの接続は宇宙エレベーターが宇宙エレベーターとして機能するためのもの。また、宇宙エレベーターを作ると、宇宙エレベーター経由でもGPU人工衛星を打ち上げすることが出来る」
- 燃料・筐体不要で時間がかかる: ユーザー裁定 2026-10-23 原文「燃料不要、筐体不要」「ただし、ロケットに比べて入手までに時間がかかる」
- 1拠点1台ずつ昇る: ユーザー裁定 2026-10-23 → 選択「1拠点1台ずつ昇る (Recommended)」
- ケーブルプール・拠点ごとの接続・撤去で返却: ユーザー裁定 2026-10-23 原文「進捗はワールド共通で、接続はその拠点ごとに接続処理を行う。たとえば、1エレベーターでグラフェン100が必要だとして、200をすでに打ち上げ済みなら、宇宙エレベーター拠点を2つおき、2つとも接続できる。追加で50うちあげても、その時点でエレベーターと接続はできない。もし接地、接続済みの2つのエレベーターのどちらか1つを撤去したら、宇宙エレベーターの素材プールに100が変換され、150となる。そうなると、再びさっきせっちした3つめのエレベーター拠点と接続可能になる」
- 押せるかをプールが判定し UI は表示するだけ: ユーザー裁定 2026-10-23 質問「宇宙エレベーター拠点の『接続する』ボタンを押せるか（プールのケーブルが1エレベーター分あるか）を、どこで判定しますか？」→ 選択「サーバーが判定 (Recommended)」 [[2026-10-23-エレベーター拠点に接続できるかはサーバーのプールが判定し画面は表示するだけ]]
- 不足時の比例低速化: agent前提（発射台に揃える実装者の具体化）。現在のR17の明示要求として維持する。次の引用は電力の使用有無までを支え、低速化の選択・比較案の棄却までは示さない。
- 昇降中に電力を使う: ユーザー裁定 2026-10-23 → 選択「昇降中に電力を使う (Recommended)」
- 簡易モデル＋昇降機の上昇: ユーザー裁定 2026-10-23 → 選択「簡易モデル＋昇降機の上昇 (Recommended)」
- 軌道到着サービスへ委ねる形: S2 の ADR 0091（feat/tier9-compute-data-loop）と S3 の依頼「打ち上げ結果の処理は S2 側のサービスに持たせ、拠点はそれを呼ぶだけ」。agent前提
- 出力口が満杯なら待たせて理由を出す: S2 のユーザー裁定 [[2026-10-23-計算データは打ち上げた設備の出力口に出す]]（feat/tier9-compute-data-loop）
- 保留を持たず、昇り始める前と渡す直前に成果が出力口へ入りきるかを確かめて待たせる: S2 のユーザー裁定 [[2026-10-23-発射台は成果が出力口に入りきるときだけ建造と打ち上げを進める]]（feat/tier9-compute-data-loop。明示引用「発射台の出力口が満杯のとき、どこで待たせますか？」→ 選択「入りきる時だけ建造開始」。同ファイルの決定文に「宇宙エレベーター拠点（S3）も同じ方式にする」）。拠点での形（2点の確認・頂上で待つ間は電力を使わない・出力口のスロット数と起動時の検査）は agent前提（前例: 機械の開始前と完了直前の出力確認）
- 運ぶ積荷・ケーブルのアイテムをブロックパラメータに持ち、起動時に軌道到着の表と突き合わせて止める: agent前提（AGENTS.md「必須の設定が無いときはいちばん早い段階で止める」、ハードコードしたアイテム GUID を避ける）
- プールを S3 がセーブする・ブロック状態の3点セットで同期・接続を専用プロトコルで送る・呼び出し側の線引き: agent前提（AGENTS.md「サーバー可変状態のクライアント同期は3点セット」、moorestech-principles「判断を内包する新設サービスの呼び出し側の線引き」、前例 SetElectricToGearOutputModeProtocol・IBlockStateObservable）
- 1エレベーター分のケーブル数・1便のケーブル数・昇降時間・電力値: agent前提（シミュレーションで決め、全体の時間目標は S1 の裁定 [[2026-10-23-Tier9の目標プレイ時間は半導体解放からクリアまで15〜25時間]] に従う）
