# 列車同期の欠落を待機し、発生位置を診断へ残す

列車・レールの順序付き差分が欠けた場合は、欠けたtick・連番を飛び越さず待機を続ける。ほかのゲーム処理は継続する。後続の受信で欠番が確定した場合、列車同期はその位置で永久待機する。通常の到着待ちでは、必要なメッセージが届けば順序どおりに進行する。

出所: ユーザー裁定 2026-09-28「クライアント側は永久にtickを待ち続け」「ゲームはtrainなど差分通知が必要なものは停止したままほかは動き続ける」。通常の到着待ちと確定欠番の区別は、TCPの順序保証に関する追加裁定に基づく実装判断。

診断には初めて待機した日時・期待tick/連番・最後の適用位置・最新受信位置・hash不一致値・前後の受信履歴を残す。後続の連番を受信済みなのに必要な連番がバッファにないことを確認した時点で、クライアントの永続データ領域の `Logs/TrainSynchronization` へJSONを保存する。同じ未解消の待機では保存を重複させない。

出所: ユーザー裁定 2026-09-28「具体的にいつからtick差分がずれ、または抜けたか、ってのを記録する」、ローカル診断保存の提案に対する「実装して」、追加裁定「欠番確定時に即保存する」。JSON形式・フォルダ・同一待機の重複抑制はagent前提（既存のクライアントローカル診断・ディスク書き込みの役割に合わせる）。

欠番は同じtick内の1連番でも即保存の対象とする。通知がまだ届いていないだけの間は、最初の待機位置と日時を保持して待つ。tick境界の連番リセットとhashによる正常進行を考慮し、適用前の受信だけで欠番と決めず、既存バッファとgateで必要な位置がないことを確認する。

出所: ユーザー裁定 2026-09-28「後続tickから実際の乖離を確認できた場合だけ保存」、TCPの順序保証についての確認後の追加裁定「欠番確定時に即保存する」。

hash不一致だけの待機は、受信済み最新tickと適用tickの差が200以上になった時点で保存し、永久待機へ移る。同じ適用位置と受信hashに対する不一致結果を再利用し、待機中の同じ状態を毎フレーム全量計算し直さない。

出所: ユーザー裁定 2026-09-28「200tick差（約10秒分）」。追加裁定は欠番の保存条件へ適用し、hash不一致の保存条件は維持する（適用範囲はagent解釈）。

永久待機への遷移時に未適用のevent/hash本体を解放する。その後の受信は直近256件のメタデータだけ保持し、payloadを蓄積しない。停止判断は列車同期側が所有し、診断ファイルの保存成否にかかわらず同じ停止状態を保つ。

出所: agent実装判断。永久待機中のpayload蓄積が他のゲーム処理の継続を妨げることを防ぐ。hash不一致の200tick到達後も同じ保持方針を使う。

履歴は上限付きで保持し、初回待機の前後関係は別に固定する。正常な到着待ちの短い空白ではエラーファイルを生成しない。既存の初回snapshot適用完了後に診断を有効にする。保存は同一停止につき一度試行し、ディスク境界の失敗はログと失敗結果に残す。ゲームの他処理へ例外を漏らさない。

出所: agent前提（`FrameTickLog` の上限付き履歴、`SessionOriginSnapshot` のディスク境界、既存初回snapshot完了の前例）。受信位置と同期状態は`TrainUnitTickState`、停止判定はhash gate、履歴とJSON保存は列車同期の診断クラスが所有する。
