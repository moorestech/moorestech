# 列車同期の欠落を待機し、発生位置を診断へ残す

列車・レールの順序付き差分が欠けた場合は、欠けたtick・連番を飛び越さず待機を続ける。ほかのゲーム処理は継続する。後から必要なメッセージが揃いhash検証に成功すれば、同じ順序付き経路で進行する。

出所: ユーザー裁定 2026-09-28「クライアント側は永久にtickを待ち続け」「ゲームはtrainなど差分通知が必要なものは停止したままほかは動き続ける」。後着時の継続はagent前提（既存の順序付きバッファで待機する意味を維持）。

診断には初めて待機した日時・期待tick/連番・最後の適用位置・最新受信位置・hash不一致値・前後の受信履歴を残す。後続の連番を受信済みなのに必要な連番がバッファにないことを確認した時点で、クライアントの永続データ領域の `Logs/TrainSynchronization` へJSONを保存する。同じ未解消の待機では保存を重複させない。

出所: ユーザー裁定 2026-09-28「一定のtick数乖離したらクライアント側からエラーログ的なのをセーブする、具体的にいつからtick差分がずれ、または抜けたか、ってのを記録する」およびローカル診断保存の提案に対する「実装して」。JSON形式・フォルダ・同一待機の重複抑制はagent前提（既存のクライアントローカル診断・ディスク書き込みの役割に合わせる）。

欠番は同じtick内の1連番でも即保存の対象とする。通知がまだ届いていないだけの間は、最初の待機位置と日時を保持して待つ。tick境界の連番リセットとhashによる正常進行を考慮し、適用前の受信だけで欠番と決めず、既存バッファとgateで必要な位置がないことを確認する。

出所: ユーザー裁定 2026-09-28「後続tickから実際の乖離を確認できた場合だけ保存」、TCPの順序保証についての確認後の追加裁定「欠番確定時に即保存する」。

hash不一致だけの待機は、受信済み最新tickと適用tickの差が200以上になった時点で保存する。

出所: ユーザー裁定 2026-09-28「200tick差（約10秒分）」。追加裁定は欠番の保存条件へ適用し、hash不一致の保存条件は維持する（適用範囲はagent解釈）。

履歴は上限付きで保持し、初回待機の前後関係は別に固定する。正常な到着待ちの短い空白ではエラーファイルを生成しない。初回snapshot適用成功後に診断を有効にする。保存失敗はディスク境界でログと失敗結果を残し、ゲームの他処理へ例外を漏らさない。

出所: agent前提（`FrameTickLog` の上限付き履歴、`SessionOriginSnapshot` のディスク境界、既存初回snapshot完了の前例）。呼び出し側は受信・適用・待機を通知し、閾値判定・履歴・保存判断は列車同期の診断クラスに集約する。
