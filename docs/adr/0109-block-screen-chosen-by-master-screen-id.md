# 0109: ブロックを開いたときの画面はマスタのブロック画面IDで選ぶ

日付: 2026-11-27
状態: 採択（`openable` を廃止する。ADR 0107 の「開けるかどうかはマスタの openable フラグで決める」を置き換える）

## 文脈

ブロックを開けるかどうかはマスタの `openable: bool` で決まり、どの画面を出すかはクライアントの C# の表が blockType で決めている（`Client.Ui.State/BlockInventory/Logic/Panel/BlockComponentRegistry.cs` が本文の種類、`Client.Ui.State/BlockInventory/SectionStack/SectionStackConfigTable.cs` が共通画面のアイテム欄・液体欄）。同じ blockType のブロックに別の画面を出せず、画面の割り当てを変えるにはコードを変える必要がある。

uGUI の頃はマスタの `blockUIAddressablesPath` がプレハブを指し、マスタが画面を選んでいた。Web UI 移行で Web 側が blockType の表を持ち、値は「空かどうか」だけに使われ、2026-09-09 に `openable` へ改名された。マスタで画面を選ぶのをやめると決めた裁定は無い（`.decisions/` と ADR を探索して確認）。

出所: ユーザー 2026-11-25「なんで今までマスタにuiに具体的な値を設定できてたのに、それが取りやめられたのかって聞いてるの。これだと柔軟性下がってるじゃん。」、2026-11-27「マスタでUIを分岐できるようにしたい」

## 決定

- **マスタの各ブロックはブロック画面IDを1つだけ持つ。ID の先はクライアントに C# で登録した画面で、画面の中身は ID の側が持つ。** blockType で画面を決める表（BlockComponentRegistry・SectionStackConfigTable）は使わない。
  出所: ユーザー裁定 2026-11-27 原文「Prefab指定やコンポーネント指定みたいに本質的にid指定になっていてほしい」→ 復唱確認のうえ選択「C#で登録した画面（推奨）」
- **`openable` を廃止し、「開けない」もブロック画面IDの1値で表す。全ブロックに必ず書く。**
  出所: ユーザー裁定 2026-11-27 選択「画面の指定にまとめる（推奨）」
- **ID が指せるのはゲーム本体に登録した画面だけ。** mod は本体の画面を自分のブロックに当てられるが、新しい画面は作れない。クライアントで mod の C# を読み込む口は作らない。
  出所: ユーザー裁定 2026-11-27 選択「本体の画面だけ（推奨）」
- **画面IDは今ある画面の組み合わせだけにする。見るだけの版など新しい画面は今回作らない。**
  出所: ユーザー裁定 2026-11-28 選択「今回は今ある画面だけ（推奨）」（問い: 同じ機能のブロックに見るだけの画面と操作もできる画面を当て分けたいか）
- agent前提（2026-11-27 にユーザーへまとめを示し「ok」を得た。裁定ではない）:
  1. ID は今ある「本文の種類 × 欄の構成」の組み合わせ1つにつき1つ作る（チェスト・機械・発電機・フィルター分岐器・列車・電柱など十数個）。名前はスキーマ enum の PascalCase（`Chest`）にし、「開けない」は `None`（2026-11-28 planning 中に変更。生成器が選択肢を C# の定数名にするため `:` を含められない）。
  2. 搬送量・電力・歯車などの追加の欄は、今と同じくブロックの値（`IBeltSpeedParam` 等）を見てどの画面にも自動で付ける。画面の見た目は変わらない（根拠: 既存の `SpecialBlockDetailReader` の性質判定。ユーザーが「画面実装の詳細」と確認した）
  3. スキーマの選択肢に無い ID がマスタにあれば、マスタ読込時に起動を止める。スキーマの選択肢にクライアントの画面が登録されていないことは CI のテストで止める（どちらもビルドに入るコードなので、食い違いはビルドの検査で必ず見つかる）。開いたときに表を引いて見つからなければ例外にし、blockType の表が未登録の種類を共通画面へ戻していた経路は消す（AGENTS.md「必須の値・設定が無いときは既定値で埋めずいちばん早い段階で止める」）。
  4. 画面の都合で blockType を見ている分岐（`OrbitalCargoLargePanelRule` の大きい画面など）は画面の定義の側へ移す。ブロックの機能の確認（`SpecialBlockCommands`・`TrainBlockCommands` の種類確認、`BlockNetworkInfoCache` のフィルター分岐器取得）は今のまま blockType を見る。
  5. サーバー（`InventoryRequestProtocol` の開けるかどうかの判定）とクライアント（`BlockGameObject` の `BlockInteractable` 付与）は、`openable` の代わりに ID が `none` でないかを見る。
  6. moorestech_master の全 mod の blocks.json を変換する（今の blockType の表どおりに ID を振り、`openable: false` は `none`）。
  7. 稼働状態や研究の進み具合で画面を切り替える仕組みは作らない。ID はブロックごとに固定。
  8. セーブ形式・通信形式は変えない（マスタの値はセーブにも通信にも乗らない）。

## 却下した案

- どの画面かだけをマスタへ移し、欄は blockType の表のまま（2026-11-27 提示）
- 画面と欄の設定値をマスタに直接書く（2026-11-27 提示）
- 画面を部品の並びとしてマスタに書く（2026-11-27 提示）
- ID の先を UI アセット（UXML）のパスにする（2026-11-27 提示）
- `openable` を別に残し、画面の指定は開けるブロックにだけ書く（2026-11-27 提示）
- mod の画面登録も作る（2026-11-27 提示）
- 見るだけの画面も今回作る（2026-11-28 提示）

## 帰結

- 同じ blockType のブロックに別の画面を当てられる。画面の割り当てはマスタだけで変えられる。新しい画面を足すには本体の C# が要る。
- マスタのスキーマから `openable` が消え、ブロック画面IDが必須で入る。moorestech_master の全 blocks.json と本 repo のピンが同時に変わる。
- 既存の表を使う箇所・テスト（`BlockRegistryCoverageTest` など）は ID の登録を検査する形に変わる。
