# 打ち上げ口は軌道到着を共通のサービスに委ね、打ち上げ成果と通知を一本化する

Tier9 の計算データループでは、GPU衛星を軌道へ送る打ち上げ口がロケット発射台（S2）と接続済みの宇宙エレベーター拠点（S3）の2つある。グラフェンケーブルもロケットで運び、S3 はその累計でエレベーター建設を進める。打ち上げ成果（計算データ）の決め方や「何が軌道に届いたか」の扱いを打ち上げ口ごとに書くと、同じ衛星で量がずれたり、S3 が発射台の内部を覗いたりする。そこで、軌道に届いた後の処理を1つのサービスにまとめ、打ち上げ口は「届いた」と伝えて返ってきたアイテムを自分の出力口へ入れるだけにする。

## 決定

- **積荷の表をマスタに置く。** 積荷ごとに「積荷アイテム・1便に積む個数・軌道到着で出る打ち上げ成果（アイテムと個数）」を持つ表を、打ち上げ口から独立したマスタとして新設する。GPU衛星 Lv1〜Lv5 は「1便1機・成果は計算データ×(レベル別の値)」、グラフェンケーブルは「1便N個・成果なし」の行になる（N と行の追加は S3）。発射台が受け付ける積荷はこの表に載っているものだけ。
- **軌道到着サービスを置く。** 打ち上げ口は軌道到着の時点で「積荷アイテムと個数」をサービスへ渡す。サービスは表から打ち上げ成果を決めて返し、UniRx で「軌道到着（積荷アイテム・個数）」を流す。S3 はこの通知を購読してケーブル累計を数える（累計の保存は S3）。
- **初打ち上げ済みかはワールド単位の状態として持つ。** 状態の持ち主は S2 の打ち上げ側で、セーブに入れる（セーブ形式が変わるため移行ステップを同梱する）。エレベーター拠点はこの状態に関わらない。

## 呼び出し側の線引き

- 打ち上げ口（発射台・エレベーター拠点）が知ってよいのは「サービスがあること・軌道到着を伝えること・返ってきたアイテムを自分の出力口へ入れること」まで。計算データの量・積荷の種類による分岐・レベル換算は知らない。
- 打ち上げ口は、出力口に打ち上げ成果を入れる空きがあるかを事前にサービスへ問い合わせ、空きが無ければ打ち上げ（昇り切り）を待たせて理由を UI に出す。成果の中身はサービスが決める。
- 発射台が「どの積荷が1便ぶん揃ったか」を判断するときも、1便の個数は表をサービス経由で引く。発射台に積荷ごとの個数を書かない。

## Considered Options

- 打ち上げ成果を各打ち上げ口のブロックパラメータに持つ: 同じ衛星の量を2か所に書くことになり、S3 の拠点が S2 の値を写す必要がある。不採用。
- 通知だけを用意し、成果の付与は各打ち上げ口が実装する: S3 が「打ち上げ結果の処理は S2 のサービスに持たせ、拠点はそれを呼ぶだけ」を希望しており、量のずれを防げない。不採用。
