# 打ち上げ口は軌道到着を共通のサービスに委ね、打ち上げ成果と通知を一本化する

Tier9 の計算データループでは、GPU衛星を軌道へ送る打ち上げ口がロケット発射台（S2）と接続済みの宇宙エレベーター拠点（S3）の2つある。グラフェンケーブルもロケットで運び、S3 はその累計でエレベーター建設を進める。打ち上げ成果（計算データ）の決め方や「何が軌道に届いたか」の扱いを打ち上げ口ごとに書くと、同じ衛星で量がずれたり、S3 が発射台の内部を覗いたりする。そこで、軌道に届いた後の処理を1つのサービスにまとめる。打ち上げ口は、成果を先に聞いて自分の出力口に入りきるかを確かめ、「届いた」と伝え、返ってきたアイテムを自分の出力口へ入れるだけにする。

## 決定

- **積荷の表をアイテムマスタに置く。** 積荷ごとに「積荷アイテム・1便に積む個数・軌道到着で出る打ち上げ成果（アイテムと個数）」を持つ表を、アイテムマスタ（items）のトップレベル配列として持つ。打ち上げ口のブロックパラメータには書かない。GPU衛星 Lv1〜Lv5 は「1便1機・成果は計算データ×(レベル別の値)」、グラフェンケーブルは「1便N個・成果なし」の行になる（N と行の追加は S3）。発射台が受け付ける積荷はこの表に載っているものだけ。
- **軌道到着サービスを置く。** サービスは2つの口を持つ。成果の先読み（`PreviewArrivalOutputs`）は、積荷アイテムと個数から成果を返すだけで、到着として扱わない。軌道到着（`Arrive`）は同じ成果を返し、UniRx で「軌道到着（積荷アイテム・個数）」を流す。S3 はこの通知を購読してケーブル累計を数える（累計の保存は S3）。
- **成果が出力口に入りきるときだけ進める。** 打ち上げ口は、先読みした成果が自分の出力口に入りきるかを、建造（拠点なら衛星の積み込み）を始める前と打ち上げる直前に確かめる。入りきらなければ待たせて理由を UI に出す（機械の出力詰まりと同じ形）。打ち上げ後に成果を預かる保留は持たない。
- **初打ち上げ済みかはワールド単位の状態として持つ。** 状態の持ち主は S2 の打ち上げ側で、セーブに入れる（セーブ形式が変わるため移行ステップを同梱する）。エレベーター拠点はこの状態に関わらない。

## 呼び出し側の線引き

- 打ち上げ口（発射台・エレベーター拠点）が知ってよいのは「サービスがあること・成果を先読みすること・軌道到着を伝えること・返ってきたアイテムを自分の出力口へ入れること」まで。計算データの量・積荷の種類による分岐・レベル換算は知らない。
- サービスは打ち上げ口の出力口を知らない。出力口に入りきるかの判定は打ち上げ口が持ち、先読みの結果を自分の出力口へ書き込まずに試して決める。出力口へ書くのは打ち上げ口自身だけなので、建造を始める前に入りきれば打ち上げ時にも入りきる。打ち上げる直前の判定は、ロード後のスロット構成の変化などへの備えとして残す。
- 発射台が「どの積荷が1便ぶん揃ったか」を判断するときも、1便の個数はマスタの表から引く。発射台に積荷ごとの個数を書かない。積荷1種につき入れ口は1スロットなので、1便の個数はその積荷のスタック上限以下でなければマスタ読込時に止める。1便ぶんの成果が空の出力口に入りきらない積荷は永遠に待つので、これもマスタ読込時に止める（発射台では成果のスタック数をレベル1のスタック上限で数え、`outputSlotCount` と比べる）。

## Considered Options

- 打ち上げ成果を各打ち上げ口のブロックパラメータに持つ: 同じ衛星の量を2か所に書くことになり、S3 の拠点が S2 の値を写す必要がある。不採用。
- 通知だけを用意し、成果の付与は各打ち上げ口が実装する: S3 が「打ち上げ結果の処理は S2 のサービスに持たせ、拠点はそれを呼ぶだけ」を希望しており、量のずれを防げない。不採用。
- 打ち上げ後に成果を打ち上げ口が預かり、預かり分が残る間は次の便を止める（提示して棄却）: サービスに先読みの口が要らない（S3 と一度合意していた）。一方で、満杯でも1便は打ち上がってしまい、裁定「出力が満杯のうちは次の打ち上げを待たせ」の字義と機械の前例（開始前に出力の空きを確かめる）から外れる。預かり分のセーブ・撤去時の返却・マスタ変更時の退避の経路も要る。ユーザーが「入りきる時だけ建造開始」を選んだため不採用。
