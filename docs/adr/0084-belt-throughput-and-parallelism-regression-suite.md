# 0084. ベルトのスループット100%と並列可能性を回帰テストで固定する

日付: 2026-10-18
状態: 採択（シナリオ一覧はユーザーが追記中。確定版は `MyBeltConvSegment/2026-10-17-スループットと並列性の回帰テスト_シナリオ案.md`）

## 文脈

ベルトsegment化は、さまざまな制約のもとでスループット100%と「1 tick が段数一定の map で終わる」並列可能性を達成している。将来、別の人が segment の内部や新クラス（Segment2 等）で仕様を広げたとき、この2つが黙って損なわれることをユーザーは恐れている。特に「下流側から順に更新すれば100%になる」型の実装は、直列段数が伸びると並列化の意味を失い、輪のように順序が定義できない境界で100%を下回る。

## 決定と出所

- テストはクラスを対象にしない。関所1「ブロックの世界」（`CreateServer → 設置 → GameUpdater → 受けチェストの個数`）と関所2「クライアント同期の契約」（FullState / TickDiff / ハッシュの一致）だけを通して測る。
  出所: ユーザー裁定 2026-10-17「ただのsegmentの並列処理テストではだめです。たとえば将来segment2みたいなクラスがつくられて…segmentは旧コードとしてのこされ、それがテストされるだけ、というオチになる可能性があります」
- カタログは A（100%保証）・B（特性値を正確な整数でピン止め）・C（複雑系、期待値は容量グラフの最大流）・D（判別器）。B は「黙って変わらない」ためのもので、値を変える PR は理由を ADR に書く。
  出所: ユーザー裁定 2026-10-17「輪 木→鉄→木 って場合は今でも100%スループットは保証していません、むしろ低下するのが正常」→ 選択「1 正確な個数をピン止め」
- 全シナリオを正順・逆順・ランダム順（固定シード1本）の設置順で回す。
  出所: ユーザー裁定 2026-10-18「正順 逆順 ランダム順にベルコンを設置するシナリオが必要…block設置順によって偶然通る可能性があるため」「ランダム設置順のシード本数 1でいいです」
- 計測開始はすべての受けチェストが2個以上受けた tick。窓は W = 361×8、分岐を含む配置は 361×16。スループットは全受けチェストの合計で判定し、分配の公平さは ±1 の軽い assert。
  出所: ユーザー裁定 2026-10-18「すべての受けチェストが2つ以上うけてから計測開始」「361*8」「分割系でもW=361*16」「分配の公平さも…テストいれたほうがいいな、これは軽くでいい」
- 並列可能性は「段数が網の大きさによらず一定」「段階内の要素順を入れ替えても結果が同じ」「`Parallel.For` でも同じ」「定常 tick のアロケーション0」で測る。時間の閾値は入れない。
  出所: ユーザー裁定 2026-10-18「下流側から順番に更新すれば…100段とかになるとさすがに並列化の意味がなくなるのでダメ」「輪…境界でかならずスループットが100%をしたまわります。もしそこをbufferなどつかって対処して100%になっていればそれは合格」
- マスタは forUnitTest に本番と同じ速度のベルト族（木 1.0 / 鉄 2.222222 / 電気 6.666667 / 高速 10、直線・上り・下り・分岐器）を追加して使う。既存のテストベルト（0.333 等）は残す。
  出所: ユーザー裁定 2026-10-18「forunit側をかえるしかないとおもう」
- 1マスだけ別の歯車網にすることは今の機構ではできない（同種の歯車ベルコンはアイテムで繋がる並びなら必ず歯車でも繋がる）。A12 は「下流 segment の停止→再開」とし、電気ベルト1マスで歯車網を切る。
  出所: ユーザー 2026-10-18「手法はまかせます」→ agent前提（`connectableShapePairs` の `conveyorGearChain <-> conveyorSide`、`BeltGearDrive` の前提コメント）
- A9 の素通し機は専用ブロックでなく、forUnitTest のレシピ「A 1個 → A 1個、処理 1 tick」で作る。
  出所: ユーザー 2026-10-18「テスト用の完全にクリーンな加工機ってできない」→ agent前提（マスタデータの追加だけで済む）
- 実装順: 先に基盤（マスタ追加・シナリオ DSL・A1）を作って動かし、カタログはユーザーの追記後に埋める。
  出所: ユーザー 2026-10-18「テストまずは実装を 私の追記は最後にします」

## 検証範囲

テスト基盤そのものが成果物。A1 が3つの設置順で100%を出し、関所2（複製ハッシュ一致）が毎 tick 通ることを最初の到達点とする。

## 計測結果（2026-10-18、基盤を通した時点。原因は実測、裁定待ち）

カタログ A を forUnitTest の木の歯車ベルト（周期 20 tick）で回した結果。A1（4族×100マス）・A4a/A4b/A5a/A6・A10・A13/A14・A18・A3・A17(3出力全開) は3順とも理論値にちょうど一致した。次の2件は一致せず、Core の挙動変更が要るので `[Ignore]` で保留し、ユーザーの裁定を待つ（出所: 実測。証拠: `uloop run-tests` の失敗メッセージ `sinks=286 sources=287 Expected: 288`、一時診断の tick 列）。

- **F1. 分岐segmentの出口クランプで後続が進行量を失う。** 直線5マス＋分岐マスは1本の6マス分岐segmentに畳まれる（`SameSpeedRunIsFoldedIntoBranch`）。README §1tickの順序 1.「前進させ、出口でクランプする…回収後に後続を追加で前進させない」のとおり、先頭が出口手前 x(<18) で止まると密着した後続も x しか進めず、(18−x) を失う。診断では着荷間隔が 121 tick ごとに 20→21 になり、5776 tick で 286/288（A7・A8a・A8b・A17 1出力）、詰まりのある A17 で 282〜283、A17 3出力全開は 288。チェストから分岐マスへ直接入れる A3（1マス分岐segment、後続なし）は 288 で損失なし。通常segment同士の境界は超過分を持ち越すので損失がない。
- **F2. 合流bufferから機械へ直接搬出すると理論最大を超える。** A5b（左右から合流→前方が直接チェスト）で 2888 tick に 152 個 = 19 tick/個。合流マスの item は段階1で回収され同じ tick の段階3で機械へ渡るため、1マス(360)を 19 tick で通過する。合流→通常ベルト→チェスト（A4a）は 144 で正常。

裁定の選択肢（未提示なので ADR の棄却案には書かない）: F1 は「buffer が空なら先頭の超過分を回収に使い、後続は満額進める」に Core を直して A に残す／現状値を B にピン止めする。F2 は「機械への搬出も次 tick に回して 20 tick/個に揃える」／仕様として許容し B にピン止めする。

## 裁定（2026-10-18）

- F1 は Core を直す: `BeltBufferedSegment.CollectForBuffer` は「buffer が空で先頭がこの tick で出口に届くなら、先頭を回収して後続は満額進める（通常 segment の搬出成立と同じ `Advance(true)`）。満杯のときだけ出口でクランプする」。参照実装 README §1tickの順序 1.「回収後に後続を追加で前進させない」とは異なる（README の更新はユーザー）。
  出所: ユーザー裁定 2026-10-18「F1は Core を『buffer が空なら先頭の超過分を回収に使い、後続は満額進める』に直す方向で修正を」
- F2 は許容し、A5b を B7 としてピン止めする（当初 2888 tick に 152 個。窓を 2880 に丸めた後は 151 個、下記「判定の見直し」参照）。
  出所: ユーザー裁定 2026-10-18「F2は許容します」
- 「100%」の判定は、窓の開始を供給の tick に揃えたうえで **供給の受け入れ個数 == floor(W/P)** と **保存則（供給 − 受け == ベルト上の増減）** の2本で行う。受けの合計は経路や buffer の位相で ±1 揺れる（A17 3出力全開で 290/288 を観測）ので、受けの合計そのものは厳密一致の対象にしない。分配は ±1。
  出所: agent前提（実測: 修正後の A17 3出力全開 sinks 合計 290・sources 289、窓 5776 は周期 20 の倍数でない）。ユーザーの「正確な個数」「全受けの合計で判定」の意図は「供給が1個も止まらない・1個も消えない」として保つ
- 修正後: Belt/Transport のサーバーテスト 472 件 pass（A7・A8a・A8b・A17 全18件を含む）。

## 判定の見直し（2026-10-18、ユーザー裁定）

- 末端のアイテム数だけでは segment のスループットを見ていない。配置ごとに「定常状態で100%でなければならない segment」を事前に決めて `Watch(マス)` で指定し、その segment の搬出数が窓（周期の倍数）の間に W/P にちょうど一致することを要求する。定常状態は「全受けが2個以上受け、監視 segment が2個以上搬出した tick」とし、何 tick 目かの厳密性は求めない（時間的猶予）。末端カウントで足りる配置はそのまま。
  出所: ユーザー裁定 2026-10-18「ほしいのはsegmentのスループットが100%。…100%稼働しないといけないsegmentってのがあるはずなので、それを事前にわれわれがもとめ、そこが100%になっているかいないかを見る…tickの厳密性まで求めると大変なので、そこは時間的猶予をかませてok」
- 搬出は Core に口を足さず、tick ごとに `CaptureItems` と buffer の個体IDを見て「前の tick にいて今いない」で数える（`Tests/Util/Throughput/BeltSegmentExitCounter`）。
- 窓は 361×8 / 361×16 を全周期（2・3・9・20）の公倍数 180 の倍数に丸めて 2880 / 5760。周期の倍数なら位相に依らず W/P がちょうど成り立つ。B7 のピン値は 2880 tick で 151（2880/19）。
  出所: agent前提（厳密一致を位相なしで成立させるため）

## 計測結果 2（2026-10-18、A9・A11・A12・A16 実装時。原因は実測）

- A9（素通し機）・A16（輪＋横入れ合流＋分岐出口）は3順とも監視 segment 100%。A16 は合流→分岐の区間が W/P、供給は交互の片側ぶん（W/P/2）、保存則一致。
- A9 は機械がレシピを選ぶまで何も受け付けない（ADR 0042）ので、テストが素通しレシピを選んでから流す。機械スロット内のアイテムはベルト上に数えないので、保存則の代わりに機械前後の segment の搬出数で見る。
- **F3. 最速だった風車が落ち始める tick に、網の回転数が1 tick だけ落ちる。** A11 ②（3台→1台）で、燃料を抜いた2台の装填燃料が尽きて減速に入った tick に、網の RPM が 9.8333（減速中の風車の値）になり、ベルト速度が 17 になった（原点 generator の切り替えが同じ tick に起きない）。1 tick の遅れが詰まった列全体に伝わり、窓の個数が 143/144 になる。ユーザー裁定 2026-10-18「時間的猶予をかませてok」に従い、A11 ② は減速が終わるまで 600 tick 待ってから測る。歯車系の挙動なので直すかは別途。
  出所: 実測（診断 `phase2w t=3281 speed=17 rpm=9.8333 genRpm=10.0000`）
- **F4. 等速でも通常segment同士の境界は満杯の下流へ1個ごとに1 tick 待つ。** A12（鉄30RPM=120 → 電気1マス=120 → 鉄）で 2880 tick に 720 個（4 tick/個、理論 960）。README §1tickの順序 4.「空きを全件記録してから前進する」ため、下流の先頭がこの tick に出ていく分の空きは次の tick まで使えず、満杯の下流へは毎回1 tick 待つ。通常→通常の等速境界は歯車網の切れ目（gearDriven の不一致）でしか生じないので、A12 は 720 を特性値としてピン止めし、停止→再開で同じ値へ戻ることを見る。通常→buffer（分岐・合流）と buffer→通常は live の空きを使うので損失なし（A3・A17 は 100%）。
  出所: 実測（`speeds=120,120,120 sources=720 sinks=720 watched=720,720,720`）。下流から順に更新する実装なら消える損失だが、それは §3 の並列可能性と引き換えになる（ユーザーが避けると明言）。buffer を境界に置く設計変更は別途
- 燃料式風車の装填燃料は負荷率に比例して燃えるので、燃料を抜いてから減速に入るまで最大 180 tick（負荷率 0.33）。A11 ③ は「速度0が30 tick 続く」まで待ってから、累積移動量から求めた搬出数と突き合わせる。

## 裁定 F3（2026-10-18）

- 歯車網の回転数は RunTick で原点を選んだ時点の原点 RPM を `GearNetworkRuntimeState.OriginRpm` に凍結し、`TryResolveRotation` はその値から導出する。tick の順序（需要 → 需給・原点選定 → 燃料消費）と計算回数は変えない。同じ tick の燃料消費で原点の `GenerateRpm` が下がっても、その tick の網は RunTick が需給計算に使った値で回り、変化は次 tick の RunTick で原点交代として反映される。
  出所: ユーザー裁定 2026-10-18「3でいいとおもうが、だからそもそも最速rpmのgeneratorを歯車のtickの最初にやればいいってことでしょ？」。「燃料消費の後に原点だけ選び直す」案は、RPM が変われば要求動力も変わり需給を回し直す必要があるためユーザー指摘で棄却
- 回帰: A11 ② は2台の燃料を抜いてから減速が終わるまでの全 tick でベルト速度が 18 のままであることを要求する。

## 裁定 F3 追記: 電気→歯車モーター単独の網（2026-10-18）

- 旧コード（原点の `GenerateRpm` を生で読む導出方式、2458377c7 以降）では、電気→歯車モーター `ElectricToGearGeneratorComponent` 1台だけで回す歯車網は、ブロック更新・ベルト搬送の時点で常に RPM 0 を読んでいた。モーターは歯車 tick 末尾の `ConsumeGeneratorTick` で 1 tick 分のバッテリーを使い切り `GenerateRpm` を 0 に戻すため。master にも同じ行がある（電力 tick 一元化 806c13630 以降）。既存テストはモーター自身の `GenerateRpm` しか見ておらず検出されていなかった。
  出所: 実測（旧コード: モーター→木の歯車ベルト10マス 300 tick で受け 0 個、モーター→歯車機械 受け 0 個。新コード: 67 個 / 70 個）
- 原点 RPM の snapshot（`GearNetworkRuntimeState.OriginRpm`）でこれも同時に解消する。電力 tick で満充電 → 歯車 tick の RunTick で原点に選ばれ需給確定 → 以降その tick の読みは定格、という 1 tick バッテリーの意図どおりの挙動になる。
  出所: ユーザー裁定 2026-10-18「副作用了解 修正実装をおねがい」（副作用: 電力不足時のモーターは脈動する、燃料風車の出力変化は次 tick 反映、過負荷チェックは RunTick と燃料消費の間なので不変、クライアント表示も同じ導出を通る）
- 歯車 tick の需要について（調査結果）: 需要 = Σ 要求トルク(その歯車の RPM) × RPM で、RPM は最速 generator の `GenerateRpm` × 歯数比。generator にドループは無いので需要は RPM が決まれば供給量と無関係に確定し、供給不足なら網ごと停止（部分供給なし）。歯車→電気のバッテリーは消費者で要求倍率が前 tick の不足量で決まるため tick 内の循環は無い。`GearDemandSnapshot` は全消費者を固定 (有効, 1.0) で返す置き場所で、可変部分は `GearEnergyTransformer._torqueRequestRate`。
- 回帰: `BeltThroughputMotorTest` A19a（モーター→木の歯車ベルト10マス、60 RPM で速度 108・周期 4、3順 100%）、A19b（モーター→ベルト3→素通し機→ベルト3、3順 100%）、`ElectricToGearGeneratorTest.MotorAloneKeepsConsumersTurningAfterTheGearTick`（tick 末尾でモーターの `GenerateRpm` は 0 だが `CurrentRpm` は定格、噛み合う軸も回る）。テスト mod の小歯車は overloadMaxRpm 10 で 60 RPM だと破断するので軸を使う。
