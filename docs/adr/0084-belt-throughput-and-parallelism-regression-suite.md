# 0084. ベルトのスループット100%と並列可能性を回帰テストで固定する

日付: 2026-10-18
状態: 採択（シナリオ一覧はユーザーが追記中。確定版は `MyBeltConvSegment/2026-10-17-スループットと並列性の回帰テスト_シナリオ案.md`）

## 文脈

ベルトsegment化は、さまざまな制約のもとでスループット100%と「1 tick が段数一定の map で終わる」並列可能性を達成している。将来、別の人が segment の内部や新クラス（Segment2 等）で仕様を広げたとき、この2つが黙って損なわれることをユーザーは恐れている。特に「下流側から順に更新すれば100%になる」型の実装は、直列段数が伸びると並列化の意味を失い、輪のように順序が定義できない境界で100%を下回る。

## 決定と出所

- テストはクラスを対象にしない。関所1「ブロックの世界」（`CreateServer → 設置 → GameUpdater → 受けチェストの個数`）と関所2「クライアント同期の契約」（FullState / TickDiff / ハッシュの一致）だけを通して測る。
  出所: ユーザー裁定 2026-10-17「ただのsegmentの並列処理テストではだめです。たとえば将来segment2みたいなクラスがつくられて…segmentは旧コードとしてのこされ、それがテストされるだけ、というオチになる可能性があります」
- カタログは A（100%保証）・B（特性値を正確な整数でピン止め）・C（複雑系、期待値は容量グラフの最大流）・D（判別器）。B は「黙って変わらない」ためのもので、値を変える PR は理由を ADR に書く。
  出所: ユーザー裁定 2026-10-17「輪 木→鉄→木 って場合は今でも100%スループットは保証していません、むしろ低下するのが正常」→ 選択「1 正確な個数をピン止め」
- 全シナリオを正順・逆順・ランダム順（固定シード1本）の設置順で回す。
  出所: ユーザー裁定 2026-10-18「正順 逆順 ランダム順にベルコンを設置するシナリオが必要…block設置順によって偶然通る可能性があるため」「ランダム設置順のシード本数 1でいいです」
- 計測開始はすべての受けチェストが2個以上受けた tick。窓は W = 361×8、分岐を含む配置は 361×16。スループットは全受けチェストの合計で判定し、分配の公平さは ±1 の軽い assert。
  出所: ユーザー裁定 2026-10-18「すべての受けチェストが2つ以上うけてから計測開始」「361*8」「分割系でもW=361*16」「分配の公平さも…テストいれたほうがいいな、これは軽くでいい」
- 並列可能性は「段数が網の大きさによらず一定」「段階内の要素順を入れ替えても結果が同じ」「`Parallel.For` でも同じ」「定常 tick のアロケーション0」で測る。時間の閾値は入れない。
  出所: ユーザー裁定 2026-10-18「下流側から順番に更新すれば…100段とかになるとさすがに並列化の意味がなくなるのでダメ」「輪…境界でかならずスループットが100%をしたまわります。もしそこをbufferなどつかって対処して100%になっていればそれは合格」
- マスタは forUnitTest に本番と同じ速度のベルト族（木 1.0 / 鉄 2.222222 / 電気 6.666667 / 高速 10、直線・上り・下り・分岐器）を追加して使う。既存のテストベルト（0.333 等）は残す。
  出所: ユーザー裁定 2026-10-18「forunit側をかえるしかないとおもう」
- 1マスだけ別の歯車網にすることは今の機構ではできない（同種の歯車ベルコンはアイテムで繋がる並びなら必ず歯車でも繋がる）。A12 は「下流 segment の停止→再開」とし、電気ベルト1マスで歯車網を切る。
  出所: ユーザー 2026-10-18「手法はまかせます」→ agent前提（`connectableShapePairs` の `conveyorGearChain <-> conveyorSide`、`BeltGearDrive` の前提コメント）
- A9 の素通し機は専用ブロックでなく、forUnitTest のレシピ「A 1個 → A 1個、処理 1 tick」で作る。
  出所: ユーザー 2026-10-18「テスト用の完全にクリーンな加工機ってできない」→ agent前提（マスタデータの追加だけで済む）
- 実装順: 先に基盤（マスタ追加・シナリオ DSL・A1）を作って動かし、カタログはユーザーの追記後に埋める。
  出所: ユーザー 2026-10-18「テストまずは実装を 私の追記は最後にします」

## 検証範囲

テスト基盤そのものが成果物。A1 が3つの設置順で100%を出し、関所2（複製ハッシュ一致）が毎 tick 通ることを最初の到達点とする。

## 計測結果（2026-10-18、基盤を通した時点。原因は実測、裁定待ち）

カタログ A を forUnitTest の木の歯車ベルト（周期 20 tick）で回した結果。A1（4族×100マス）・A4a/A4b/A5a/A6・A10・A13/A14・A18・A3・A17(3出力全開) は3順とも理論値にちょうど一致した。次の2件は一致せず、Core の挙動変更が要るので `[Ignore]` で保留し、ユーザーの裁定を待つ（出所: 実測。証拠: `uloop run-tests` の失敗メッセージ `sinks=286 sources=287 Expected: 288`、一時診断の tick 列）。

- **F1. 分岐segmentの出口クランプで後続が進行量を失う。** 直線5マス＋分岐マスは1本の6マス分岐segmentに畳まれる（`SameSpeedRunIsFoldedIntoBranch`）。README §1tickの順序 1.「前進させ、出口でクランプする…回収後に後続を追加で前進させない」のとおり、先頭が出口手前 x(<18) で止まると密着した後続も x しか進めず、(18−x) を失う。診断では着荷間隔が 121 tick ごとに 20→21 になり、5776 tick で 286/288（A7・A8a・A8b・A17 1出力）、詰まりのある A17 で 282〜283、A17 3出力全開は 288。チェストから分岐マスへ直接入れる A3（1マス分岐segment、後続なし）は 288 で損失なし。通常segment同士の境界は超過分を持ち越すので損失がない。
- **F2. 合流bufferから機械へ直接搬出すると理論最大を超える。** A5b（左右から合流→前方が直接チェスト）で 2888 tick に 152 個 = 19 tick/個。合流マスの item は段階1で回収され同じ tick の段階3で機械へ渡るため、1マス(360)を 19 tick で通過する。合流→通常ベルト→チェスト（A4a）は 144 で正常。

裁定の選択肢（未提示なので ADR の棄却案には書かない）: F1 は「buffer が空なら先頭の超過分を回収に使い、後続は満額進める」に Core を直して A に残す／現状値を B にピン止めする。F2 は「機械への搬出も次 tick に回して 20 tick/個に揃える」／仕様として許容し B にピン止めする。
