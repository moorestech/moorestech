# 地形の見た目データはサーバーが焼いてチャンク配信する（生成はサーバーに閉じる）

マップ生成の目標アーキテクチャとして「**生成はサーバーで完結し、クライアントは結果を表示するだけ**」の線で統一する。ハイトマップが既にサーバー焼き＋TerrainChunkバイナリストリーム（ハッシュ付き）で配信されているのと同様に、スプラット重み（alphamap）と草密度（Terrain detail density）もサーバーがワールド生成時に焼き、同じチャンク配信機構の拡張で渡す。

クライアントに残る責務は「レンダリングの語彙」のみとする:

- レイヤーアドレス → TerrainLayer アセットの解決
- DetailPrototype への prefab 割当（PersonalAssets 依存はここに閉じる）
- 表示用の高さ摂動（R12 の責務分割は維持。摂動は生成でなくレンダリング）

## 背景: 境界の染み出しがバグの発生源だった

PR #1145（5x5マルチタイル化・MapMaking移植復元）は、配置ノイズ・SDF・岩surround等の生成計算をクライアント側に置いた。その結果、51系統レビューで見つかった大物——配置ノイズのタイルローカル座標反復（1km周期）・見た目キャッシュの非冪等性・岩クラスタ情報の転送——は、すべて「生成の一部がクライアントへ染み出した境界」で発生している。サーバーで焼き切れば、このクラスのバグは構造的に消える。

## 岩クラスタの帰結

クラスタは生成側の意図であり、生成が終わったら隠れて mapObject の Transform（位置・回転・スケール）だけで表現されるべき（ユーザー裁定）。鉱脈が既にクラスタIDでなく **AABBという幾何結果**を渡している前例と一貫する。

surround（岩周りの裸地スカート）描画がサーバー焼きへ移れば、`RockClusterInfo` は生成パイプライン内部（`ObjectClusterPlacer` / `ObjectIndependentPlacer`）に完全に閉じ、`MapObjectLayoutMessagePack` の `ClusterId` / `ClusterCenterX/Z`（Key 8〜10）と map.json の必須3キーは転送・永続化ごと削除できる。

### 過渡措置（PR #1145 の扱い）

PR #1145 のクラスタ3キーは**後で消える前提でそのまま通してマージする**。以下は棄却:

- クライアントが岩位置から空間クラスタリング（union-find）で再導出する案 — 後続で捨てる過渡実装になり二度手間
- `clusters` 別テーブルへの正規化 — 同じく消えるものへの投資
- PR #1145 の段階でサーバー焼きまでやり切る案 — レビュー済みコードの大規模やり直し

## 受け入れるコスト

- **転送・セーブ量**: alphamap はレイヤー数分の重み配列（粗い見積もりで byte 量子化 512²×8層 ≒ 2MB/タイル、25タイルで50MB前後＋草密度）。ハッシュキャッシュで2回目以降は差分ゼロだが、マルチプレイ初回同期は重くなる
- **焼き時間の移動**: ワールド生成時にサーバーが視覚分も焼く（現状のクライアント側は初回3.1s/キャッシュ1.3s）
- **移行規模**: PR #1145 で作った Client 側 Visual パイプライン（Splat/Surround/SDF）の計算部分のサーバー移設

## 未解決・移行時の確認事項

- 勾配依存テクスチャを摂動前/後どちらの高さで焼くかは MapMaking 原本の挙動に合わせる（移行時に確認）
- v8 実データで `ClusterId>=0` が 74338件中 **0件**（`useClusterMode: true` が4エントリあるのに）の食い違いは未解明。クラスタ描画経路は実データで一度も動いていない — 調査タスク `moorestech-7pk`
- 移行本体は挙動変更のため着手時に grill-first を通す — 実装タスク `moorestech-pt8`
