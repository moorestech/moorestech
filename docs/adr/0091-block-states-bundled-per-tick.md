# 0091: ブロック状態をtick末尾に1イベントへ束ねて送り、クライアントは座標で振り分ける

## Status
Accepted

## Context
ユーザー原文「ブロック情報をtick単位でまとめて1パケットで送ることをしたい」

windows-desktop の計測（docs/performance/2026-10-22-windows-desktop-low-fps/README.md）では、メインスレッドの78%が受信イベントの処理で、件数は `va:event:changeBlockState` が毎秒約1.7万件だった。今はブロック状態が変わるたびに、座標入りタグ `va:event:changeBlockState:(x, y, z)` で1件ずつ送っている。クライアントは約1.5万個の座標タグをブロックごとに購読している。外箱の読み込み・タグ文字列での配送・ソケット送信が、すべて件数に比例してかかっている。

## Decision
- ブロック状態の変化は、その場で送らずに溜める。tick末尾（操作の適用・`ServerThreadActionQueue` の処理・網の再構築の後、境界ハッシュの前）に、溜めた分を1イベント（ブロック状態の束）にして全員へ送る。変化0件のtickは送らない。出所: ユーザー裁定 2026-10-22 原文「ブロック情報をtick単位でまとめて1パケットで送ることをしたい」→ 選択「外箱を束ねて座標表で振分」、詳細説明のあと「この形で確定」
- クライアントは束を1か所で購読して1回だけデシリアライズし、各件の座標から `BlockGameObjectDataStore` で `BlockGameObject` を引いて状態プロセッサを呼ぶ。座標入りタグの購読は廃止する。WebUI の `BlockInventoryTopic` も同じ振り分け経路から通知を受ける。出所: 同上
- 束の1件の中身は今の `BlockStateMessagePack`（座標＋`Dictionary<string, byte[]>`）のまま。中身の型付き化とパイプの間引きは今回の範囲外。出所: 同上（棄却案として「束ねる＋中身の形式も変える」「束ねる＋パイプの間引きも」を提示）
- 溜めるときは座標ごとの最新1件へ上書きせず、同じ座標の途中の状態も発生順に残す。クライアントは束の順に当てるので、機械の「直前の状態」（`CommonMachineBlockStateDetail.PreviousStateType`）など状態の遷移を見る処理にも、1tick内の変化が全部届く。出所: ユーザー裁定 2026-10-30 原文「残すように修正して」（当初の agent前提「座標ごとに最新1件へ上書き」を差し替え。上書きで tick内の遷移が失われることを説明したうえでの裁定。2026-10-30 のベンチマークでは、上書きのときのブロック状態は 3,212 件/秒）
- 状態がクライアントへ届くのは tick末尾になる（最大1tick弱遅れる）。設置・撤去のイベントは今どおり即時に送る。出所: ユーザー裁定 2026-10-22「この形で確定」（棄却案「状態も即時性を保ってほしい」を提示）
- 完了基準：テストが通り、固定ベンチマークを変更の前後で回して `docs/performance/benchmark/results/` と README の結果一覧に残すこと。数値目標は置かない。出所: ユーザー裁定 2026-10-22 選択「前後を計測して記録する」
- 前回と同じ中身なら溜めない判定（`_lastQueuedPayloads`、`QueueChangedState`）は、溜める前に行う。`RequestBlockState`（初期状態の問い合わせ）の応答は判定をせずに強制で溜め（`QueueStateForInitialPull`）、同じtickの束に載せる。出所: agent前提（既存の ChangeState / ForceChangeState の契約を維持）
- 撤去・設置のときは、その座標に溜めた分を全部捨てる。同じtickに撤去→再設置しても、古いブロックの状態が新しいブロックに届かない。出所: agent前提（既存の OnBlockRemove / OnBlockPlace による差分記録の掃除と同じ理由）
- クライアントで座標に該当するブロックが無い件（撤去直後など）は読み飛ばす。状態プロセッサの例外は隔離しない（旧購読ラムダの try-catch は移さず外す。AGENTS.md の外部境界に当たらないため。例外はネットワーク受信側の購読者単位の隔離でログされ、その束の残りの反映は止まる）。出所: シミュレーター予測（確信高）→前提宣言 2026-10-27（moores-code-review D4。当初の agent前提「try-catch を移設」を差し替え）
- 送り口は前例（ベルト・列車の束）どおり購読で駆動する。`IWorldBlockUpdateEvent.OnTickEndStatesCommitted` を `MasterTickUpdater` が tick末尾（網の再構築の後・境界ハッシュの前）で発火し、`ChangeBlockStateEventPacket` が購読して送る。出所: ユーザー裁定 2026-10-27 選択「前例どおり購読にする」（moores-code-review D5。当初の agent前提「MasterTickUpdater から明示呼び出し」を差し替え）
- サーバーは差分判定用に作ったバイト列を束に継ぎ合わせ、シリアライズを1件1回にする（送るバイト列は変えない）。出所: ユーザー裁定 2026-10-27 選択「サーバーだけ継ぎ合わせる」（moores-code-review D2）
- クライアントの束の振り分けは EditModeInPlayingTest で CI に守らせる。出所: ユーザー裁定 2026-10-27 選択「CIテストを1本足す」（moores-code-review D1）
- セーブ形式は変わらない。バグ報告のリプレイが記録するのはクライアントからの受信パケットだけなので、リプレイにも影響しない。出所: agent前提（ReplayRecordedPacketEntry のコード確認）

## Considered Options
- 束ねるが、クライアントは座標タグ購読のまま（受信後に束をほどいて既存タグで配り直す）— 棄却。タグのハッシュ計算を含む配送が残るため。出所: ユーザー裁定 2026-10-22
- 束ねる＋中身の形式も変える／束ねる＋パイプの間引きも — 棄却（今回の範囲外）。変更が大きいか、ゲーム挙動の別裁定が要るため。出所: ユーザー裁定 2026-10-22
- 状態の即時性を保つ別の束ね方 — 棄却。tick末尾までの遅れを許容したため。出所: ユーザー裁定 2026-10-22

## Consequences
- 件数に比例していた外箱の読み込み・タグ配送・送信の回数が、tick数（20回/秒）まで減る見込み（推測。計測で確かめる）。
- 1ブロックごとの中身のデシリアライズ（`BlockState.Deserialize`）、状態プロセッサ本体、パイプが毎tick全件変わる件数は残る。
