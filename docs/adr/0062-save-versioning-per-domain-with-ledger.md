# 0062. セーブの版はドメインごとに持ち、配布単位ごとの台帳で変換の順序を決める

日付: 2026-09-17
状態: 採択・未実装（ADR 0061 の「worldVersion を上げる形式変更ごとに V(n)→V(n+1) の変換ステップ」を、実装時に本ADRの方式へ置き換える。PR #1359 の版1本の方式は前史として残す。PR #1359 は 2026-09-17 に master へマージ済み）

## Context

ADR 0061 でセーブ互換をロード時マイグレーション連鎖で保つと決め、PR #1359 が実装した。版はセーブ全体で整数1つ（`worldVersion`）、ステップはセーブ全体の `JObject` を受け取る。

この形に2つの不満が出た。

1. ブロックのコンポーネント1つが保存形式を少し変えただけで、セーブ全体の版が上がり、`Game.SaveLoad` に置かれたステップがブロック内部のJSONの形を知ることになる。書き出しは各ドメインが自分で担っているのに、変換だけ `Game.SaveLoad` が抱えている。
2. mod がブロックに留まらないセーブデータを持つとき、バニラだけが管理する `worldVersion` には乗れない。mod の作者は `WorldSaveAllInfo.CurrentVersion` を上げられず、複数の mod が同じ整数を取り合うこともできない。

調査で確認した事実:

- 復元処理（`WorldSaveDataRestorer.Restore`）に他ドメインのJSONを読む箇所は無い。あるのは実行時オブジェクトの復元順の制約と、IDによる参照だけ。
- ドメインをまたいで中身を解釈する形式変更は、履歴上ほぼ無い。約2年半・形式に触れた約40件のうち1件（コミット `2826edf7a`: レール接続情報をブロックの state からトップレベルの `railSegments` へ移動）。
- ブループリントの `settings` はブロックの state と同じ形式ではない。`IBlockBlueprintSettings` が専用のキー（`BlueprintSettingsKey`）と専用のJSONクラスを持つ別形式。
- ブロックコンポーネントの `SaveKey` の大半は `typeof(...).FullName` で、クラス改名や名前空間の移動でセーブ上のキーが無言で変わる。
- mod がセーブへ独自データを載せる口は無い（`MoorestechServerModEntryPoint` にセーブ関連の登録が無く、`WorldSaveAllInfo` は型付きで未知のトップレベルキーを捨てる）。`ModMetaJson` に対応ゲーム版の欄は無く、ゲーム自体にも意味のある版番号が無い（Unity の `bundleVersion` は `0.1`）。
- マスタ欠損の除去器は、既にセクション単位に分かれている（`IMissingMasterSectionPruner`。world の除去結果を `RemovedWorldBlockPositions` として依存側へ渡す `IRemovedBlockAwareSectionPruner` もある）。

## Decision

- **版はセーブ全体で1つではなく、ドメインごとに持つ。セーブ直下に、ドメインIDから版への対応表（版の表）を置く。ブロック1個ごとに版は埋めない。**
  出所: ユーザー裁定 2026-09-17 原文「ブロック内部のパーサーがちょっと変わっただけで、ワールド全体をマイグレーションするというのは過剰だから、責務を分けて、ワールド全体で管理しないといけないところはワールド全体で管理、個別で管理すべきところは個別ドメインで管理するようにするってのがどうか？という話です。つまり、統一されたバージョンをもつのではなく、個別ドメインごとに個別のバージョンをもつってことです」「modはブロックだけでなく、WorldSaveAllInfoに置くためのよりゲーム全体に影響するセーブデータを管理したい、という需要が間違いなく発生します。このような時、バニラだけで管理しているworldVersionの問題が浮上します。」
  版の表をセーブ直下に1つ置きブロックごとに埋めない点は agent前提（変換はロード前段で一括に終わるため、同じドメインのデータは1つのセーブ内で必ず同じ版になる）

- **ドメインの単位は、ブロックのセーブデータがコンポーネントの `SaveKey` 1つ、トップレベルのセクションがJSONキー1つ。`currentTick`・`randomState`・`backfilledFields` 等のスカラ値は `Game.SaveLoad` が所有する外枠ドメイン1つにまとめる。**
  出所: ユーザー裁定 2026-09-17 原文「何ならList<BlockJsonObject> や List<PlayerInventorySaveJsonObject>も「個別ドメイン」と捉えて、それぞれの責務でマイグレーションしてもらう、とかのほうが良いような気もする」→ 質問「ブロックのセーブデータは、どの単位を1ドメインにしますか？」→ 選択「SaveKey単位」／質問「トップレベルのセクションは、どうドメインに区切りますか？」→ 選択「JSONキー1つで1ドメイン」（[[2026-09-17-セーブのドメインはSaveKeyとトップレベルJSONキーを単位にする]]）
  棄却案: ブロック種別(blockType)単位／world全体で1ドメイン／所有アセンブリ単位でまとめる

- **ブループリントの設定は `BlueprintSettingsKey` 1つで1ドメインとし、設定を出すコンポーネント側がキーごとに版と変換を持つ。ブループリント側（`blueprints` ドメイン）は一覧と配置情報の形だけを管理する。**
  出所: ユーザー裁定 2026-09-17 質問「ブループリントの設定の版は誰が持つか」→ データ構造の例と入れ物ドメインの仕組みを提示 → 確認「案1の『設定を出すコンポーネント側がキーごとに版と変換を持つ』でよいですか」→ 回答「はい」（[[2026-09-17-ブループリント設定の版は設定を出すコンポーネントが持ち入れ物ドメインで値を列挙する]]）
  棄却案: 設定の中身の変更もブループリントのドメインの版と変換に集約する

- **他のドメインの値を内側に抱えるドメイン（world はブロックの state を、blueprints はブロックの設定を抱える）は「入れ物ドメイン」とし、その持ち主が「自分の中から、あるキーの値を全部列挙する方法」を実装する。共通の枠組みは入れ物に値の列挙を頼み、受け取った値をステップへ渡して結果を戻すだけで、入れ物の中の構造は知らない。ブループリント専用の仕組みは作らない。**
  出所: ユーザー裁定 2026-09-17 原文「てことは、ブループリント専用の枠組みになるってこと？」→ 入れ物ドメインを汎用の仕組み1つとして提示（world と blueprints が同じ interface を実装）→ 回答「はい」

- **ブループリントの設定は、JSON文字列からオブジェクトへ展開して、ブロックの state と包み方を揃える。展開の変換は新方式の最初のステップの1つとして書き、`IBlockBlueprintSettings` の `GetBlueprintSettingsJson`／`ApplyBlueprintSettingsJson` は文字列からオブジェクトへ変えて全実装を書き換える。**
  出所: ユーザー裁定 2026-09-17 質問「ブループリントの設定を、JSON文字列からオブジェクトへ展開するか」→ 確認「案1（オブジェクトへ展開して揃える）でよいですか」→ 回答「ok」（[[2026-09-17-ブループリントの設定はJSON文字列からオブジェクトへ展開しstateと包み方を揃える]]）
  棄却案: 文字列のまま残し、設定のステップが自分でパースして書き戻す

- **配布単位（バニラ本体、各 mod。まとめて更新される単位）の内側では、変換の順序を追記専用の台帳で決める。台帳はステップを適用順に並べた列で、末尾にしか足さない。ドメイン別の版は台帳から導出されるラベルで、順序を決める情報ではない。**
  出所: ユーザー裁定 2026-09-17 原文「いや、あり得るのであればちゃんとサポートしたい。そのうえで、ドメインごとのバージョンを保持しつつ、全順序やマイグレーションの順番等もサポートするためにはどうしたら良いかな」→ 台帳方式をバニラ内・mod ありの具体例つきで提示 → 回答「良さそう」
  棄却案: 版をドメインごとに完全に独立させ、ドメインをまたぐ変換は禁止する／またぐステップに相手ドメインの版の前提を宣言させ、枠組みが依存を解いて順序を決める

- **ステップは、自分が版を上げるドメインを宣言し、そのドメインの部分木だけを受け取る。ドメインをまたぐ変換は、複数のドメインを同時に上げる1つのステップとして書き、宣言した全ドメインの部分木を受け取る。**
  出所: ユーザー裁定 2026-09-17 同上（台帳方式の提示に含めた。例: レールの state と `railSegments` を両方受け取り両方の版を上げるステップ）→ 回答「良さそう」

- **配布単位の間は、依存の向きに沿って処理する。バニラの台帳を最新まで流してから mod の台帳を流す。別の mod を拡張する mod は本体 mod への依存を宣言し、本体 mod の台帳の後に流れる。後から流れる側が見る相手のデータは、いま入っている相手の現在の形だけ。バニラのステップは mod のデータに触らない。**
  出所: ユーザー裁定 2026-09-17 原文「いや、あり得るのであればちゃんとサポートしたい。…」→ mod ありの具体例で提示 → 回答「良さそう」。拡張 mod の依存宣言と順序は、下の書き込み裁定の復唱で提示し、否定されなかった解釈（agent前提に近い。明示の承認は書き込みの可否に対してのみ）
  理由: バニラと mod、mod と mod は別々の順番で更新されるため、同じ版の組へ至る経路がプレイヤーごとに違う。「変換が書かれた当時の相手の形」を見せる方法は原理的に無い。

- **mod のステップは、対象のドメインを宣言すれば、別の mod のドメインにもバニラのドメインにも書き込める。宣言していないドメインには手が届かない。相手のデータの形を保つ責任は、書き込む側の mod の作者にある。書き込みで相手のデータが壊れた場合は、相手の復元か次の変換が失敗した時点で、理由を付けてロードが止まる。**
  出所: ユーザー裁定 2026-09-17 質問「mod が、別の mod のセーブデータを書き換えてよいか」→ 回答「3。特定のmodを拡張するmodをサポートするため」（案3: 対象と順序を宣言すれば認める）／質問「バニラを拡張する mod にも、同じ規則でバニラのドメインへの書き込みを認めますか」→ 原文「許す。極力modderに寛容にする」（[[2026-09-17-modは宣言すれば別のmodとバニラのドメインへ書き込める]]）
  棄却案: 書き換えられるのは自分のドメインだけにする（バニラ・別 mod のデータは読み取り専用）／本体 mod が公開した契約の範囲でだけ書き込みを認める／mod 同士は認めるがバニラへの書き込みは認めない
  改訂: 本インタビューの先の段で出た「mod が読めるバニラのデータは読み取り専用」を、この裁定で「宣言すれば書き込める」に改める。

- **mod 同士の順番が宣言から決まらないときも、ロードは止めない。互いに依存を宣言していない mod が同じドメインに書き込む場合も、依存の宣言が循環している場合も、決まった規則（mod ID の順など。同じ mod の組み合わせなら毎回同じ順番）で順番を強制的に決めて続行する。循環で満たせなかった宣言は警告として出す（表示方法は別途検討）。実際に壊れた場合は、問題が起きた時点で止まる。**
  出所: ユーザー裁定 2026-09-17 質問「mod 同士の順番が決められないとき、どうするか」（場面A: 依存宣言なしで同じドメインに書く／場面B: 依存宣言の循環）→ 原文「場面Bは決定論的に強制的に順番を決める」→ 復唱「場面A、場面Bとも、ロードは止めません。…違っていたら言ってください」→ 訂正なし（[[2026-09-17-mod同士の順番が決まらないときは決定論的に順番を強制して続行する]]）
  棄却案: 依存の宣言が循環しているときは理由を出して止める（agentの推薦）／プレイヤーに優先順位を選ばせて続行する

- **ステップが失敗したときの理由には、そのドメインへの書き込みを宣言している配布単位の一覧を含める。**
  出所: agent前提（書き込みを認めると、バニラや本体 mod の変換の失敗が自分の不具合か他の mod のせいかをすぐに切り分けられなくなる。AGENTS.md「fail-closedの経路は理由を開発者が読めるログへ必ず出す」）

- **mod は、対応するゲームの版の範囲を mod 全体で宣言する。比べる相手としてゲームに版番号を新設しビルドに焼き込む。宣言の範囲外でもロードは止めず、警告を出すだけにする。**
  出所: ユーザー裁定 2026-09-17 原文「このmodがサポートするのはver.いくつまで、というところを明示的に示しておけば、この問題も生まれづらいんじゃないか？それでmodのロードをブロックする必要はないと思う。ただ、警告としてUI上に表示する、（このやり方は別途検討）みたいな機能があると良い」→ 確認「版の上げ方の規則は別途決める前提で、案1（ゲームに版番号を新設）で進めてよいですか」→ 回答「ok」（[[2026-09-17-modの対応版はゲームに新設する版番号に対して宣言し警告にだけ使う]]）
  棄却案: バニラの台帳の長さを版として使う／版番号と台帳の長さの両方を宣言に使う

- **ロードを止めるのは、実際に問題が起きたときだけ。止める: mod のステップが失敗した・例外を投げた／セーブの mod データが mod の知る版より新しい／バニラの未来版・バニラのステップ失敗。止めない: ゲームの版が mod の宣言範囲の外（警告）／mod が入っていない（その mod のデータと版の表を触らずに運ぶ）。**
  出所: ユーザー裁定 2026-09-17 原文「問題が発生するまでは基本的にロードOK、問題が発生したら止める、見たな思想でいたい。ゲーム側のverだけが上がっても、mod側としては問題ないケースがほとんどだと思うから、そうなってる？」→ 状況別の扱いの表を提示 → 回答「良さそう」
  棄却案: mod のステップ失敗時に mod のデータを脇へ退避してワールドは続行する

- **台帳に無い版の組を持つセーブ（feature ブランチのビルドで作った開発者の手元セーブ）は、台帳を先頭から走査して「対象ドメインが全部まだ変換前なら流す・全部変換済みなら飛ばす」で進める。止めるのは、複数ドメインを同時に上げるステップが片方だけ変換済みのときだけ。**
  出所: ユーザー裁定 2026-09-17 確認「流せるものは流し、矛盾したときだけ止めるで進めてよいですか」→ 回答「ok」（[[2026-09-17-台帳に無い版の組のセーブは流せるステップを流し矛盾したときだけ止める]]）
  棄却案: 台帳に無い組は即止める／適用済みステップ名もセーブに記録する

- **mod が持つ、ブロックに属さないセーブデータは、セーブ直下の `modData` の下の mod ID 別の置き場に入れる。mod の独自ブロックの state は、これまで通り world のブロックの中に SaveKey で入る。**
  出所: ユーザー裁定 2026-09-17 確認「形A（mod専用の置き場を1つ作る）で進めてよいですか」→ 回答「ok」（[[2026-09-17-modのセーブデータはmodData配下のmod ID別の置き場に入れる]]）
  棄却案: mod がトップレベルに自由にキーを足す

- **mod に「バニラは変えない」と約束する参照キーは、ブロック位置・マスタのGUID・ブループリントのGUID・レールノードのGUIDの4つ。`BlockInstanceId` は約束しない。約束を破る変更は mod への破壊的変更として告知する。**
  出所: ユーザー裁定 2026-09-17 確認「案1（位置とGUID類だけを約束する）で進めてよいですか」→ 回答「ok」（[[2026-09-17-modに約束する安定参照キーは位置とGUID類に限りBlockInstanceIdは含めない]]）
  棄却案: `BlockInstanceId` も含めて全部を約束する

- **mod を外していた間に指す先が無くなった参照（撤去されたブロック、マスタから消えたアイテム等）の後始末は、mod に任せる。mod が自分のデータを読み込むときに検証して捨て、直せなければ失敗してロードが止まる。ゲーム側は、外していた間の変更・除去の履歴を保証しない。**
  出所: ユーザー裁定 2026-09-17 質問「mod を外していた間に起きた変化を、誰が面倒見るか」→ 確認「案1（mod に任せる）でよいですか」→ 回答「おｋ」
  棄却案: ゲーム側が、mod を外していた間の変更・除去の履歴をセーブに残し、入れ直した mod が追随できるようにする
  理由: 指す先が無くなる事態は mod を外していなくても起きる（プレイヤーがブロックを撤去する）ので、mod はどのみち扱えなければならない。マスタから消えたものは除去器が退避した実体（`pruned`）が手がかりになる。

- **いまの `worldVersion` は「セーブの入れ物の形式の版」として残す。2から3への変換が、版の表を足す移行ステップになる。それ以降は、版の表や `modData` の置き場など入れ物の形を変えるときだけ上げる。いまの旧連鎖の仕組みは、入れ物用の連鎖としてそのまま残る。ロード時は整数を1つ読めば、版の表の読み方が確定する。**
  出所: ユーザー裁定 2026-09-17 質問「版の表そのものの形が変わるときの版を、どこに持つか」→ 回答「1で」（案1: いまの worldVersion をこの役割で残す）（[[2026-09-17-worldVersionはセーブの入れ物の形式の版として残す]]）
  棄却案: 特別な版を設けず、版の表の中の外枠ドメインの版で管理する

- **進め方: PR #1359 は版1本の方式のまま先にマージする。新方式への移行は変換ステップ1本で行う（`worldVersion` を2から3へ上げるステップで、全ドメインを版1とした版の表を足す）。ロード時はまず入れ物用の連鎖で `worldVersion` を最新まで上げてから、版の表による変換に入る。V1→V2 のステップはその連鎖の中に前史として残す。実装はバニラの枠組みが先、mod 対応が後。ただし版の表の形と `modData` の置き場は最初から mod を前提にした形で作る。**
  出所: ユーザー裁定 2026-09-17 確認「この3点でよいですか」→ 回答「はい」（[[2026-09-17-ドメイン別の版への移行はPR1359のマージ後に変換ステップ1本で行いバニラの枠組みを先に作る]]）

- **変換はロード前段で全部終わらせる。全ドメインの未来版の判定と変換を終えてから復元に入り、コンポーネントの読み込み処理の中で版を見て分岐する形にはしない。版の読み取り・未来版の拒否・台帳の整合検証・原本の退避は共通の枠組み（`Game.SaveLoad`）が持ち、ドメインが出すのは「どこを・どの版から・どう書き換えるか」だけ。**
  出所: agent前提（PR #1359 の `SaveLoadPreparer` の構造の維持。復元の途中で未来版や変換失敗に出会うと fail-closed が成立しない。moorestech-principles「汎用基盤にドメイン語彙を持ち込まない」）

- **mod のステップに渡す部分木は、枠組みが複製して渡し結果を差し戻す。mod のステップの呼び出しは外部境界として隔離する。**
  出所: agent前提（`JToken` は `Parent`・`Root` を辿れるので、部分木を渡すだけではセーブ全体に手が届く。AGENTS.md の try-catch 例外規定「外部境界の隔離目的に限り使用可」）

- **ドメインの登録は interface の実装で行う。述語やコールバックは渡さない。**
  出所: agent前提（AGENTS.md「`Func<>`の使用は禁止」。前例は `IMissingMasterSectionPruner`）

- **前提作業として、`SaveKey` を文字列定数へ固定する（現在の `FullName` の値をそのまま写すので既存セーブは壊れない）。セーブに載る全クラスのJSONの形を期待値と比べるスナップショットテストを入れ、形が変わったのに版を上げていない状態をPR時点で落とす。台帳の各位置の見本セーブが最新までロードできる通しテストを持つ。**
  出所: agent前提（ドメインIDは版の表のキーになり永久に変えられない。版の上げ忘れは、版を分けても同じ形で起きる）

- **未裁定（本ADRでは決めない）: 警告の表示方法、ゲームの版番号の上げ方の規則、mod の登録口の具体形（`MoorestechServerModEntryPoint` に何を足すか）。**
  出所: ユーザー裁定 2026-09-17 原文「（このやり方は別途検討）」（警告の表示方法）。他2件は agent前提で同じ基準により保留
  参考: 警告の表示は、PR #1359 の除去件数通知（通知カテゴリ `saveMigration`、接続時に1回）が前例になる。

## Consequences

- ADR 0061 のセーブ互換の裁定のうち「worldVersion を上げる形式変更ごとに V(n)→V(n+1) のステップ」が、実装時に「形式を変えたドメインの版を上げ、そのドメインのステップを台帳の末尾に足す」へ変わる。AGENTS.md の例外項・moorestech-save-migration スキル・`.dev-hooks/rules.json` の文言は実装時に書き直す。用語集の「マイグレーション連鎖」の定義も実装時に改める。
- 全順序は配布単位の内側でしか保証しない。mod がバニラや別の mod の過去の形を見ることはできない。
- バニラのステップは、mod に書き換えられたかもしれないデータを受け取る。テスターのワールドでバニラの変換が mod のせいで失敗しうる。バニラの変換の失敗を、バニラの不具合と言い切れなくなる。
- 台帳は並行PRの意図的な衝突点になる。2本のPRが同時に形式を変えると台帳の末尾で git の衝突が起き、後からマージする側は、相手が上げたドメインを自分のステップが受け取っている場合だけステップを見直す。
- 旧形式を読む変換コードは、バニラも mod も削除できない（ADR 0061 の「後から遡って適用できる」裁定を守るため）。
- 版はセーブの外では通じない。セーブの外へ持ち出すデータ（ブループリントの共有等）を作るなら、持ち出す形式に版を埋め込む設計が別に要る。
- 退避のキーが版番号1つから版の組になる。どこかのドメインが上がるたびにセーブ全体の複製が増えるので、世代の上限が要る。
- mod を古い版へ戻すと、その mod のデータが未来版になりワールドが開けなくなる。プレイヤーの逃げ道は「mod を更新する」か「mod を外す」（外せばデータは触らず運ばれ、入れ直せば続きから再開できる）。
- 台帳に無い版の組のセーブで、ブランチごとに中身の違う同番号の変換は検出できない（開発者の手元セーブに限る既知の限界）。
- mod が入っていない間に運ばれたデータの中の参照は、除去器が手を出せない。mod を入れ直したとき、消えたマスタへの参照が残りうる。この後始末は mod の責務とする（上の裁定）。
