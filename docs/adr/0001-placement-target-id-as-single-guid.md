# 設置対象IDを Guid 1本に統一する

設置対象の識別子は種別ごとにバラバラだった（ブロックはマスタGUIDだがWeb契約では実行時BlockId、ブループリントは表示名の文字列、ブループリントコピーツールに至っては識別子が存在しない）。ホットバー割当をセーブに永続するにあたり、この不揃いがそのままセーブ形式に固定されるため、**すべての設置対象を Guid ひとつで識別する**ことに決めた。ブループリントにはGUIDを発行して名前を表示名へ格下げし、ブループリントコピーツールは `buildMenu.yml` の `buildTools` としてマスタ化する。

## Considered Options

- **種別enum＋キー文字列を値オブジェクト化**（現行のentryType/entryKeyの正式化）— 変更は小さいが、ブループリントのキーが表示名のままでリネームに耐えず、種別ごとにキーの意味が違う不揃いが残るため却下。
- **Guidと種別を併記** — ルーティングは速いが、両者が齟齬した値を作れてしまうため却下。

## Consequences

- 設置の向き（スポイトで拾った `PickedDirection`）は設置対象の一部ではなくなり、設置操作中の一時状態に留まる。ホットバー割当は向きを保存しない。
- Guid→設置対象を解決する設置対象カタログを共有アセンブリに1本置く。ブループリントの供給元だけをインターフェースで差し替え（サーバは `BlueprintDatastore`、クライアントは `ClientBlueprintLibrary`）、サーバの割当検証とクライアントのメニュー構築が同じ有効性定義を見る。
- ブループリントの削除・参照APIは名前ベースからGUIDベースへ変わり、同名ブループリントを許容する（`" (2)"` の連番付与は廃止）。
