# ADR 0090: パイプ網の流体量を 1/1000 単位の整数で持ち、Stepper をノードごとに集める形（並列可能）にする

- 日付: 2026-10-24
- 状態: 採択
- 関連: ADR 0088（パイプの tick 差分同期。棄却案「先に固定小数点へ」を本 ADR で採る）、ADR 0089（SoA）、`.decisions/2026-10-24-パイプ網の流体量は1000分の1単位の整数で持ちStepperはノードごとに集める.md`

## 背景
ADR 0088 でクライアントがサーバーと同じ流体計算を回す形にしたが、計算は double のままで、サーバーとクライアントの一致は「同じ CLR で同じ順に加算する」ことに依存していた。加算順が違えば丸めが違い、ハッシュ不一致で同期が止まる。これは並列化（面やノードを分割して別スレッドで回す）を禁じる。レビュー（2026-10-23〜24）でも、受理量を残量から引き算で求めた値が 1 ulp ずれて不一致になる事故が実際に見つかった（`FluidSimNetwork.AddExternal` の `out accepted` 化で修正）。
整数なら加算は順序に依らず、同じ入力から同じ出力が出る。あわせて、今の Stepper は面ごとに両端ノードへ足し込む形（scatter）で、並列に回すと同じノードへの書き込みが衝突する。ノードごとに自分の面を集めて自分だけ書く形（gather）なら、ノード範囲を分けて回せる。
Unity の API レベルは .NET Standard 2.1 で、128 ビット整数（`Int128`・`Math.BigMul(long,long)`）は使えない。中間積が 64 ビットに収まる単位を選ぶ必要がある。

## 決定
- **置き場: 今の PR（ブランチ fix/train-client-tick-slack-pacing）に足す。** 出所: ユーザー裁定 2026-10-24 原文「流体についてdoubleから整数化への許可が早速オリました。この並列化可能な状態への変更を追加したい」→ 選択「今の PR に足す」。棄却案: 今のブランチの上に新しいブランチを切る（レビューと計測表を分けられるが、ユーザーは 1 PR を選んだ）。
- **範囲はパイプ網だけ。** 網の配列（量・容量・面の上限・面の速度・ポートの上限と速度）、Stepper、差分と全量のメッセージ、ハッシュ、パイプのセーブ、クライアントのコピーを整数にする。機械のタンク（`FluidContainer`）・`FluidStack`・レシピ・UI の流体量は double のまま。出所: ユーザー裁定 2026-10-24 選択「パイプ網だけ」。棄却案: ゲーム全体の流体量（変換点は消えるが機械系の全ファイルとマスタの扱いに広がる）。
- **1 単位 = 流体量の 1/1000（ミリ）。型は `long`。** タンク 50,000 は 5,000 万単位。充填率は 2^30 を 1.0 とする整数（`amount * 2^30 / capacity`）で持ち、充填率差 × 圧力スケール（隣接容量の小さい方）の積は 2^30 × 5×10^7 ≈ 5.4×10^16 で 64 ビットに収まる（容量 10^9 単位＝流体量 100 万まで安全）。1 tick に 0.001 未満の流れは 0 に丸まり、その差は均したつもりで止まる。出所: ユーザー裁定 2026-10-24 選択「1/1000（ミリ）」。棄却案: 1/1,000,000（充填率の積が 64 ビットの上限に近く、容量 10 万超のタンクで溢れる）。
- **異種流体が同じ tick に同じ空ノードへ入ろうとしたら、面の番号が小さい方の流体を採り、他の流体の面はその tick 閉じる。** 今の挙動と同じ規則をノードごとに集める形で書く。出所: ユーザー裁定 2026-10-24 選択「面の番号が小さい方を通す（今と同じ）」。棄却案: 流量が大きい方を通す／どちらも通さない（両側が押し続けると永遠に空のまま）。
- **並列実行は入れない。構造だけ並列可能にする。** Stepper の各フェーズを「ノード範囲 [start, end) を受け取り、その範囲の要素だけを読み書きする」関数にし、`Step` はそれを全範囲で順に呼ぶ。スレッドは使わない。範囲を 2 分割して呼んでも全範囲 1 回と同じ結果になることをテストで担保する。出所: ユーザー裁定 2026-10-24 選択「構造だけ並列可能にし、実行は直列のまま」。棄却案: 今回から複数スレッドで実行（5,000 本で 0.2 ms の計算にスレッド起動コストの方が大きい）。
- **境界の丸め（agent前提）。** 機械→パイプ（`AddLiquid`）は `floor(amount × 1000)` 単位だけ受け入れ、端数は機械側に残す（流体は増えも減りもしない）。パイプ→機械（ポートの `Deliver`）は整数単位の量を double で渡し、機械が受け入れた double 量を `ceil` で単位に戻してノードから引く（ノードが引く量 ≥ 機械が得た量。最大 1 ミリが消える側に丸め、増える側には絶対に丸めない）。根拠: `IFluidInventory.AddLiquid` は double のまま残す裁定なので、端数の往復が避けられない。増える側への丸めは無限増殖の口になる。
- **定数の整数化（agent前提）。** `PressureGain 0.12` は `12/100`、`Damping 0.002` は `2/1000`（`v × 998 / 1000`、切り捨てで必ず 0 へ減衰する）。`AmountEpsilon` は廃止し「0 より大きい」で判定する。
- **流量の比例縮小（agent前提）。** `outflowScale`・`inflowScale` の double 配列をやめ、`flux = desired × amount / outflowSum`（切り捨て）のように有理数の掛け割りで求める。面上限 3 万単位 × 量 5,000 万単位 = 1.5×10^12 で収まる。切り捨てなので送り側の残量を超えない。
- **Stepper の構造（agent前提）。** 面の両端ノードへの scatter 加算を、ノードごとの gather に置き換える。網は構築時に「ノード→接続面の一覧（CSR: `NodeFaceStart[]`・`NodeFaceIndices[]`）」を持つ。フェーズ: (1) 面の速度更新（面ごと、読むのは両端ノードの量）、(2) ノードごとに流出希望の合計（接続面とポートを集める）、(3) 面ごとに送り側縮小後の暫定流量、(4) ノードごとに流入合計と「この tick 受け入れる流体」（空ノードは番号最小の流入面の流体）、(5) 面ごとに確定流量（受け側縮小と異種流体の閉面）と速度の書き戻し、(6) ノードごとに確定流量を集めて量と流体 ID を更新、(7) ポートの配達。各フェーズは自分の添字の要素だけに書き、前のフェーズの配列だけを読む。
- **セーブ形式は版 7 へ。** パイプの `amount`・`faceVelocities[].velocity` を整数単位の `amountMilli`・`velocityMilli` に変える。`SaveMigrationStepV6ToV7` が double を ×1000 して最近傍に丸める。`WorldSaveAllInfo.CurrentVersion = 7`。機械のタンク（`FluidContainerSaveJsonObject`）は変えない。
- **クライアント表示（agent前提）。** 水位は `FillRate` を float に直して渡す。WebUI と `FluidMessagePack` は double のままなので、網の整数を `amount / 1000.0` に戻して渡す。

## 結果
- 同じ全量と同じ差分列から、サーバーとクライアントがビット単位で同じ網を得る。どの順・何分割で足しても同じなので、将来ノード範囲をスレッドに配れる。
- 流れの最小単位は 0.001。微小な圧力差は 0 に丸まり、完全な水平化の手前で止まる（表示上の差は小数 3 桁以下）。
- 境界で最大 1 ミリが消える側に丸まる。増える側には丸めない。
- 既存セーブは版 7 へ変換される（amount × 1000 の最近傍）。

## 棄却案
- 全流体量の整数化（ユーザー裁定で範囲外）。
- 1/1,000,000 単位（64 ビットに収まらない積が出る）。
- 流量の大きい方／どちらも通さない の異種流体規則。
- 今回からの並列実行。

## 検証
- 同じ網を全範囲 1 回と、ノード範囲を 2 分割・3 分割して回したときの配列が完全一致する（単体テスト）。
- 既存の `FluidSimulationStepperTest`（保存則・釣り合い・一方向・ポート配達）が整数版で通る。期待値の「±1e-9」は「±1 単位」に置き換える。
- 版 6 のセーブ（double の amount・velocity）が版 7 に変換され、ロード後の網の量が ×1000 の最近傍になる（移行テスト）。
- ハッシュの感度テスト `FluidNetworkStateHashTest` が long 版で通る。
