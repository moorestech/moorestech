# 0072. 配布ビルドに、起動オプションで有効化する遠隔実行（任意C#の実行口）を入れる

日付: 2026-09-27
状態: 採択

## Context

プレイテストのクラッシュ報告（D3D12 デバイスロスト、`docs/research/2026-09-27-playtest-crash-d3d12-device-lost.md`）を RTX 2060 の検証機で再現しようとしたが、垂直同期を外から切れず、報告者の「フレームレート上限なし」の条件を作れなかった。配布ビルドには、実行中の状態を外から読んだり変えたりする手段が無い。uloop（unity-cli-loop）の execute-dynamic-code は Editor 専用で、ビルド後には使えない。

ゲームは Mono で動くため、実行中に C# をコンパイルしてアセンブリを読み込める（前例: `Mod.Loader/ModsResource.cs` の `Assembly.LoadFrom`）。

## Decision

- **遠隔実行は配布ビルドを含む全ビルドに入れる。既定では無効で、起動オプションを付けたときだけ入口を開く。** 検証機で、テスターと同じ Steam の配布ビルドのまま使うため。オプションなしでは待ち受けもコンパイラの読み込みもしない。
  出所: ユーザー裁定 2026-09-27 原文「development版だけでもいいんだけど、なんかコマンドを送ってAIから色々操作したり任意コード実行できるようにする仕組み作れないかな」→ 質問「この遠隔実行の口を、どのビルドに入れますか？（配布ビルドは Release）」→ 選択「B：全ビルドに入れ、既定では無効（起動オプションで待ち受け）」
  棄却案: Development ビルドだけ（`#if DEVELOPMENT_BUILD`）／ゲームに入れず Mod DLL で後付け

- **C# はゲームの中でコンパイルする。** Roslyn（Microsoft.CodeAnalysis 4.14、netstandard2.0。uloop の依存として既にプロジェクトにある）を製品に同梱し、送る側はソース文字列だけを渡す。参照は実行中プロセスの読み込み済みアセンブリで、型は必ずそのビルドと一致する。
  出所: ユーザー裁定 2026-09-27 質問「C# をどこでコンパイルしますか？」→ 選択「A：ゲームの中でコンパイル（Roslyn 同梱・約12MB増）」
  棄却案: 送る側（Mac mini）でビルドの `Managed/*.dll` を参照してコンパイルし DLL を送る

- **入口は既存の Web UI サーバー（Kestrel、`127.0.0.1`）に1本足す。** 起動オプションがあるときだけ登録する。起動ごとにランダムなトークンを作ってユーザーのデータフォルダのファイルにだけ書き、トークンの無い要求は拒否してログに残す（同じ PC のブラウザ上のページからの POST を防ぐ）。
  出所: ユーザー裁定 2026-09-27 質問「外から C# をどこで受け取りますか？」→ 選択「A：既存の Web UI サーバーに入口を足す（トークン必須）」
  棄却案: 専用の待ち受けを新設／ネットワークを使わずファイルで受け渡す

- **既存メソッドへの差し込み用に Harmony を同梱する。** 送った C# から既存メソッドの前後に計測やログを差し込める。起動オプションなしでは一度も呼ばれない。
  出所: ユーザー裁定 2026-09-27 質問「既存メソッドを書き換える仕組み（Harmony）も同梱しますか？」→ 選択「B：同梱する」
  棄却案: 同梱しない（呼び出し・読み書き・リフレクションまで）

- **クラッシュ報告の再現検証（上限なし FPS の耐久テスト）は、遠隔実行の本実装を正規の手順（計画→実装→PR→配布ビルド更新）で作ってから、それを使って行う。** 使い捨ての Mod DLL は作らない。検証は配布ビルドの更新まで止まる。
  出所: ユーザー裁定 2026-09-27 原文「いや、急がず正規ルートを踏む」→ 復唱「使い捨て Mod DLL での耐久テストはやめ、本実装を正規手順で作ってから再現検証する」に「はい」（同日の先行裁定「B：先に使い捨ての Mod DLL で耐久テスト、本実装は並行」を覆す）
  棄却案: 先に使い捨ての Mod DLL で耐久テストし本実装は並行（同日いったん採択後に撤回）

- **遠隔実行が有効だったセッションのプレイ報告・異常終了の報告は、いつもどおり送り、印を付ける。** manifest に有効だった旨と実行したコードの一覧を添え、取り込み側は印付きをテスター報告の集計・自動修正ランの対象から外す。
  出所: ユーザー裁定 2026-09-27 質問「遠隔実行を有効にしたゲームが落ちたとき、クラッシュ報告をどう扱いますか？」→ 選択「A：送るが印を付ける」
  棄却案: 有効時は送らない／区別せず送る

以下はユーザーが「残りおまかせ」とした範囲で agent が決めた前提（出所: ユーザー 2026-09-27「残りおまかせしたいんだけど」への委任。裁定ではない）:

- 送るコードの形は uloop の execute-dynamic-code に揃える（メソッド本体として書き、`return` した値を文字列にして返す。`await` 可）。AI が Editor と同じ書き方で使えるため。出所: agent前提（uloop execute-dynamic-code 同形）
- 実行先は要求ごとに「クライアント」「サーバー」を選ぶ。クライアントは Unity のメインスレッドで順番に、サーバーは同一プロセスの内蔵サーバーの更新スレッドの tick 末尾で実行する（サーバーの状態は更新スレッドが持つため。受信パケットを tick 末尾で適用する `TickEndPacketQueue` と同じ位置）。別プロセス・別マシンのサーバーは対象外。出所: agent前提（`ServerInstanceStartup.cs` の gameUpdateThread・`TickEndPacketQueue` の前例）
- 応答は完了（または非同期の完了）まで待ち、成否・戻り値・例外・実行中に出たログを返す。継続する計測は、コード側で UniTask を投げっぱなしにすれば続き、結果はログで読む。出所: agent前提（WebSocketMessageDispatcher の action ループへ渡す前例）
- 入口はゲーム開始の初期化（Web UI サーバーの起動）から終了まで使える。タイトル画面では使えない。サーバーがまだ無い時点でサーバー側を指定した要求は、理由付きの失敗として返す。出所: agent前提（Web UI サーバーの起動位置 `Client.Starter/InitializeScenePipeline.cs`）
- コードが固まった・状態を壊したときの復旧はゲームの再起動とする。タイムアウトで打ち切る仕組みは作らない（メインスレッドで動くコードは外から止められないため）。出所: agent前提
- 送る側は `scripts/playtest/remote-exec.sh`（ソースファイルかstdinを受け、SSH 越しにトークンを読んで POST し結果を出す1コマンド）とし、検証機（Windows）と Mac のローカル実行の両方に対応する。出所: agent前提（`verify-on-windows.sh` の SSH 経路）
- ワールドを変える検証は、退避したセーブの複製で行う運用とし、仕組みでは縛らない。出所: agent前提
- 本実装の完了条件は、検証機の配布ビルドで (1) 起動オプションありで C# を送って結果が返る (2) Harmony で既存メソッドに差し込める (3) オプションなしでは入口が開かない、を確かめること。出所: agent前提

## Consequences

2026-09-28 追記（ユーザー裁定）: 起動フラグは `--remoteExec` とする。遠隔実行の結果は `Rejected`・`CompileFailed`・`RuntimeException`・`Succeeded` の種別で返す。報告の `remoteExec` は無効時に null、有効時に `ledgerFiles` を持つオブジェクトとし、進行記録も有効印を保持して日次集計から除外する。

- テスターの PC にも Roslyn と Harmony（計約14MB）が入る。オプションを付けない限り読み込まれない。
- 起動オプションを付けた PC では、「トークンを読める人（＝その PC のユーザー権限を持つ人）」が何でも実行できる。オプションはテスターへ案内しない。
- 読み込んだアセンブリは解放されないため、実行のたびにメモリが少しずつ増える。長時間の計測では、遠隔実行自身の増加分を差し引いて読む。
