# ADR 0105: クリーンルームの機械と清浄機の画面は、自分の装置の最終の確率と次のクラスまでの台数を短く出す

- Status: Accepted
- Date: 2026-11-20
- Related: ADR 0104（ダイシングの品質モジュールは個数で逓減しながら効かせる。抽選式を変えた。本 ADR の数字は 0104 より前の式での例で、表示はサーバーの式の結果をそのまま出すので、式が変わっても表示の決まりは変わらない）、ADR 0094（チップ抽選の式。0104 が一部を覆した）、ADR 0101（清浄機のフィルター自動搬入。変えない）
- Supersedes: `.decisions/2026-10-23-部屋の状態は機械と清浄機のUIと壁ホバーに出す.md` の「機械UIの上部に部屋欄（換気回数・清浄機の稼働とフィルター残量）」、`.decisions/2026-10-23-上位チップは下位の代わりに使え抽選の中身は機械UIと研究に見せる.md` の「機械UIにダイ損失率を出す」

## Context

ユーザーの依頼（2026-11-19、逐語）:

```
全てのクリーンルーム関連のUIにクリーンルームの情報が乗っててうざい
自分の装置の確率について書いてほしい
　何がアップしたらどれくらいの確率になるのかUIに書いておいてほしい

フィルターにあと何台おいたらレベルがアップするのか書いておいてほしい

ダイジングの稼働中と非稼働中のUIが違うのと、失敗率と失敗ダイの確立それぞれ乗っててわけわからん。要するに何？失敗のダイって何％なの？？？ってなる
その変のUIなんとかして。何も分からない
```

確認した事実（2026-11-19〜20、コードの読み）:

- 室内の機械（精密切断機・EUV露光式半導体製造装置）の画面は、部屋欄（密閉・クラス・換気回数・清浄機1台ずつの行）と抽選の中身欄を出す。清浄機の画面も同じ部屋欄を出す（`BlockContextSectionsView`・`CleanRoomSectionView`・`CleanRoomYieldSectionView`）。
- ダイシングの抽選の中身欄は「品質モジュールTier／ダイの損失率／Lv別の割合／失敗ダイの割合」の行（`CleanRoomYieldLogic.DicingLines`）。Lv別の割合と失敗ダイの割合は「損失を免れたダイの内訳」で、損失率とは別の段。最終的に失敗ダイになる割合（損失率＋(1−損失率)×失敗ダイの割合）は画面のどこにも無い。
- 出力の空きを待つ間だけ、「確定済み・出力の空き待ちの抽選」と「次の新規抽選（今の条件）」の2組が縦に並ぶ（`CleanRoomYieldLogic.Lines` の `PendingDrawCleanRoomYield` 分岐）。空き待ちは「切り終えた後」ではなく、待機中に抽選が確定し、出力の空きが無くて加工を始められない間のこと（`IdleMachineProcessState`。2026-11-21 に訂正。それまでは「切り終えて出力の空きを待つ間」と書いていた）。
- 部屋が成立していない間とレシピ未選択の間は、抽選の中身欄そのものが出ない（`ContextViewConversion.Yield` が `Absent` を返す）。材料切れで止まっているだけの間は稼働中と同じ1組が出る（`CleanRoomYieldPreviewComponent` は選択レシピと部屋の効果だけから計算する）。
- 部屋クラスは「清浄機の除去量の合計÷空きセル数」で決まる（しきい値の判定は `CleanRoomPurityLogic`）。清浄機1台の除去量は マスタの `removalVolumePerSecond`（v8 は 5）×電力比×フィルターの有無（`CleanRoomAirFilterComponent`）。

## Decision

### 1. 機械の画面の部屋の情報は1行にする

- 室内の機械の画面に出す部屋の情報は「部屋クラス C」の1行だけ。換気回数と清浄機1台ずつの行は機械の画面から外す。止まっている間は今までどおり停止の理由を出す。
  - 出所: agent前提（原文「全てのクリーンルーム関連のUIにクリーンルームの情報が乗っててうざい」＋ 2026-11-19 の問い「部屋の情報を、機械と清浄機の画面にどこまで残しますか。」が未選択（お任せ）だったので推奨案 A。2026-11-20 の仕分けシートで「そのまま通す項目」として提示し、異論なし。黙認なのでユーザー裁定ではない）

### 2. 確率の欄は最終の内訳を短い行で出す

- 精密切断機は次の行だけを出す。Lv の行は 0% のレベルを出さない。足して 100% になる。

  ```
  出力：300個
  Lv1：42.3%
  Lv2：7.2%
  失敗：50.5%
  ```

  - Lv N の値 = (1−損失率)×Lv N の割合。失敗の値 = 損失率＋(1−損失率)×失敗ダイの割合。
  - 出所: ユーザー裁定 2026-11-19 原文「失敗率と失敗ダイの確立それぞれ乗っててわけわからん。要するに何？失敗のダイって何％なの？？？ってなる」→ 最終の内訳の図への赤「もっとシンプルに 出力：300個 Lv1：42% Lv2：7.2% 失敗：50% と書いて」
- 「品質モジュールTier」「ダイの損失率」の行は消す。確率は小数1桁で出す。「出力」の個数はレシピの出力個数（ウェハ1枚のダイ数）。
  - 出所: agent前提（上の赤の行の形に無い行を消す。小数1桁は今の表示のまま。2026-11-20 に「そのまま通す項目」として提示し、異論なし）
- EUV露光式半導体製造装置は「失敗：30.8%」の1行（今の「層の失敗率」の値）。
  - 出所: agent前提（ダイシングと行の形をそろえる）
- 最終の内訳はサーバーが計算して運ぶ。クライアントは整形だけを行う。保存される抽選記録（`DicingPreview` の `CaptureDrawRecord`）の項目は増やさない。
  - 出所: agent前提（抽選式の持ち主はサーバー。3 の差分も同じ式から出すので計算を1か所にする。抽選記録に項目を足すとセーブ形式が変わる）

### 3. 確率はいつも同じ1組だけ出す

- 出力の空きを待つ間も、確率の欄は今の条件での1組だけを出す。「確定済み・出力の空き待ちの抽選」の組と見出しは出さない。空き待ちを示す行も足さない。
  - 出所: ユーザー裁定 2026-11-21 原文「ダイジングの稼働中と非稼働中のUIが違うのと、失敗率と失敗ダイの確立それぞれ乗っててわけわからん。」→ 問い「ダイシングの確率は「いつも1組だけ。出力の空き待ちのことは画面に一切書かない」でよいですか」→ 選択「A. その読みでよい (いつも同じ1組。空き待ちのことは書かない)」（2026-11-20 の同じ話題の問い2件はお任せ＋コメント「無回答。この概念がわからないし、余計にこの表記を複雑にしている」「意味わかんないって書いたダイの話し」で裁定にならなかったので、読みを復唱して確かめた）
- 部屋が成立していない間は、確率の欄を出さない（今のまま。停止の理由だけ）。
  - 出所: ユーザー裁定 2026-11-20 問い「部屋が成立していない間、確率の欄をどうしますか」→ 選択「B. 今のまま出さない (停止の理由だけ)」

### 4. 「失敗率の改善方法」はボタンで開くモーダルに差分で出す

- 確率の欄の下にボタン「失敗率の改善方法」を置く。押すと機械の画面の上にモーダルが重なり、今の値と、改善ごとの差分を出す。

  ```
  今: Lv1 42.3% / Lv2 7.2% / 失敗 50.5%
  部屋クラスを B に            Lv1 +9.2% / Lv2 +3.8% / 失敗 −13.1%
  品質モジュールLv1 を追加     Lv1 +1.2% / Lv2 +1.5% / 失敗 −2.7%
  品質モジュールLv2 を追加     Lv1 −36.9% / Lv2 +37.0% / Lv3 +8.2% / 失敗 −8.2%
  ```

  - 並べる改善は3種類: 部屋クラスを1つ上げる／今刺さっている中で一番高い Lv の品質モジュールを1個増やす／それより1レベル上の品質モジュールを1個刺す。
  - EUV露光式半導体製造装置も同じボタンと同じ3種類。差分は「失敗 −◯%」だけ。
  - 出所: ユーザー裁定 2026-11-19 原文「自分の装置の確率について書いてほしい 何がアップしたらどれくらいの確率になるのかUIに書いておいてほしい」→ 赤「上げるとどうなるかは別UIでボタンで見せるようにして（同じところで表示するとごチャル ボタンは（失敗率の改善方法）みたいにして で、差分を見せて 部屋クラスをBに Lv1 + 10% Lv2 +5% 失敗 -5% 品質モジュールLv1 追加 Lv1 + 10% Lv2 +5% 失敗 -5% 品質モジュールLv2 追加 みたいな 品質モジュールに関しては、今刺さってる中で一番高いモジュールを増やす表記と、1レベル上を刺すときの表記にする」、EUV の図への赤「これも同じく」
  - 出所: ユーザー裁定 2026-11-20 問い「「失敗率の改善方法」は、どう開きますか。」→ 選択「B. 小窓が重なる」補足「モーダルのほうがわかりやすい」
- やっても数字が変わらない行は出さない（すでにクラスA・品質モジュールの枠に空きが無い・1レベル上のモジュールが無い・上限に達していて増えない）。出す行が1つも無いときはボタンを出さない。品質モジュールが1個も刺さっていないときは「品質モジュールLv1 を追加」の1行にする。
  - 出所: agent前提（2026-11-20 に「そのまま通す項目」として提示し、異論なし。ボタンを出さない条件とモジュール無しの扱いは提示していない）
- まだ作れない品質モジュールの行も出す。作れる行と同じ見た目で、「まだ作れない」の印は付けない。
  - 出所: ユーザー裁定 2026-11-21 問い「「失敗率の改善方法」に、まだ作れない品質モジュールの行も出しますか」→ 選択「A. 作れなくても出す (上げるとどうなるかを先に見せる。まだ作れない品質モジュールの行が、印なしで混ざる)」
- 差分はサーバーが、抽選と同じ式（`CleanRoomRoleRates`）に仮の条件を入れて計算し、確率と同じ取得で運ぶ。
  - 出所: agent前提（2 と同じ理由。クライアントに式の写しを持たせない）
- モーダルは押した時点の中身を出し、開いている間は更新しない。ESC を押したら、モーダルと機械の画面を同時に閉じてゲーム画面へ戻る。機械から離れる・撤去されるなどで機械の画面が自動で閉じたときも、モーダルを一緒に閉じる。
  - 出所: ユーザー裁定 2026-11-22（`.decisions/2026-11-22-失敗率の改善方法のモーダルは開いた時点の中身で固定する.md`）
  - 出所（自動で閉じたとき）: ユーザー裁定 2026-11-28 問い「モーダル基盤に「どの画面から開かれたか」を持たせ、画面と一緒に閉じる処理と倍率を基盤側で受け持つ形に直してよいですか」→ 原文「はい、canselaletion token + IDisposableを実装って感じにして」（2026-11-23 に「閉じて再発防止して」を出所としていたのは誤り。別の話題への発言だった）
  - 出所（ESC）: ユーザー裁定 2026-11-23 原文「クリーンルームの改善方法のモーダルが、ESCを押しても残り続ける」→ 選択「両方一度に閉じる」
  - 原因: 実測（証拠: PlayMode シナリオ improvement-modal-esc-repro のログ `before state=SubInventory modal=True` → `after state=GameScreen modal=True`。入力は InputSystem への注入）
- このモーダルの面は、レシピ詳細と同じ `GamePanel` の Craft 枠にする。設計図の名前入力モーダルは今の見た目のまま残す。
  - 出所: ユーザー裁定 2026-11-23 原文「そもそもデザインスタイルが他のインベントリ等で使われているUIじゃなく、本当に酷い」→ 選択「レシピ詳細と同じ枠」
- 題は本文の文字として置き（モーダルに題の罫線を付けない規約のため）、閉じるは機械の画面と同じ副次アクションのボタンで右に置く。
  - 出所: agent前提（visual-vocabulary §3・`PanelActionButton` の前例）
- モーダルの中身に表を載せられるようにする（今の `ModalRequest` は文字だけ）。UI 規約のホワイトリストに無い表現が要る場合は、実装より先に `.agents/skills/ref-uitk-design/` の `visual-vocabulary.md` へこの裁定を引用して足す。
  - 出所: agent前提（ref-uitk-design の規約）
- モーダルを要求する側は、自分の寿命の `CancellationToken` を渡す。トークンが取り消されたら、その要求だけを閉じる。要求の戻り値は `IDisposable` の持ち手で、`Dispose` は自分の要求だけを取り消す。「要求を投げて返事を待つ」仕組みは残す。このモーダルは、機械の画面が出ている間だけ生きるトークンを渡す。
  - 出所: ユーザー裁定 2026-11-28 原文「はい、canselaletion token + IDisposableを実装って感じにして」／2026-11-23 原文「「要求を投げて返事を待つ仕組み」は廃止　←これ自体は妥当なんじゃないの？なんで廃止するの？モーダルって一般的にそういうものじゃん」／2026-11-23 回答「なんでそれを考える必要があるの？モーダルを「そのインベントリの一部」として適切に扱えてないのでは」
  - 出所（細部）: agent前提。取り消しは例外でなく `ModalResult.Cancel` で解決する（try-catch を使わない規約）。取り消し済みのトークンでの要求は出さずに警告を残す。
- 設計図の名前入力のモーダルも `CancellationToken` で閉じる。名前入力が開くたびに `CancellationTokenSource` を作ってそのトークンを渡し、閉じるときに `Cancel` する。`CancellationToken.None` は渡さない。
  - 出所: ユーザー裁定 2026-11-28 問い「PR #1704 で、設計図の名前入力モーダルも CancellationToken で閉じる形（開くたびに CTS を作り、閉じるとき Cancel）に直すかを決めてください」→ 原文「はい」
  - 出所（細部）: agent前提。寿命は要求より先に差し替える（通知の途中で同期に閉じられても、寿命の取り消しで要求が閉じる）。開いたままの開き直しでは前の寿命を取り消さずに捨てる。
- 高解像度での倍率は、モーダルの土台（`UiModalHost`）に舞台の倍率で載せる口を置いて受け持つ。設計図の名前入力には掛けない（見た目を変えない）。
  - 出所: ユーザー裁定 2026-11-23 問い「改善モーダルは高解像度でも小さくならないよう、モーダル自身が倍率を掛け直しています。このままだと、次に同じ種類のモーダルを足すときに掛け忘れて、その画面だけ小さく表示されます。倍率の処理をどこに持たせますか？」→ 選択「モーダルの土台に集約（推奨）」
- 機械の画面が閉じたかは、機械の画面本体と同じ表示の判定（`BlockInventoryScreenVisibility.IsShown`）を購読して知る。
  - 出所: ユーザー裁定 2026-11-23 問い「改善モーダルが「機械画面を離れた」と知る判定が、機械画面本体とは別に書かれています。このままだと、機械画面の閉じ条件を変えたときにモーダルだけ古い条件で閉じたり残ったりします。また配線が消えてもテストが気づきません。判定をどこから受け取りますか？」→ 選択「画面の表示状態を購読（推奨）」

### 5. 清浄機の画面は部屋クラスと次のクラスまでの台数を1行で出す

- 清浄機の画面の部屋の行は「クラスC（クラスBまであと5台）」の形。クラスA のときは「クラスA」だけ。
  - 出所: ユーザー裁定 2026-11-19 原文「フィルターにあと何台おいたらレベルがアップするのか書いておいてほしい」→ 赤「クラスC（クラスBまであと5台） として」
- 台数は今の稼働状態のまま数える（止まっている清浄機の除去量は 0 のまま。書いた台数を置けば実際に上がる）。新しく置く清浄機は電力 100%・フィルターありで数える。
  - 出所: ユーザー裁定 2026-11-20 問い「止まっている清浄機があるとき、「あと何台」をどう数えますか」→ 選択「A. 今の状態のまま数える (置けば実際に上がる台数)」
- 出すのは次のクラスまでの台数だけ。
  - 出所: agent前提（上の赤の行の形。2026-11-20 に「そのまま通す項目」として提示し、異論なし）
- 清浄機1台ずつの行は、台数のまとめ1行（「清浄機 6台（うち1台が止まっています）」）に替える。この清浄機自身の行にフィルターの個数は書かない。
  - 出所（フィルターの個数）: ユーザー裁定 2026-11-19 赤「フィルター3個は見れば分かるんだから出さなくて良い」
  - 出所（まとめ1行）: ユーザー裁定 2026-11-21（下の行）
- 清浄機の画面の部屋の欄は「部屋クラス（あと何台）／台数のまとめ／この清浄機の電力・フィルターの残量」の3行。換気回数の行と、清浄機を1台ずつ並べた行は消す。止まっている清浄機が「どれか」は、1台ずつ開いて探すことになる。
  - 出所: ユーザー裁定 2026-11-21 問い「清浄機の画面から、換気回数の行と、清浄機1台ずつの行を消してよいですか」→ 選択「A. 両方消す (3行。止まっている清浄機が「どれか」は、1台ずつ開いて探すことになる)」
- 台数はサーバーが部屋クラスの判定と同じ式（`CleanRoomPurityLogic`）から計算し、部屋の要約と一緒に運ぶ。昇格に使うしきい値（昇格時の倍率込み）で数える。
  - 出所: agent前提（判定式の持ち主はサーバー。クライアントは今、部屋の体積などを捨てている）

## Considered Options

- 確率の欄を2段のまま言葉を直し合計を足す（2026-11-19 に提示。ユーザーは選ばず最終の内訳の図に赤を入れた）
- 「上げると」の行を確率の欄の下に常時並べる（2026-11-19 に提示。ユーザー棄却「同じところで表示するとごチャル」）
- 「失敗率の改善方法」を機械の画面の中身の入れ替えで出す（2026-11-20 に提示。ユーザーはモーダルを選択）
- 部屋が成立していない間も欄の場所を残して「部屋クラスが決まると確率を表示します」と出す（2026-11-20 に提示。ユーザーは「今のまま出さない」を選択）
- 「あと何台」を、止まっている台を直した前提で数える／両方書く（2026-11-20 に提示。ユーザーは「今の状態のまま数える」を選択）
- 空き待ちの間だけ今回決まった個数に替える／2組のまま行の形だけ新しくする（2026-11-20 に提示。どちらも押されなかった）
- 「いつも1組だけ」の読みが違う（どうしたいかをコメントに書く）（2026-11-21 に提示。ユーザーは「その読みでよい」を選択）

## Consequences

- 損失率と品質モジュールTier は画面から読めなくなる。抽選の2段の仕組みを知りたいときは研究の説明を読む。
- 出力の空き待ちの間、画面の確率は「次に切るぶん」のもので、空き待ちのぶんに使われた確率とは違うことがある（切った後に条件を変えた場合）。
- 確率と台数の計算はサーバーにあり、クライアントは式を持たない。式を変えたときに画面の直しは要らない。
