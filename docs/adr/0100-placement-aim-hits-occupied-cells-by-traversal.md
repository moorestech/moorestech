# 0100: 設置照準のブロックへの当たりを、当たり判定を持たずに占有セルをたどって求める

Status: Accepted
日付: 2026-11-12

## 背景
ADR 0099 の決定2で、設置照準の当たり判定は「ブロックごとの GameObject 1個に、薄い面の `BoxCollider` を6枚付ける」形（`BlockPlacementHitFaces`）になり、PR #1655 でマージされた。前後の計測は `docs/performance/2026-11-12-placement-preview-frame/README.md` にある。

ベースラインワールド（15,082ブロック）で、この当たり判定には次の負担が残っている。
- GameObject 15,082個、`BoxCollider` 90,492枚。コライダーの総数は変更前と同じ 191,676。
- ワールド読み込み: ブロック生成のフレームが変更前より +1,963ms 重い。`AddComponent` が 135,738回増え、その大半は当たり判定の `BlockPlacementHitFaces` と `BoxCollider` 6枚。
  原因: 実測（証拠: 同 README「ブロック生成のフレームで増えた分」）
- 設置モードに入る遷移に約566ms、出る遷移に約174ms かかる。中身はほぼ `GameObject.ActivateAwakeRecursively`。当たり判定 15,082個の有効化・無効化が大半と見ている。
  原因: 推測（根拠: 同 README。設置モード中に有効になる数は `BlockPlacementHitFaces` 15,082、`PreviewOnlyObject` 10,289で、両者を分けて測っていない）

ADR 0099 決定2 は「セル座標→ブロックの索引をたどって計算で当てる」案を、「B で効果を測り、足りなければこちらで更に削る」として棄却していた（Editor 実測 0.046ms/本）。

照準の入口は `PlaceSystemUtil.TryRaycastPlacementSurface` の1か所だけで、呼び出し側へ渡るのは `PreviewSurfaceType?`（ワールド基準の面の向き。null は地面）と当たった位置だけ。当たったブロックそのものは、どの呼び出し側も使っていない。

## 決定
1. 設置照準の当たり判定（`BlockPlacementHitFaces`）を廃止する。ブロックへの当たりは、占有セルの索引を照準レイに沿ってたどって求める。
   出所: ユーザー裁定 2026-11-12 原文「現在全ブロックに照準を取得するための6つのコライダを1ブロックごとに1オブジェクトあると思うんですが それを消してプログラムで走査するようにしたいです」。設計書への書き起こしは「書き起こしていいよ」
   棄却: B 案（ADR 0099 決定2、マージ済み）のまま残す

2. 当たり方（どのセルのどの面に当たるか）は、B 案の薄い面と同じ「占有マスの直方体の面」とする。ブロック本体の形には当たらない。
   出所: agent前提（ADR 0099 決定2「どの案でも当たり方は今と変わらない」と、ユーザー裁定の「1個に薄い面6枚」の理由「当たり方を今と完全に同じにする」を引き継ぐ）

3. 占有セルの索引は、クライアントのブロック置き場（`BlockGameObjectDataStore`）が持つ。ブロックの `BlockPositionInfo.MinPos`〜`MaxPos` の全セルをそのブロックへ引けるようにし、ブロック置き場の辞書と同じ瞬間に更新する（設置・撤去・別 ID への置き換えの3経路）。撤去中の破棄アニメーションの間は、もう照準に当たらない（B 案では GameObject が消えるまで当たっていた）。
   出所: agent前提（ブロック置き場が辞書と同時に更新する索引の前例 `BlockTypeIndex`・`NearestTargetIndex`。破棄アニメ中に探索から外す前例 `DropFromNearestIndex`）

4. 照準は次の手順で決める。呼び出し側の受け取り（`PreviewSurfaceType?` と当たった位置）は変えない。
   1. 今と同じマスク（`Without_Player_MapObject_Block_LayerMask`）で物理レイを撃ち、最初に当たったものとその距離を得る。
   2. 同じレイで占有セルを1マスずつたどる（3D の DDA）。たどる範囲は、物理レイの当たった距離までと、全占有セルを囲む直方体の中だけとする。物理レイが何にも当たらなくても、この直方体を出たら止まる。
   3. 占有セルに先に入ったら、入った面を `PreviewSurfaceType` に変換し、レイ上のその点を当たった位置として返す。
   4. 占有セルに入らなければ、今のコードと同じく、物理レイが地面に当たっていれば地面（null）とし、それ以外に当たっていれば照準なしとする。
   5. レイの始点（カメラ）が占有セルの内側にあるときは、そのブロックの直方体から出る面に当たったとする（B 案で「内側から撃つと奥の面に当たる」のと同じ）。
   出所: agent前提（照準の入口が1か所であることと、B 案の受け入れ条件「内側から +X へ撃つと YZ_X」の継承。距離の上限は、B 案の照準が距離無制限だったことに合わせて固定値を置かない）

5. レイがセルの辺や角をちょうど通るときは、Y、X、Z の軸の順で、先の軸の面に入ったとする。
   出所: agent前提（どの面にするかを決めておくことだけが要る。上面への積み上げが最も多いので Y を先にした）

6. 照準がブロックに当たるのは、今と同じく設置モード中（`PlaceBlockPreviewDisplay` の `OnEnter`〜`OnExit` の間）だけとする。設置モードの外では占有セルをたどらず、今と同じく物理レイの結果だけで決める。今、設置モードの外でこの照準を使うのは削除ツールの箱選択（`DeleteBoxInput` → `PlacementUnitCellResolver.TryGetCursorCell`）だけで、その照準はブロックを素通りして地面に当たっている。これを変えない。
   原因（今の素通り）: 推測（根拠: `PlaceBlockPreviewDisplay.OnExit` で全ブロックを `Hidden` にし、`BlockPreviewOnlyObjectsView.Apply` は `Hidden` で当たり判定を無効にする。`DeleteObjectState` は表示を切り替えない。実機では確かめていない）
   出所: ユーザー裁定 2026-11-12 質問「計算方式にすると、（箱選択が）ブロックの面の外側のセルを指すようになります。どうしますか？」→ 原文「なぜ今まで通り以外にする必要があるの」
   棄却: 箱選択もブロックの面の外側のセルを指すようにする（ADR 0079 の記述「1x1 設置と同じヒット面の外側セル」に合わせる案）

7. 当たり判定のために足していた次のものを外す。
   - `BlockPlacementHitFaces`、それを作る `BlockGameObject.Initialize` の呼び出し
   - コライダー距離カリングでの `BlockBoundingBox` レイヤーの除外（`BlockColliderCullingRegisterService`）。当たり判定を外すためだけにあった
   `BlockBoundingBox` レイヤー自体と、`LayerConst` の定数・マスク、アウトラインの対象からの除外（`RuntimeOutlineFactory`）は残す。枠の辺のプレハブ（`BlockPreviewBoundingBox.prefab`）の GameObject 25個がこのレイヤーに置かれているため。
   出所: agent前提（当たり判定のためだけの除外は残さない。辺がまだ使うレイヤーは残す）

   当たり判定が無くなると、設置モード中にツールチップの照準（`GameObjectToolTipTargetController`、`DefaultRaycastLayers & ~ConnectionLine` で撃つ）を薄い面が遮らなくなる。これは受け入れる。
   出所: agent前提（遮っていたのは当たり判定の副作用で、意図された挙動ではない）

9. 照準1本の計算時間は、ベースラインワールドで物理レイが空へ抜ける最悪の向き（全占有セルを囲む直方体を水平に端から端まで通る向き）でも、Editor で 0.1ms 以下に収める。収まらなければ、照準の結果を変えずに速くする（たとえば、空のチャンクを飛ばす2段の索引にする）。距離の上限を置いて照準の結果を変えることはしない。
   出所: agent前提（決定4の「距離の上限を置かない」を保ったまま、作り方の上限だけを決める）

8. 範囲外: `BlockGameObjectDataStore.IsOverlapPositionInfo`・`GetOccupancy` は今、全ブロックを1つずつ見ている。新しい索引で引けるようになるが、今回は替えない。設置プレビュー枠の辺（ADR 0099 決定3・4）も替えない。
   出所: agent前提（依頼の本筋でない既存処理は変えない）

## 見込み
当たり判定の GameObject 15,082個と `BoxCollider` 90,492枚が0になる。ワールド読み込みのブロック生成フレームは、B 案で増えた約2秒の大半が無くなる見込み。設置モードに入る・出る遷移は、当たり判定の有効化・無効化の分だけ短くなる見込み（推測。ほかのプレビュー部品の分は残る）。照準1本あたりの計算は、0099 時の Editor 実測で 0.046ms。効果は実装後に、ADR 0099 と同じ手順（`docs/performance/2026-11-12-placement-preview-frame/README.md`）で前後を測って記録する。`docs/performance/benchmark/snippets/placement-frame-count.cs` は型を名前で引き、型が無ければ null を出すので、そのまま使える。
