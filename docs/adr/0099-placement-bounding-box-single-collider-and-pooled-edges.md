# 0099: 設置プレビュー枠を、ブロックごとの当たり判定 GameObject 1個と使い回しの辺に分ける

Status: Accepted
日付: 2026-11-09

## 背景
設置プレビュー枠（`BlockPreviewBoundingBox.prefab`）は1個に GameObject が37個ある（辺12本・面6枚とその親子）。これを設置済みの全ブロックに1個ずつ作っている。ベースラインワールド（15,082ブロック）では約55.8万個になり、シーン全体の Transform 約98万の約57%を占める。
原因: 実測（証拠: `docs/performance/2026-10-22-gameobject-count/breakdown-raw.txt` の `BlockPreviewBoundingBoxSurface` 90,492・`BlockPreviewBoundingBox` 15,082 と、プレハブ内の GameObject 37個）

ワールド読み込みでは、枠を作るフレームが約13秒止まる（`Instantiate` 15,082回で3.3秒、生成後の処理 self 7.2秒。同じフレームで `BlockPreviewBoundingBoxSurface` を90,498個作っている）。
原因: 実測（証拠: `docs/performance/2026-11-08-world-load-remeasure/heavy-subtree-raw.txt` の frame 688）

枠の用途は2つある。
- 辺: 設置モード中、プレイヤーの周囲20mのブロックだけ描く（ADR 0083）。半径外のブロックの辺は、作るだけで描かれない。
- 面: 設置の照準レイだけが当たる当たり判定（`BlockBoundingBox` レイヤー）。照準レイ（`PlaceSystemUtil.TryRaycastPlacementSurface`）は `Block` レイヤーを外して撃つので、ブロック本体の当たり判定ではなく、占有マスの箱に当たる。

## 決定
1. 今回の GameObject 削減の範囲は、設置プレビュー枠だけにする。
   出所: ユーザー裁定 2026-11-09 質問「今回の GameObject 削減で、どこまでを扱いますか？」→ 選択「プレビュー枠だけ」
   棄却: 枠＋ブループリントのサムネイル被写体の残留（約3.8万個）／枠＋サムネイル＋ベルトコンベア・土台の階層削減（どちらも後続へ回す。下の「後続」）

2. 面（設置照準の当たり判定）は、ブロックごとの GameObject 1個に集める。その GameObject に、今の枠と同じ薄い面の当たり判定（BoxCollider）を6個付ける。`BlockBoundingBox` レイヤーに置き、当て方は今どおり物理レイとする。どの面に当たったかは、当たった BoxCollider（`hit.collider`）から今の `PreviewSurfaceType`（ワールド基準の面）を引く。設置モード中は全ブロックで有効、設置モード外は無効にし、半径外のブロックの横にも今どおり置ける（ADR 0083 決定4を維持）。
   出所: ユーザー裁定 2026-11-09 原文「一旦やって見て考えればいいのか ダメだったらさらに削るみたいな形だもんね じゃあ描画はプール・B型でやる感じで」→ 選択「B（当たり判定は1ブロック1個の GameObject）」
   棄却: 「セル座標→ブロック」の索引をたどって計算で当てる（Editor 実測 0.046ms/本で負荷は小さいが、自作の当て方が増える。B で効果を測り、足りなければこちらで更に削る）／周囲20mだけ今の枠を作る（半径外のブロックに照準が当たらなくなり ADR 0083 決定4を覆す）
   ユーザーへの説明: 設置照準は今も占有マスの箱に当たり、ブロック本体の形には当たらないこと。どの案でも当たり方は今と変わらないこと。

   当たり判定の中身は、薄い面6枚とする。
   出所: ユーザー裁定 2026-11-09 質問「設置照準の当たり判定は、GameObject 1個に『箱型1個』と『薄い面6枚』のどちらを付けますか？」→ 選択「1個に薄い面6枚」
   棄却: 箱型の当たり判定1個（物理の登録数は約1.5万に減るが、カメラが占有マスの内側にあると照準がそのブロックを素通りし（推測。根拠: 物理レイは始点が内側にある当たり判定に当たらない）、角の付近で面の判定が変わりうる）

3. 辺は全ブロックに持たせず、使い回し（プール）の GameObject を描画対象のブロックへ貸し出して描く。
   出所: ユーザー裁定 2026-11-09 原文「やっぱり描画はプールする感じでゲームオブジェクト使いましょう拡張性・変更性の方が大事だ」
   棄却: `Graphics.RenderMeshInstanced` で GameObject 無しに描く

4. プールの形は次のとおり（2026-11-09 にユーザーへ提示し「ok」を得た設計）。
   - 枠のプールはゲーム中に1つで、DI に Singleton 登録し、`ClientDIContext` の static プロパティで配る（`BlockGameObject` が `ClientContext.VanillaApi` を引くのと同じ形。2026-11-12 計画時に具体化）。プールの親 Transform の下に「辺12本の枠」（今のプレハブから面を除いたもの）を置く。空きがあれば貸し、無ければ新しく作って貸す。返されたら非表示にして空きへ戻し、数は減らさない。
   - ブロック側には「枠の借り口」（GameObject ではないクラス）を `IPreviewOnlyObject` の1つとして持たせ、今の `BlockPreviewOnlyObjectsView` の表示切り替えに乗せる。描画の指示（設置モードで半径内、またはデバッグのホバー）で借り、今の `BlockPreviewBoundingBox.SetBoundingBox` と同じ計算で位置・向き・大きさを合わせる。描画しない指示で返す。
   - 枠はブロックの子にしない。ブロックの GameObject が破棄されたとき（`OnDestroyAsObservable`）に、借りていた枠を返す。撤去（`DestroyBlock`）だけでなく、`BlockGameObjectDataStore.PlaceBlock` の置き換え経路（`Destroy(oldBlock.gameObject)` で `DestroyBlock` を通らない）でも返すため（2026-11-12 計画時に修正）。
   - 前例は `BlockPlacePreviewObjectPool`（空きを探して貸す・無ければ作る・使い終わったら非表示）。前例は「全部まとめて返す」方式だが、20m の出入りでブロック単位に増減するので、1つずつ返す形にする。
   出所: agent前提（前例 `BlockPlacePreviewObjectPool`、既存の表示切り替え `BlockPreviewOnlyObjectsView`）。ユーザーは提示した設計に「ok」と回答（2026-11-09）

## 見込み
枠の GameObject は約55.8万個から、当たり判定の約1.5万個＋描画中の枠（数百組×25個。面を除いたプレハブは root 1・辺の親12・辺12）になる見込み。物理エンジンに登録する当たり判定の数（約9万）は今と同じ（推測。効果は実装後にベンチマークと読み込み計測で前後比較する）。

## 後続（今回の範囲外）
- ブループリント「工場」のサムネイル被写体が、撮影後も約3.7万 GameObject 残っていた件。撮り損ねると被写体を破棄しない作りが原因と見ている（推測）。再現して原因を測ってから直す。
- ベルトコンベア・土台の階層削減（ブロック配下の約6割）。プレハブの組み替えが要る。
