# ADR 0090: パイプ網の流体量を整数単位（10 億分の 1）で持ち、Stepper をノードごとに集める形（並列可能）にする

- 日付: 2026-10-24
- 状態: 採択（追記 2026-10-24 で単位を 1/1000 から 1/1,000,000,000 に変更し、微小量の扱いを「毎 tick 0 にする」に確定）
- 関連: ADR 0088（パイプの tick 差分同期。棄却案「先に固定小数点へ」を本 ADR で採る）、ADR 0089（SoA）、`.decisions/2026-10-24-パイプ網の流体量は1000分の1単位の整数で持ちStepperはノードごとに集める.md`、`.decisions/2026-10-24-パイプ網の流体量は10億分の1単位にし動けない量は毎tick空にして容量比は128ビットで正確に求める.md`

## 背景
ADR 0088 でクライアントがサーバーと同じ流体計算を回す形にしたが、計算は double のままで、サーバーとクライアントの一致は「同じ CLR で同じ順に加算する」ことに依存していた。加算順が違えば丸めが違い、ハッシュ不一致で同期が止まる。これは並列化（面やノードを分割して別スレッドで回す）を禁じる。レビュー（2026-10-23〜24）でも、受理量を残量から引き算で求めた値が 1 ulp ずれて不一致になる事故が実際に見つかった（`FluidSimNetwork.AddExternal` の `out accepted` 化で修正）。
整数なら加算は順序に依らず、同じ入力から同じ出力が出る。あわせて、今の Stepper は面ごとに両端ノードへ足し込む形（scatter）で、並列に回すと同じノードへの書き込みが衝突する。ノードごとに自分の面を集めて自分だけ書く形（gather）なら、ノード範囲を分けて回せる。
Unity の API レベルは .NET Standard 2.1 で、128 ビット整数（`Int128`・`Math.BigMul(long,long)`）は使えない。当初は中間積が 64 ビットに収まる単位（1/1000）を選んだが、追記のとおり 64×64→128 の掛け割りを自前で書き、単位を 10 億分の 1 に上げた。

## 決定
- **置き場: 今の PR（ブランチ fix/train-client-tick-slack-pacing）に足す。** 出所: ユーザー裁定 2026-10-24 原文「流体についてdoubleから整数化への許可が早速オリました。この並列化可能な状態への変更を追加したい」→ 選択「今の PR に足す」。棄却案: 今のブランチの上に新しいブランチを切る（レビューと計測表を分けられるが、ユーザーは 1 PR を選んだ）。
- **範囲はパイプ網だけ。** 網の配列（量・容量・面の上限・面の速度・ポートの上限と速度）、Stepper、差分と全量のメッセージ、ハッシュ、パイプのセーブ、クライアントのコピーを整数にする。機械のタンク（`FluidContainer`）・`FluidStack`・レシピ・UI の流体量は double のまま。出所: ユーザー裁定 2026-10-24 選択「パイプ網だけ」。棄却案: ゲーム全体の流体量（変換点は消えるが機械系の全ファイルとマスタの扱いに広がる）。
- **1 単位 = 流体量の 10 億分の 1（10^-9）。型は `long`。**（当初は 1/1000。追記で変更。）タンク 50,000 は 5×10^13 単位で、long には流体量 92 億まで入る。圧力は「充填率差 × 隣接容量の小さい方」を、容量が等しければ量の差、違えば大きい側の量を容量比で縮めてから引く（`FluidPressureMath.PressureUnits`）。容量比の掛け割りと比例縮小の掛け割りは `FluidMulDiv.MulDiv`（64×64→128 ビットの積と 128÷64 の商）で正確に求め、丸めは最後の切り捨て 1 回だけ。2^30 の整数充填率は廃止した。出所: ユーザー裁定 2026-10-24（会話）「aA − aB × cA / cB こういうところだけ128bit 整数にすればどうなる？」→ 採用。
- **異種流体が同じ tick に同じ空ノードへ入ろうとしたら、面の番号が小さい方の流体を採り、他の流体の面はその tick 閉じる。** 今の挙動と同じ規則をノードごとに集める形で書く。出所: ユーザー裁定 2026-10-24 選択「面の番号が小さい方を通す（今と同じ）」。棄却案: 流量が大きい方を通す／どちらも通さない（両側が押し続けると永遠に空のまま）。
- **並列実行は入れない。構造だけ並列可能にする。** Stepper の各フェーズを「ノード範囲 [start, end) を受け取り、その範囲の要素だけを読み書きする」関数にし、`Step` はそれを全範囲で順に呼ぶ。スレッドは使わない。範囲を 2 分割して呼んでも全範囲 1 回と同じ結果になることをテストで担保する。出所: ユーザー裁定 2026-10-24 選択「構造だけ並列可能にし、実行は直列のまま」。棄却案: 今回から複数スレッドで実行（5,000 本で 0.2 ms の計算にスレッド起動コストの方が大きい）。
- **境界の丸め（agent前提）。** 機械→パイプ（`AddLiquid`）は `floor(amount × 10^9)` 単位だけ受け入れ、端数は機械側に残す。パイプ→機械（ポートの `Deliver`）は整数単位の量を double で渡し、機械が受け入れた double 量を `ceil` で単位に戻してノードから引く。根拠: `IFluidInventory.AddLiquid` は double のまま残す裁定なので、端数の往復が避けられない。注意（追記）: 1 単位が 10^-9 になったので、機械側の double 演算の誤差（量 5 万で 10^-11 程度）が数単位に相当し、`ceil` だけでは「ノードが引く量 ≥ 機械が得た量」を厳密には保証できない。どちらの向きにも最大数単位（10^-8 未満）ずれ得るが、丸めの偏りではなく双方向の誤差なので増殖の口にはならない。
- **定数の整数化（agent前提）。** `PressureGain 0.12` は `12/100`、`Damping 0.002` は `2/1000`（`v × 998 / 1000`、切り捨てで必ず 0 へ減衰する）。double 版の `AmountEpsilon = 1e-9` のカットオフは、追記の「動けない量を毎 tick 0 にする」に置き換わる。
- **流量の比例縮小（agent前提）。** `outflowScale`・`inflowScale` の double 配列をやめ、`flux = desired × amount / outflowSum`（切り捨て）を `FluidMulDiv.MulDiv` で求める。切り捨てなので送り側の残量を超えない。
- **Stepper の構造（agent前提）。** 面の両端ノードへの scatter 加算を、ノードごとの gather に置き換える。網は構築時に「ノード→接続面の一覧（CSR: `NodeFaceStart[]`・`NodeFaces[]`）」を持つ。フェーズ: (1) 面の速度更新（面ごと、読むのは両端ノードの量）、(2) ノードごとに流出希望の合計（接続面とポートを集める）、(3) 面ごとに送り側縮小後の暫定流量、(4) ノードごとに流入合計と「この tick 受け入れる流体」（空ノードは番号最小の流入面の流体）、(5) 面ごとに確定流量（受け側縮小と異種流体の閉面）と速度の書き戻し、(6) ノードごとに確定流量を集めて量と流体 ID を更新、(7) ポートの配達、(8) 動けない量しか無いノードを 0 にして名を外し、要素ハッシュを足す。各フェーズは自分の添字の要素だけに書き、前のフェーズの配列だけを読む。
- **セーブ形式は版 7 へ。** パイプの `amount`・`faceVelocities[].velocity` を整数単位の `amountNano`・`velocityNano` に変える。`SaveMigrationStepV6ToV7` が double を ×10^9 して最近傍に丸める。`WorldSaveAllInfo.CurrentVersion = 7`。機械のタンク（`FluidContainerSaveJsonObject`）は変えない。
- **クライアント表示（agent前提）。** 水位は `FluidSimNetwork.FillRate`（double の割り算、表示専用）を float に直して渡す。WebUI と `FluidMessagePack` は double のままなので、網の整数を `FluidUnits.ToAmount` で戻して渡す。

## 結果
- 同じ全量と同じ差分列から、サーバーとクライアントがビット単位で同じ網を得る。どの順・何分割で足しても同じなので、将来ノード範囲をスレッドに配れる。
- 流れの最小単位は 10^-9。静止から動き出せない圧力差（16 単位以下）の残りは tick の最後に 0 になり、名も外れる（double 版の 1e-9 カットオフと同じ桁）。
- 境界の往復で最大数単位（10^-8 未満）がどちらの向きにもずれ得る。
- 既存セーブは版 7 へ変換される（amount × 10^9 の最近傍）。

## 棄却案
- 全流体量の整数化（ユーザー裁定で範囲外）。
- 流量の大きい方／どちらも通さない の異種流体規則。
- 今回からの並列実行。
- 1/1000 のまま容量比を 2^30 の充填率で丸める（当初案。追記で 10^-9 と MulDiv に置き換え）。

## 検証
- 同じ網を全範囲 1 回と、ノード範囲を 2 分割・3 分割・7 分割して回したときの配列が完全一致する（`FluidSimulationStepperPartitionTest`）。
- 既存の `FluidSimulationStepperTest`（保存則・釣り合い・一方向・ポート配達）が整数版で通る。
- 版 6 のセーブ（double の amount・velocity）が版 7 に変換され、ロード後の網の量が ×10^9 の最近傍になる（`SaveMigrationStepV6ToV7Test`）。
- ハッシュの感度テスト `FluidNetworkStateHashTest` が long 版で通る。
- `FluidMulDivTest`: 境界値と固定シードの乱数 20 万例が `BigInteger` の厳密値と一致し、除数 0 と商の溢れは例外になる。

## 追記 2026-10-24（最終バグ確認後）: 動けない量は毎 tick 0 にし、単位を 10 億分の 1 に上げ、容量比は 128 ビットで正確に求める
- **問題。** 整数化で、隣との圧力差が小さいと速度の増分が切り捨てで 0 になり、排水しきったはずのパイプ列に数単位が永久に残る。double 版はこの残りが減衰で 1e-9 を割った時点で `CleanupIfEmpty` が 0 にして名を外していたが、整数版は決して空にならず、流体の名も外れない。そのため、水を抜いた網へ油を流すと最初の残りで面が閉じ、永久に通らなかった（moores-code-review の最終バグ確認、core-any-removed-invariant が検出。再現: 1/1000 単位で 10 本直列を端で排水 → [0,1,1,3,6,6,2,0,0,0] が残る）。
- **なぜ残るか。** 速度は `gain = 圧力差 × 12 / 100`、`v = (v + gain) × 998 / 1000` の切り捨てで進む。静止（v = 0）から 1 単位を流すには gain ≥ 2、つまり圧力差 ≥ 17 単位が要り、16 単位以下の差は何 tick 待っても動かない（`FluidPressureMath.MaxImmovablePressureUnits = 16`）。これは単位の細かさとは無関係で、定数が決める「単位数」である。
- **経緯。** まず「痕跡の規則」（動けない量を面の開閉・受け入れ判定・機械流入・持ち越しの 4 箇所で空と同じ扱いにし、別の流体が入ったら名だけ置き換える）を入れたが、流れの計算に量の閾値の分岐が 4 箇所増え、排水後の階段状の残り（ポートから i 本目に最大 17 × i 単位）も残った。ユーザーと検討し、double 版と同じ「残量チェックで 0 にする」1 箇所に戻し、単位を上げて消える量を double の 1e-9 と同じ桁にする方針に変えた。
- **決定 1: 動けない量は tick の最後に 0 にして名を外す。** `FluidSimNetwork.ClearIfImmovable`（Stepper の最終フェーズ）。「動けない量」は、自分の面のうち圧力スケール（min(両端の容量)）が最大の面で空の隣へ押しても gain が 2 に届かない量（`FluidPressureMath.IsImmovable`。0 を含む）。鉄のパイプ（500）どうしで 16 単位、タンク（50,000）と鉄のパイプの面では 1,699 単位（圧力差 16）まで。流れの計算は量の閾値を見ず、面の開閉は「両側に名があり、名が違う」だけで決める。
- **決定 2: 1 単位 = 10^-9。容量比と比例縮小は `FluidMulDiv.MulDiv`。** 1/1000 のままでは消える量が 1 パイプ 0.016、タンク 1.7 で、double の 1e-9 と桁が違いすぎる。10^-9 なら 1.6×10^-8 と 1.7×10^-6。10^-9 単位ではタンク 5×10^13 × 容量 500×10^9 の積が 64 ビットを超えるので、2^30 の充填率をやめ、64×64→128 の積と 128÷64 の商を自前で書いた（Hacker's Delight divlu2。容量が等しい面は引き算だけで掛け割りを通らない）。商は被乗数以下になる形だけで使い、long に収まらない場合は例外。
- **決定 3: 流入の有無で 0 にするのを止めない。** 「その tick に流入があったノードは消さない」条件も検討したが、消えるのは 1 tick に 16 単位（1.6×10^-8）未満しか入らない流入だけで、マスタのどの流量よりも 5 桁以上小さい。条件を足す計算の方が余計なので入れない（ユーザー裁定「余計な計算はいらない」）。限界として `FluidImmovableResidueTest` に「2^-27 ≒ 7 単位/tick の流入は毎 tick 消える」を明示した。
- **決定 4: 境界ポートの最小ゲイン底上げは撤去。** 残りは決定 1 で 0 になるので不要。ポートのノードが機械に渡さず消す量は閾値（16 単位）以内。
- **残る限界。** 排水の終端で、動けない量に落ちたノードは 0 になる前に隣から数単位ずつ受け取って毎 tick 消すことがあり、1 ノードあたり数十単位（10^-8 相当）が消え得る。総量の厳密な保存は「流れている間」だけで、静止時に 10^-8 単位の損失がある（double 版も 1e-9 を捨てていた）。境界の double 誤差で最大数単位がどちらの向きにもずれ得る（決定の「境界の丸め」参照）。
- **棄却案。** (a) 面の速度増分を 2 単位に底上げ（容量が等しく合計が奇数の 2 ノードが ±1 単位で永久に往復）。(b) 送り側縮小で切り捨て 0 の先頭の出口へ 1 単位渡す（中央ポートの網で単位がポートを素通りして往復。再レビューで Critical）。(c) 痕跡の規則（上記の経緯。4 箇所の分岐と階段の残りが残る）。(d) 固定の 20 単位で切る（タンクの 20〜1,699 単位が残って別の流体を遮る。閾値は容量比で決める必要がある）。(e) 1/1,000,000 で 2^24 の充填率（MulDiv を書けば不要）。(f) 10^-9 で 128 ビット演算を全体に使う（必要なのは容量比と比例縮小の 2 箇所だけ）。
- **検証。** `FluidImmovableResidueTest`: 16/17 の閾値、タンクの 1,699/1,700、直列排水で全ノードが 0 と名なしになり損失が各ノード数十単位以内、動けない量の水が油を遮らず油が厳密に保存されハッシュが全走査と一致、閾値 + 1 の水は面を閉じたまま、ポートのノードは閾値以内の損失で空になる、閾値を超える流入は積み上がり閾値以下の流入は消える、0 にする tick を含めても分割不変。`FluidMulDivTest`: BigInteger との照合。`BoundaryPortDrainAndFeedbackTest` は「残量 0・名なし・渡した量は閾値以内の減り」に、`FluidNetworkReplicaTest` の流入は閾値を超える量に直した。
