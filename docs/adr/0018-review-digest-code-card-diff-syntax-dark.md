# 裁定サイトのコードカードをunified diff・構文着色・OS追従ダークで読ませる

`pr-independent-review` が出す `digest.html` のコードカードを、行番号のみの単色ブロックから
「行番号＋`+`/`-`グリフ＋構文着色」のunified diff表示へ変え、サイト全体をOS追従のダークモードへ対応させる。

出所: ユーザー裁定 2026-08-18「コードブロックは.csのシンタックスハイライトや+-の差分表示が欲しい / どこに注目したら良いか分からない」「あとついでにダークモード対応もしてほしい」

## 背景: 3つの欠落が重なって「何も表示されていない」に見えた

ユーザーは `https://review.moores.tech/pr/1167` のF01を見て「何も表示されていない」と述べた。調査で3層の問題が分離した。

1. **PR #1167 のdigestはコンバータを通っていない**。`runs/pr-1167/` に `digest.md` が無く、カードidが `F01`（コンバータは `f.id.lower()` で `f01` を吐く）、`class="ln"` と `<ins>` が全文で0個。コンバータがmasterへ乗ったのは16:45:52（PR #1168）で、1167のレビュー開始は16:32。**コンバータ以前のSKILL.mdで走った不可避の事故**であり、1167の再生成は行わない（出所: ユーザー裁定 2026-08-18「順番的にコンバータが作られる前のPRなの？それならしょうがない」）
2. **コンバータを通しても変更前が見えない**。`code-card` の記法 `[フラグ]<行番号>|<コード>` にはフラグ `+`（追加）と `*`（注目）しかなく、**削除行を表す手段が存在しない**。置換を「緑の追加行」だけで見せるため、何を何に変えたかが読めない
3. **色だけの識別に依存している**。`+` は緑背景・`*` は黄背景で、記号のグリフが無い。pr-1155-r2は92行中56行にフラグが付いており、緑が背景として支配的になって黄が沈む。加えて全言語が単色で、C#のキーワード・型・文字列・コメントが灰色の壁になる

## 決定

### 1. 差分表示はGitHub型unified（行番号の右に`+`/`-`/空白のグリフ列）

`code-card` に削除行 `-<行番号>|<コード>` を新設する。削除行の行番号は旧ファイルの番号を使い、赤系背景で描く。追加・削除・文脈の区別は背景色に加えて**必ずグリフ列**（`+` / `-` / 空白）で示し、色覚や暗所で色が潰れても読めるようにする。

棄却: 旧/新の2列行番号（GitHub完全再現だが `36,36|...` のような複雑な行記法になり、生成subagentの転記ミスが増える）／before/afterの2ブロック並置（短い置換に冗長で、抜粋が連続していない現状と噛み合わない）。

### 2. 削除行の欠落は patch.diff との照合でビルドを落とす

規約の明文化だけでは守られない（背景1がまさにその実例）。コンバータは同ディレクトリの `patch.diff` を読み、`+` 行を含む code-card について、その `+` 行が属するhunkに削除行があるのに `digest.md` へ書かれていなければ**エラーで非0終了**する。既存の「verifyを通るまで digest.md を直す」ループへそのまま乗り、書かない選択肢が消える。

照合対象は `+` 行を含むカードに限る（既存コードだけを引用して論拠にするカードは正当なので落とさない）。`patch.diff` は Step 3 が必ず生成し pr-1127 以降の全runに存在するため、不在はエラーとする（出所: agent前提。runディレクトリ16件の実測）。

棄却: 規約で必須化するだけ（守られなかったときに気づけない。今回の1167と同じ構造の穴）／コンバータが patch.diff から `-` 行を自動補完する案（「この変更を見せたい」という人の意図と自動挿入がずれたときにノイズが増える）。

### 3. 構文着色は highlight.js を digest.html へインライン同梱し、行ごとに適用する

CDN参照は `file://` で開ける自己完結HTMLという前提を壊すため採らない。ミニファイ済みの highlight.js をテンプレートへ直埋めし、ブラウザ側で着色する。1runあたり約127KBの増加を許容する（出所: ユーザー裁定 2026-08-18）。

適用単位は**行ごと**。各行を `<span class="ln">` / `<span class="sign">` / `<span class="code">` に分け、`code` 部分にだけ `hljs.highlight()` をかける。`highlightElement()` は `innerHTML` を丸ごと置換するため、行番号ガター・グリフ・注目行マークとそのままでは同居できない。行単位なら複数行にまたがる構文（`/* */` ブロックコメント・複数行文字列）の着色が崩れうるが、moorestechのコメント規約は `//` の日英2行セットであり実害が小さい。

棄却: 標準ライブラリのみの自前トークナイザ（依存ゼロだが精度が粗い）／pygments導入（システムpythonにもbrew pythonにも不在で、無人ハーネスに環境依存の失敗点を新設する。`codex` CLI不在で外部監査0/3になった前例と同型）／ブロック一括着色後に行分割（spanスタック追跡の自作処理が必要で、`-`行と`+`行を連結したテキストは文法的に壊れているため正しさが見かけ倒しになる）。

### 4. 言語は finding の `files` 先頭の拡張子から決める

`code-card` フェンスに言語を書かせず、YAMLの `files:` 先頭の拡張子をコンバータが言語名へ写す（`cs`→csharp、`ts`/`tsx`→typescript、`css`→css、`json`→json、`yml`/`yaml`→yaml 等）。未知拡張子は無着色にフォールバックする。生成subagentの手間ゼロで書き忘れが起こらない。1カードに複数言語が混ざる場合は後半が誤着色されるが、カードは単一ファイルの抜粋が原則なので許容する。

棄却: フェンスへ明示（書き忘れ・誤記の失敗点が増える）／自動＋フェンス上書き可（「どちらでもいい」が生成subagentの判断揺れを生む）。

### 5. 注目行（`*`）は背景ではなく左縁バーと文字コントラストで示す

追加=緑背景・削除=赤背景・構文色に黄背景を重ねると背景が3層になり、ダークモードで特に潰れる。注目行は左端の太い縦バー（アンバー）と文字色の強調で示し、背景色は追加/削除に譲る。

棄却: 黄背景の維持（追加行と重なると黄が勝ち、緑が見えなくなる。今回の不満の一部がこれ）／行外マーカー（横スクロールの向こうへ逃げて見えなくなる）。

### 6. ダークモードはサイト全体・OS追従のみ

対象は `digest-template.html`・裁定レイヤーCSS（`site/adj_style.py`）・一覧ページCSS（`site/style.py`）の3つすべて。テンプレートは11個のCSS変数を持つ一方、生の16進が109箇所残っており、これをトークン化する作業が実体になる。半分だけダーク化するとカードを押した瞬間に白が見えるため分割しない。

切替は `prefers-color-scheme` のみ。`digest.html` は毎run使い捨てで localStorage の引き継ぎが無く、トグルUIは既存のコメントUI（左下パネル・FAB）に並ぶ新UIを増やす割に価値が低い。

棄却: digest.htmlのみ／コードカードのみ（裁定ボタン・一覧が白のまま残る）／手動トグル併設。

### 7. findings.json の `excerpt` に削除行は含めない

`excerpt` は `pr-adjudicated-apply` が修正対象を特定する入力契約で、現行は「PR後の現行コード」の素テキスト。ここに `-` 行が混ざると、適用側が削除済みの旧コードを現行コードと誤読し、現行ファイルとの文字列一致も壊れる。`-` 行は人間が見るHTMLにだけ出す。

棄却: excerptもunified diffにする（適用スキル側の読み方も同時改修が必要）／excerptを `{lines:[{no,kind,code}]}` へ構造化する（findings.jsonスキーマの破壊変更で、裁定サイトと適用スキルの両方を同時に改修することになる）。

## 適用範囲

- 対象: `.agents/skills/pr-independent-review/`（`assets/digest-template.html`・`scripts/digest_md/`・`README-digest-format.md`・`tests/golden/`）と `~/hermes-agent/data/services/pr-review/site/`（`adj_style.py`・`style.py`・必要なら `inject.py`）
- 既存runの `digest.html` は再生成しない。PR #1167 も含め、次のレビューから新表示になる
- 見た目の回帰は既存のゴールデン（pr-1155）で担保する。`-` 行と着色を含む形へ期待HTMLを更新し、削除行を持つケースを追加する

### 8. 案（`options`）はコンバータがカード本文へ描き、手書きの代替案段落を禁止する

出所: ユーザー裁定 2026-08-19「裁定の選択肢のフィールドをちゃんと出すようにしてほしい。1167みたいに、それをデフォルトにして」

コンバータは `options:` を findings.json（裁定ボタンの入力）へしか渡しておらず、カード本文に案が出るかは生成subagentが `**代替案:**` 段落を手書きしたかどうかに委ねられていた。実測では手組みHTMLの pr-1167 が17箇所・golden の pr-1155 が12箇所で案を表示している一方、**コンバータ産の pr-1157 は0箇所**であり、最新の経路が最も案を落としやすい。

`_card_html` が `options` を案A/案B…の一覧として描き、先頭に推奨マークを付ける。手書きの `**代替案:**` 段落はコンバータがエラーで落とし、`recommendation:` は省略させて `options` 先頭から自動で埋める。案の正本は `options:` の1箇所になる。

これは `.decisions/2026-08-18-推奨案の3重記述は注意書きだけで留める.md` の撤回であり、その撤回は `.decisions/2026-08-19-案はoptionsを正本としてカードへ機械描画する.md` に記録した。当時の棄却理由（要約の自由度を失う／ゴールデンの書き直しが要る）は、`options` が元から自由文であることと、本ADRのplanで既にゴールデンを書き直すことで解消している。

棄却: 手書き段落とoptions描画の併存（同じ案が1カードに2回出て片方だけ古くなる事故が残る）／案の列挙はoptionsへ寄せつつ本文には案間の関係だけ書かせる（機械判定が難しく運用で境界が崩れる）。
