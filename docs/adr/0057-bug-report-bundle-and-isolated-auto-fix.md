# 0057. バグ報告は常時記録のバンドルを送り、隔離環境でサーバー状態を忠実再生して自動修正する

日付: 2026-09-11
状態: 採択

## Context

テストプレイ中に見つけたバグを、プレイを止めずに送信し、Mac mini側で自動的に再現・修正させたい。既存資産として、単一 `save.json` のワールドセーブ（`Game.SaveLoad`、tick末尾の `WorldSaveCoordinator.SaveIfRequested`）、クライアントからの即時セーブ要求（`va:save`＋完了イベント）、固定ワールドからPlayMode起動できるプレイテストDSL（`Client.Playtest`、環境変数 `PLAYTEST_WORLD_DIRECTORY`）、サーバーのtick駆動（`GameUpdater` 1tick=50ms、受信パケットは `TickEndPacketQueue` でtick末尾に処理）がある。無いのは受信パケットの記録、報告UI、バンドル化、Mac miniへの運搬、再現側の自動起動。

実測（world_1複製・ブロック8048個・save.json 3.1MB）: JSON組み立て105〜210ms、書き込み3〜6ms、要求から完了通知まで87〜155ms。ブロック部が99%で、各コンポーネントが個別にJSON文字列化するためDTO組み立て約80ms＋外側JSON化約30ms。サーバーtickは専用スレッドで追いつき処理なし。

## Decision

- **再現の到達目標は「サーバー状態の忠実再生」。スナップショット＋処理tick付き受信パケット列でバグ直前のサーバー状態を機械的に復元する。連続スナップショットの突き合わせで決定性を実測担保し、乱数シード化と非決定箇所の是正を本件の範囲に含める。クライアント側の最後の操作は説明文と画面フレームからエージェントが補う。**
  出所: ユーザー裁定 2026-09-11 質問「『再現』の到達目標をどこに置きますか？」→ 選択「サーバー状態の忠実再生」（[[2026-09-11-バグ報告の再現目標はサーバー状態の忠実再生とする]]）。乱数は原文「乱数統一はok」
  棄却案: 最良の出発点まで（パケット再生なし）／入力レベルまで完全自動再現（生入力フレーム再生）

- **送り手はv1では開発者本人（Editorと自作ビルド）のみ。常時記録は常にオン、バンドルに未コミット差分やローカルパスを含めてよい。プレイヤー配布版からの報告は将来目標であり本件では作らない。**
  出所: ユーザー裁定 2026-09-11 原文「基本は1、将来的には3」（質問「送り手は誰ですか？」の選択肢1=開発者本人のみ、3=プレイヤー配布版からも）（[[2026-09-11-バグ報告の送り手は当面開発者本人のみとする]]）
  棄却案: 将来は外部テスターも（HTTPアップロード・認証を今から入れる）／プレイヤー配布版からも今回対応

- **運搬は「本体はローカルoutboxへ書くだけ」＋「別プロセスの運搬スクリプトがTailscale経由でMac miniのinboxへrsync」。Tailscaleに入れない機材への手当ては初版では何もせず、将来のプレイヤー版で作るHTTP受け口に委ねる。**
  出所: ユーザー裁定 2026-09-11 質問「バンドルをMac miniへ運ぶ経路は？」→ 選択「Tailscale経由のrsync」（[[2026-09-11-バグ報告バンドルの運搬はTailscale経由rsyncとする]]）。ビルド検証機については原文「ない可能性がある」（Mac miniへ直接届くネットワークか、の問いに対して）。繋がらない機材の扱いはユーザー裁定 2026-09-11 原文「何もしない、繋がらないときは将来的なhttp経路を使う」（[[2026-09-11-Tailscaleに繋がらない機材の運搬は初版では何もしない]]）
  棄却案: Mac miniのHTTP受け口（cloudflared公開）／Mac miniのGitLabを受け口にする

- **報告UIはポーズメニュー（Escape）に説明文の記述欄と送信ボタンを直接置く。送信後はポーズメニューが閉じてゲームへ戻り、outboxへの書き出し完了をトーストで知らせる。サーバーは報告中も止めない。**
  出所: ユーザー裁定 2026-09-11 原文「エスケープを押して、ぱっとその旨を書いて送信ボタンを押したら」→ 選択「ポーズメニューに記述欄と送信を直置き」（[[2026-09-11-バグ報告の入口はポーズメニューへ記述欄と送信を直置きする]]）
  棄却案: ポーズメニューに「バグ報告」ボタン→モーダル／専用キーで直接報告モーダル

- **Mac mini側の自動修正ランは、再現できたら再現テスト＋修正＋修正後のプレイ録画をdraft PRにまとめて止まる。マージはしない。再現不能・仕様曖昧の場合はコードを触らず、試したことと質問をbdへ積む。**
  出所: ユーザー裁定 2026-09-11 質問「自動修正はどこまでを終点にしますか？」→ 選択「再現テスト付きdraft PRまで」（[[2026-09-11-バグ報告の自動修正は再現テスト付きdraft-PRを終点とする]]）
  棄却案: 再現と原因特定まで（修正はしない）／レビュー通過なら自動マージ

- **画面録画は本体が描画結果を非同期読み出しして子プロセスのffmpegへ流し、分割ファイルで直近をリング保持する。各フレームにサーバーtickを対応付ける。ffmpeg不在時はスクリーンショットのみに縮退し、理由をログとmanifestに残す。**
  出所: ユーザー裁定 2026-09-11 質問「画面録画はどこで撮りますか？」→ 選択「ゲーム内でフレームを読み出しffmpegへパイプ」（[[2026-09-11-バグ報告の画面録画はゲーム内フレーム読み出しをffmpegへパイプする]]）。両用は原文「動画はエージェント用でも人間用でもあります」
  棄却案: OS画面をffmpegサイドカーで常時録画／動画は作らず連番スクショのみ

- **draft PRの再現テストは、ワールドファイルに依存しない最小の合成NUnit（既存サーバーテストと同型）を正とする。バンドルを読むプレイテストシナリオと録画はPR本文の証拠に留め、バンドル本体はmoorestech_logs側に置く。最小化できないバグはPRに「プレイテスト証拠のみ」と明記する。**
  出所: ユーザー裁定 2026-09-11 質問「再現テストはどの形を正としますか？」→ 選択「合成NUnitを正とし、バンドル依存のプレイテストは証拠扱い」（[[2026-09-11-バグ報告の再現テストは合成NUnitを正としバンドル依存プレイテストは証拠扱い]]）
  棄却案: スナップショットをフィクスチャとしてコードrepoにコミット／再現テストを必須にしない

- **取得側（常時記録・バンドル化）はランタイムC#で完結させ、Editor依存は再現側だけに許す。ビルドにはビルド時生成のBuildInfo（コミット・master dataピン・dirtyフラグ）を焼き込む。**
  出所: agent前提（原文「テストはメインはエディタだがそのうちビルド版も入る」から導出。ADR本文の裁定ではなく設計上の帰結）

- **スナップショットは通常セーブと同一形式（`WorldSaveAllInfoV1`）で、プレイヤーのsave.json/.bakとは別ディレクトリに処理tick番号付きで30秒周期・4世代のリング保持する。Escapeでポーズメニューを開いた瞬間にも即時スナップショットを取る。セーブ形式に現在tickと乱数状態を追加し、ロードで復元する。**
  出所: 周期30秒はagent前提（ユーザーの懸念 原文「自動セーブ5分起きは再現性等が厳しい気もする」への回答として提示、異議なし）。4世代＝直前2分はユーザー裁定 2026-09-11（Codex残問「直前の記録をどれだけ確実に残すか」→ 選択「直前2分」、[[2026-09-11-バグ報告の常時記録は直前2分を確実に残す]]）。Escape時点の確保はユーザー裁定 2026-09-11（Codex残問「記入中もワールドの時間を進めるか」→ 選択「進める。Escapeを押した瞬間の記録を確保しておく」、[[2026-09-11-バグ報告の記入中もワールド時間は進めEscape時点の記録を確保する]]）
  棄却案: 直前30秒／直前5分／記入中だけサーバーtickを止める

- **スナップショットは体感できる引っかかりを出さない。ブロックコンポーネントのセーブ状態（`IBlockSaveState.GetSaveState` の文字列）をオブジェクトで返す形へ改め、JSON化と書き込みをtickスレッドの外で行う。tickスレッドに残る取り込みは1tick（50ms）内に収まりtickを取りこぼさないことを実測で確認する。通常セーブも同じ経路になる。**
  出所: ユーザー裁定 2026-09-11（Codex残問「30秒ごとの約0.1〜0.2秒の停止を初版で許容するか」→ 選択「体感できる引っかかりが出ないことを初版の条件にする」、[[2026-09-11-スナップショットは体感できる引っかかりを出さないことを初版の条件にする]]）
  棄却案: まず許容し支障があれば改善（現行セーブ経路のまま2〜4tick停止）

- **パケットログの記録点はサーバーのtick末尾処理（`ReceiveQueueProcessor.ProcessPacket` 相当）で、「処理tick＋生バイト列」を順に記録する。保持はリング最古世代のtick以降。再生はスナップショットをロードし、同じ処理tickでパケットを流し直す。**
  出所: agent前提（サーバーがtick境界で処理する既存構造に合わせ、クライアント側送信時刻との対応付けを不要にする）

- **乱数は非シードの `new Random()`（`ProbabilityCalculator`・`MachineOutputFactoryUtil`・`TrainCarInstanceId`・`VanillaStaticMapObject`）とstatic共有Randomを廃し、ワールドseed由来で状態をスナップショットに含める単一の決定的乱数サービスへ集約する。**
  出所: agent前提（忠実再生の裁定から必要。原文「乱数統一はok」）

- **決定性検査（スナップショットkから再生しk+1と突き合わせ）は再現側の自動修正ランの最初の段で必ず実行し、発散したDataStoreを報告する。発散があればエージェントはその是正を優先する。ローカルでも同じツールを実行できる。**
  出所: agent前提（忠実再生の担保手段。推測ではなく実測で非決定箇所を洗い出す）

- **常時記録の有効化は起動設定のフラグで、通常起動はオン、NUnitテストとプレイテストDSLはオフ。**
  出所: agent前提（テストのノイズと書き込みを避ける）

- **バンドルは manifest（コミット・dirty・未コミット差分・master dataの実チェックアウト値・プラットフォーム・Editor/ビルド・報告tick・各スナップショットtick・説明文・縮退項目と理由・カメラ位置向き・開いているUI）＋スナップショット群＋パケットログ＋動画と連番フレーム＋Unityログのリング＋報告時スクリーンショット。取得側と再現側の契約はこのバンドル形式のみ。**
  出所: agent前提（壁打ちで提示し異議なし。契約を固定して両側を独立に作る）

- **Mac mini側は inbox を監視し、バンドル1件ごとに隔離worktreeを切って自動修正ランを直列に起動する（サーバーポート11564固定のためプレイテストは同時1つ）。運用は既存のMac mini無人開発運用（タスク毎worktree・PR更新hook）に乗せる。**
  出所: agent前提（既存運用と前例一致）

- **クライアント→サーバーの「今すぐ記録を確定してバンドル用に書き出せ」は新設プロトコル1本（Mode enumで操作分岐）で行い、設計は creating-server-protocol スキルの型に従う。**
  出所: agent前提（moorestech-principles「1プロトコル＝1ドメイン」）

- **初版の完成条件はMacのEditorでの「報告→Mac mini再現→draft PR」の通し。自作ビルドからの報告の実機確認は後続タスク。**
  出所: ユーザー裁定 2026-09-11（Codex残問「初版の完成条件に含める実行環境」→ 選択「MacのEditorまで」、[[2026-09-11-バグ報告システム初版の完成条件はMacのEditorまでとする]]）
  棄却案: MacのEditorとMac自作ビルド／EditorとMac・Windows自作ビルド

- **本体repoとmaster dataの未コミット差分（新規ファイル含む）をバンドルに入れ、Mac miniは同コミットのworktreeへパッチを当てて再現する。Play中のInspector編集・ホットリロードは復元しない。差分がサイズ上限を超えたらパス一覧だけ残しmanifestに縮退を記録する。**
  出所: ユーザー裁定 2026-09-11（Codex残問「開発途中の状態をどこまで再現対象にするか」→ 選択「ファイル変更まで対応、Play中だけの編集は対象外」、[[2026-09-11-バグ報告は未コミットのファイル変更まで再現対象としPlay中編集は対象外]]）
  棄却案: コミット済みの内容で起動したプレイだけ対象／Play中のInspector編集・ホットリロードも含める

- **再現は必ず報告時のコミット＋差分で行う。修正の土台は、同じ再現テストが最新masterでも落ちればmaster基底の新ブランチ、落ちなければ報告ブランチ基底の新ブランチ（PRは報告ブランチ宛て）。**
  出所: ユーザー裁定 2026-09-11（Codex残問「報告バージョンが最新masterと違うとき修正はどこへ届けるか」→ 選択「報告ブランチで再現し、masterにもあるならmaster向け、無ければ報告ブランチ向け」、[[2026-09-11-バグ修正の届け先は報告ブランチで再現しmasterにもあればmaster向けとする]]）
  棄却案: 常に報告した作業ブランチ向け／常にmaster向け

- **初版はゲームが操作できる状態での手動報告のみ。クラッシュ・フリーズの専用UIや自動検知は作らない。**
  出所: ユーザー裁定 2026-09-11（Codex残問「クラッシュやフリーズも報告対象に含めるか」→ 選択「初版は操作できる状態での手動報告に絞る」、[[2026-09-11-バグ報告初版はクラッシュとフリーズを対象外とし手動報告に絞る]]）
  棄却案: 再起動後に前回の記録を報告できるようにする／クラッシュ・フリーズを検知して自動送信

- **バンドルは本人とエージェントだけが閲覧する。公開repoのdraft PRには再現手順の説明とmoorestech_logs内のパスだけを書き、動画・スナップショット・修正後の録画は添付しない。**
  出所: ユーザー裁定 2026-09-11（Codex残問「バンドルの閲覧範囲」→ 選択「本人とエージェントだけ。公開PRには説明とパスだけ」、[[2026-09-11-バグ報告バンドルの閲覧は本人とエージェントに限り公開PRには説明とパスだけ載せる]]）
  棄却案: 修正後の録画だけは公開PRに添付／報告ごとに公開可否を選ぶ

- **添付が欠けても送信できる。ポーズメニューで欠けた項目を見せ、manifestに欠損項目と理由を残し、エージェントはある資料で進める。**
  出所: ユーザー裁定 2026-09-11（Codex残問「添付が揃わないときの送信」→ 選択「欠けた項目を表示し、残った資料で送信・調査」、[[2026-09-11-バグ報告は添付が欠けても残った資料で送信し調査する]]）
  棄却案: スナップショットとパケットログを必須にし動画の欠損だけ許容／すべて揃うまで送信しない

- **自動修正ラン1件に時間・利用枠の上限は設けず、解決か明確な行き詰まりまで続ける。**
  出所: ユーザー裁定 2026-09-11（Codex残問「難航する1件にどこまで時間・利用枠を使ってよいか」→ 選択「上限なし、解決か行き詰まりまで続ける」、[[2026-09-11-バグ報告の自動修正ランは上限なしで解決か行き詰まりまで続ける]]）
  棄却案: 1件ごとに上限を設ける／1日単位の共有予算内で続ける

## Consequences

- 通常セーブの形式に現在tickと乱数状態が加わる。既存セーブの移行は moorestech-save-migration スキルで扱う。
- 乱数集約は確率産出・過負荷破損・燃料消費・列車ID採番の挙動を「同一seed・同一操作列なら同一」に変える。ゲーム体験上の差は無い前提。
- ブロックコンポーネントのセーブ状態の返し方が全コンポーネント（JsonConvert呼び出し28箇所）で変わる。通常セーブの停止も同時に消える。
- ffmpegは開発機の前提ツールになる。不在時は録画無しに縮退し、その事実がmanifestとログに残る。
