# 0053. SDD規模ゲート未満は本体インラインでなくopus固定の単一subagentで実装する

日付: 2026-09-08
状態: 採択

## Context

`subagent-driven-development`（SDD）スキルは、規模ゲート（約15ファイル/約1,000行/実装7タスク以下/長いデバッグ往復なし/並列不要のAND）未満の計画を「本体セッションが直接コードを書くインライン実装」に落としていた（ADR相当: `.decisions/2026-08-20-SDD規模ゲートはインライン優先のAND条件にする.md`）。SDD本体はタスクごとにimplementer subagentを派遣しタスク別レビューゲートを置くため、1計画あたり$40〜90の固定費と本体ループの肥大が乗る。その回避策がインラインだったが、インラインは本体コンテキストを実装で消費し、最終レビュー対応の余力を削る。

前セッションで「インラインモードのとき単一subagentモードでsonnet実装になっているか」と問われ、「なっていない」と回答。中間モードを足す設計が承認され、implementerはsonnetでなくopusにする旨が明言された。スキルはmoorestech特化版（`.agents/skills/subagent-driven-development/`）とプロジェクト非依存の一般版（`~/.agents/skills/subagent-driven-development/`、git管理外）の2系統が意図的に分岐しており、両方へ同じ意味の変更を各語彙で入れる。

## Decision

- **規模ゲート未満は「単一subagent実装モード」へ全面置換し、本体は実装コードを書かない。** opus固定のimplementer subagent 1体が計画全体を実装し、本体はワークスペース隔離・事前計画レビュー・派遣・最終レビュー・PR作成のみを担う。「インライン実装」という選択肢は廃止する。
  出所: ユーザー裁定 2026-09-08 原文「インラインはやっぱsonnetではなくopusにして（トークンコストがそこまで大きくならないのと精度優先）」「このrepoのskillも~.agentsもどっちも」→ 選択「A. 全面置換」（プレビュー: 2段ゲート・SDD閾値未満→単一opus subagent・本体は実装しない）
  棄却案: ①B. 2段階閾値（極小〜数ファイル/〜200行は本体インラインを残す。agent推奨案だった）②C. 第3の任意選択肢（既定はインライン、本体コンテキストが薄い時だけ落とす）

- **単一subagent↔従来SDDの境界閾値は現行の5条件ANDを維持する。** 新モードの実測が出たら再調整する。
  出所: ユーザー裁定 2026-09-08 選択「現行閾値を維持」
  棄却案: ①閾値を広げる（約20ファイル/1,500行/10タスク）②閾値を狭める（約10ファイル/600行/5タスク）

- **契約は implementer-contract.md を共有し、派遣は新規 single-implementer-prompt.md で行う。** ブリーフは `scripts/task-brief` で抽出せず計画ファイル全体のパスを直渡しする。プロンプトで「タスク順に実装しタスクごとにコミット」「報告ファイルへタスク別進捗をコミットsha付きで追記」を指示する。契約本文の「タスクブリーフ」語はタスク単位・計画全体の両方を指す語へ一般化する。
  出所: ユーザー裁定 2026-09-08 選択「契約共有＋専用プロンプト」
  棄却案: ①専用契約 single-implementer-contract.md を新設 ②既存 implementer-prompt.md を流用

- **worktree隔離は単一subagentモードにも必須として及ぶ。** 例外は既存の2つ（既にworktree内／人間が本体実装を明示）のみ。「worktree隔離が必要なだけならworktree＋インラインでよい」の一文は削除する。
  出所: ユーザー裁定 2026-09-08 選択「必須として及ぶ」
  棄却案: 任意のまま

- **タスクごとのレビューゲートは置かず、最終レビュー1本のみ。** 完了後に moores-code-review（一般版: プロジェクトのレビュースキル or all-code-review）を自動・無条件で実行し、所見は単一fix subagent（opus）へ渡す。
  出所: ユーザー裁定 2026-09-08 選択「無し・最終レビュー1本のみ」
  棄却案: ①計画の半分で中間レビュー1本 ②タスクごとにレビュー

- **「モデル選定」節は例外として冒頭に明記する。** 「単一subagentモードのimplementerとそのfix subagentはopus固定。以下のティア規則は従来SDDのタスク単位派遣にのみ適用」を足し、ティア規則本文は変えない。
  出所: ユーザー裁定 2026-09-08 選択「例外として明記」（根拠原文「トークンコストがそこまで大きくならないのと精度優先」）
  棄却案: 節を書き換え「実装は常にopus」へ統一

- **途中失敗（コンテキスト枯渇・途中BLOCKED・一部タスクのみDONE）は継続単一subagentを再派遣する。** 報告ファイルのタスク別進捗と `git log` で完了タスクを確定し、残りタスクのみを指示した2体目を同テンプレで派遣する。反復上限は2回、それでも終わらなければ規模誤判定とみなし残りを従来SDDへ切り替える。従来の「インラインで始めてコンテキスト残量3割でSDDへ」の途中切替規定はこれに置き換える。
  出所: ユーザー裁定 2026-09-08 選択「継続単一subagentを再派遣」
  棄却案: 残りは即従来SDD

- **進捗台帳は派遣時・完了時の2行、タスク別進捗は報告ファイル。** コントローラーは `progress.md` へ「単一subagentモード派遣 base <sha> 報告=<path>」と「完了 commits <base>..<head>」のみ書く。compaction後の復旧は台帳→報告ファイル→`git log` の順。
  出所: ユーザー裁定 2026-09-08 選択「派遣時・完了時の2行＋報告ファイル」
  棄却案: subagentが台帳も直接書く

- 以下はagent前提（ユーザーは共通理解として承認したが、ユーザー裁定には昇格しない）:
  - 単一subagentはフォアグラウンドで派遣する（前提: SDD subagentのバックグラウンド孤児化事故のメモリ）
  - 派遣前の事前計画レビューと判定の声出しはコントローラーが従来どおり行う
  - 使用場面dot図・危険信号・ワークフロー例・descriptionを新モードに合わせて更新する
  - 両スキルは同じ節構成で各語彙にて手書きする（機械コピー禁止）

## Consequences

- 極小修正（1ファイル数行）でもworktree作成・ブリーフ往復・報告ファイルが発生する。本体コンテキストを薄く保つことを優先した意図的なトレードオフ。
- 2026-08-20裁定のうち「ゲートの向き（AND）・実装タスクの数え方・判定の声出し」は生きたまま、「閾値未満の行き先」だけが差し替わる。
- 新モードの実測（完走率・compaction発生・コスト）が溜まったら閾値を再裁定する。
