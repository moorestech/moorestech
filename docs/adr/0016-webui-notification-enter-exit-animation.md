# 通知の出入りにアニメーションを許可し生存尺から逆算して駆動する

デザイン哲学 §6 は「装飾アニメーションを増やさない」と定め、実際に Web UI のCSSにはアニメーション・トランジションが**1件も存在しない**（唯一の動きは `shared/treeView` のパン慣性で、これはJS実装の「操作の物理」として §8.5 が別扱いしている）。今回、通知が出るとき・消えるときの演出を入れたいという要望を受け、**`NotificationHost`（サーバー発のゲーム通知）の出入りに限り §6 の例外を認める**。演出は左から固定長（12px級）のスライドインと不透明度のフェードイン、退場はその逆再生とし、色相・形・光彩の語彙は増やさない。

実装上の要点は、**退場のために状態を増やさない**ことである。`notificationStore` は「タイマーで削除されるまで存在する」という1状態のみを持ち続け、退場開始時刻は生存尺から「生存尺 − 退場尺」として導出して、CSS側で遅延付きの退場アニメーションとして表現する。生存尺は `DISPLAY_MS` を単一の正とし、要素へインラインのCSS変数で渡す。あわせて生存尺を5秒から**7秒**へ延ばし、入場（160ms級）と退場（200ms級）はその7秒の内側に含める。

出所: ユーザー裁定 2026-08-17（対象=`NotificationHost` のみ／演出=左からの小さなスライド＋フェード／「通知がタイマーで完全に消えるまで存在するというステートでいいんじゃないの？」＝退場状態を持たせない／「7秒で含める」／同時表示数の上限は設けない）

## Considered Options

- **store に `entering`/`visible`/`exiting` と二段タイマーを持たせる**（却下）: agentの当初推奨。単体テストで退場遷移を直接検証できるが、退場開始は既知の生存尺から算出できるため状態としては冗長だという指摘を受けて棄却した。
- **View 側に保持リストと `onAnimationEnd` を持たせる**（却下）: store無変更で済むが、表示中リストの真の状態が store と View に二重化する。
- **不透明度のフェードのみ**（却下）: 語彙追加が最小だが、動く3D世界の上に半透明面が薄く現れるため発生に気づかない場面がある。
- **積み替え（既存通知が下へ押される動き）も補間する**（却下）: 高さ可変リストの補間はFLIP相当の実装が必要で、e2eの座標検証が不安定になる。
- **`ToastHost` も同じ演出へ揃える**（却下）: ToastHost は Mantine `Notification` 剥き出しの様式外負債（§3違反）で、演出より様式化が先。別issue `moorestech-cgm` へ送った。
- **同時表示数に上限を設ける／同一メッセージを「×N」へ集約する**（却下）: 7秒化で連打時の溢れ確率は上がるが、現行5秒でも起こりうる既存の性質であり、仕組みを増やさない方を選んだ。

## Consequences

- **§6 の改訂が必須**（「装飾アニメーションを増やさない」に通知の出入りという明示の例外を書く）。§8 の NotificationHost 条項へ演出・尺・駆動方式を追記する。目標HUD側の「アニメーションは追加しない」（§8.14）は維持する。
- `DISPLAY_MS` は 5000 → 7000。完全不透明で読める時間は約6.6秒になる。
- **e2eは同期検証できる形に保つ**（§6の要件）。アニメーション名と尺をCSS契約として検証し、内容のアサーションは `element.getAnimations()` の完了待ちで同期させる。テスト時に尺をゼロへ落とす抜け道は作らない（実挙動と乖離するため）。（出所: agent前提）
- `prefers-reduced-motion` の分岐は実装しない。Web UI は CEF 埋め込みのゲームオーバーレイで媒体側のOS設定が届かず、分岐を増やす価値がないため。要求が出た時点で改めて裁定する。（出所: agent前提）
- 生存尺がJSとCSSの2箇所に散ると「面が消えてから残る／途中で切れる」破綻が出る。`DISPLAY_MS` からインラインCSS変数で流し込む一方向の依存を崩さないこと。
